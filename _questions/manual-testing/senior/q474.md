## The Intent
The interviewer is checking whether you can solve the regression scaling problem — where release frequency increases but testing capacity does not. At senior level, they want to see a systematic triage model that uses real data to make selection decisions, not intuition or habit, and that can be communicated to stakeholders transparently.

## The STAR Script
**Situation:** I was leading manual QA for a product that had moved from monthly to weekly releases. The regression suite contained 280 manual test cases, which took 14 engineer-hours to execute fully. With weekly releases, full regression every week consumed the entire QA capacity — no capacity remained for new feature testing, exploratory testing, or any quality debt work. The team was running full regression by default regardless of what had changed.

**Task:** Design a triage model that selected the right regression tests for each release automatically, making the selection process transparent, defensible, and quick — without requiring significant analysis time before every release.

**Action:** I built a three-input triage model implemented as a shared spreadsheet updated before each release cycle. Input 1 — change fingerprint: I maintained a coverage map linking each of the 280 test cases to the product areas and components it covered. Before each release, I reviewed the release notes and tagged each story and bug fix with its component. The triage model automatically flagged all test cases linked to changed components as mandatory. This was the change-driven minimum set. Input 2 — defect cluster amplification: I maintained a 12-month defect cluster map — which components had generated the most defects historically, weighted by recency (recent defects counted more heavily than old ones). Components in the top quartile of defect density received amplified regression priority: all test cases covering those components ran regardless of whether that component had changed in the current release. I called these "always-watch" components — historically unreliable areas that earned ongoing scrutiny. Input 3 — critical journey protection: I permanently classified 22 test cases as non-negotiable — they covered the five highest-value user journeys (payment, authentication, core data entry, reporting, and export). These ran in every release, regardless of change or defect history. They were the floor below which no triage could go. Output — release regression set: the triage model combined the three inputs and produced a specific named list of test cases for that release, with a count and estimated execution time. For a typical small release, the output was 60–80 cases (4–5 hours). For a large release touching multiple components, it was 120–150 cases (7–9 hours). I shared the triage output with the engineering lead before each cycle as a one-paragraph summary: "This release touches payments and notifications. The triage has selected 74 cases — 22 critical journeys, 31 from change impact, 21 from defect cluster amplification. Estimated execution: 4.5 hours. Deferred: 206 cases covering stable, unchanged components with no defect history."

**Result:** Weekly regression execution time dropped from 14 hours (full suite) to an average of 5.5 hours (triage output). The deferred coverage was reviewed quarterly in a full regression cycle. Defect escape rate through triage-selected regression remained equivalent to the full suite — the triage was selecting the right tests. One quarter, the triage model output a warning flag: a component that had been stable for six months suddenly appeared in three consecutive releases — I elevated it to "always-watch" status proactively, before it generated defects.

## Key Terms

| Term | Definition |
|------|------------|
| **Regression triage** | The process of selecting which regression tests to execute for a specific release, based on risk rather than running the complete suite |
| **Coverage map** | A document or structure linking test cases to the product components and areas they cover — the foundation for change-driven test selection |
| **Change fingerprint** | The set of product components and areas modified in a specific release — used to select test cases covering those areas |
| **Defect cluster** | A product component or area with a historically elevated defect rate — indicating inherent fragility that warrants elevated regression attention |
| **Defect cluster amplification** | Elevating the regression priority of historically high-defect areas regardless of whether they changed in the current release |
| **Critical journey protection** | A permanently classified set of test cases covering the highest-value user journeys that run in every release without exception |
| **Triage output** | The release-specific named list of selected test cases, with count, estimated execution time, and a summary of the selection rationale |
| **Deferred coverage** | Test cases not selected for a specific release — explicitly documented, not silently omitted, with a plan for when they will be executed |
