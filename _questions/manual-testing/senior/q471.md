## The Intent
The interviewer is checking whether you treat accessibility as a systematic quality discipline — not a compliance checkbox or an afterthought. At senior level, they want to see a complete strategy: the coverage framework, the tools, the assistive technology testing, the governance model, and how you build accessibility into the delivery workflow rather than auditing for it retrospectively.

## The STAR Script
**Situation:** I led QA for a public-facing government service that was legally required to meet WCAG 2.1 AA under the Public Sector Bodies Accessibility Regulations 2018. An external audit had found 34 accessibility violations — 11 of which were classified as serious. The development team had never received accessibility testing as part of the QA process; all findings had come from the external audit. I was asked to redesign the QA practice so that accessibility was tested continuously, not retrospectively.

**Task:** Design a comprehensive accessibility testing strategy that embedded WCAG compliance into the delivery process, covered all four categories of disability, and produced the evidence required for the mandatory accessibility statement.

**Action:** I designed the strategy across four layers. Layer 1 — automated scanning as a baseline gate: I integrated axe-core into the Playwright test suite and into the Storybook component library. Automated scanning ran on every PR and caught the structural issues detectable by DOM inspection — missing ARIA labels, insufficient colour contrast, missing form labels, and keyboard trap patterns. I configured it to fail builds on WCAG 2.1 AA violations with no baseline exceptions — all violations required fixing or explicit documented justification. Layer 2 — keyboard-only navigation testing: I created a keyboard testing charter for every new feature and every sprint regression cycle. The charter covered six key behaviours: all interactive elements are reachable by Tab key in a logical order, focus is always visibly indicated, modals trap focus correctly and return focus on close, skip navigation links work, no keyboard traps exist, and all functionality achievable by mouse is achievable by keyboard. This required no assistive technology — any tester could conduct it. Layer 3 — screen reader testing with real assistive technology: I introduced monthly screen reader testing sessions using NVDA with Firefox (most common combination for UK public sector users) and VoiceOver with Safari for iOS. I created a structured screen reader test script for the five most critical user journeys, covering: heading structure and page landmarks for navigation, meaningful link and button text (not "click here"), form error announcements, dynamic content updates announced to screen reader users, and image alt text accuracy. I trained two QA engineers in screen reader testing through a structured programme — four 2-hour sessions with real-world exercises. Layer 4 — cognitive and plain language review: for every new content addition I applied a plain language review against the GOV.UK content design principles, checking reading age, use of active voice, and avoidance of jargon. This addressed WCAG 3.1 (Readable) which automated tools cannot assess.

**Result:** The strategy reduced new accessibility violations reaching the external audit from 34 to 3 in the following annual review — all three were complex cognitive accessibility issues in a newly added feature. The automated gate prevented 47 structural violations from being merged in the six months following implementation. The screen reader testing sessions caught 8 issues the automated scanner had missed — including a dynamic search results panel that updated without announcing the result count to screen reader users, and a date picker that was keyboard-navigable but whose month/year controls were not labelled for screen readers.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Can run an automated axe-core scan and identify failing elements; understands that keyboard navigation should be tested |
| **Mid** | Conducts keyboard navigation testing and basic screen reader testing; integrates automated scanning into a pipeline |
| **Senior** | Designs a four-layer accessibility strategy — automated scanning, keyboard testing, screen reader testing with real AT, and cognitive/plain language review — embedded in the delivery workflow, producing audit evidence and building team capability |

## Key Terms

| Term | Definition |
|------|------------|
| **WCAG 2.1 AA** | Web Content Accessibility Guidelines version 2.1 at the AA conformance level — the standard required by UK public sector bodies and referenced in equality legislation |
| **axe-core** | An open-source accessibility testing engine that scans rendered pages for programmatically detectable WCAG violations |
| **Keyboard trap** | A UI condition where keyboard focus enters an element and cannot exit using standard keyboard controls — a WCAG failure |
| **Screen reader** | Assistive technology that converts on-screen content to speech or braille output — NVDA (Windows), JAWS (Windows), and VoiceOver (macOS/iOS) are the most widely used |
| **ARIA (Accessible Rich Internet Applications)** | A set of HTML attributes that provide semantic meaning to assistive technology — used to label interactive elements and communicate dynamic content changes |
| **Focus management** | The programming practice of controlling where keyboard focus moves in response to user interactions — critical for accessible modal dialogs and dynamic content |
| **Plain language review** | An assessment of written content for reading age, clarity, and use of active voice — addressing WCAG criteria that automated tools cannot evaluate |
| **Accessibility statement** | A legally required document published by public sector bodies describing their accessibility conformance, known issues, and remediation plans |
