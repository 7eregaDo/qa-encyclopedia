## The Intent
The interviewer is checking whether you understand test documentation as a discipline with competing requirements — not just a bureaucratic overhead. In regulated contexts (medical devices, financial services, pharmaceutical software, aviation), test documentation is legal evidence. At senior level, they want to see that you have designed documentation standards that serve both engineering and compliance needs without creating documentation debt that nobody maintains.

## The STAR Script
**Situation:** I led QA for a clinical decision support software product regulated as a medical device under the UK Medical Device Regulations. The MHRA required documented evidence that every software function relevant to clinical safety had been tested systematically, that the test results were traceable to the requirements they verified, and that deviations from expected results were formally resolved before release. The existing test documentation was informal — inconsistent formats, missing traceability, and test execution records that existed only as screenshots in a shared folder.

**Task:** Design test documentation standards that satisfied the MHRA's evidentiary requirements, were practical for a team of five QA engineers to maintain, and could withstand scrutiny in a regulatory inspection.

**Action:** I designed the documentation standard across four artefact types. Artefact 1 — Test Plan: a release-level document specifying the scope (which requirements are tested), the test approach (test types, environments, tools), the entry and exit criteria, the risk assessment for untested areas, and the roles responsible for execution and review. The test plan had a mandatory review and approval step — signed by the QA lead and the clinical lead before testing began. Template included: document ID, version, approval signatures with dates, and a change log. Artefact 2 — Test Case specification: each test case followed a mandatory structure — unique ID traceable to a specific requirement ID, objective (what property is being verified), preconditions (the exact system state required), test steps (numbered, unambiguous, action-verb format: "Navigate to...," "Enter...," "Verify that..."), expected result (specific, assertable, not "the system behaves correctly"), and clinical risk classification (Low/Medium/High — determining the required evidence level). High-risk cases required an independent second-reviewer signature. Artefact 3 — Test Execution Record: a completed copy of the test case with the actual result recorded for each step, the pass/fail decision, the tester's name and date, and — for any failure — a defect reference number. Execution records were stored immutably — no editing after completion. Failures were recorded honestly; a failed result followed by a fix and a retest produced two separate execution records, not an overwritten one. Artefact 4 — Traceability Matrix: a master document linking every regulated requirement to the test cases that verified it, and recording the test execution status. Any requirement without a test case was flagged as a documented risk gap requiring explicit justification. Any requirement where all test cases had not passed was a release blocker.

I implemented the standard incrementally — piloting with two engineers on the highest-risk module first, gathering feedback on friction points, then rolling out to the full team. I also built a review checklist that the QA lead used to verify documentation completeness before signing off the test plan.

**Result:** The MHRA inspection 14 months later reviewed the test documentation for the two most recent releases. The inspector cited the traceability matrix as "comprehensive" and the execution records as "complete and credible." Zero documentation-related findings were raised. Engineers reported that the structured test case format — particularly the specific expected results — had reduced ambiguity in execution and improved consistency between testers. The discipline of honest failure recording caught a case where a previous team had been recording failing steps as passing to avoid retest cycles — this practice was eliminated within one sprint of the standard's rollout.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Writes test cases with clear steps and expected results; records pass/fail results per test case |
| **Mid** | Maintains a traceability matrix linking test cases to requirements; ensures test documentation is complete before sign-off |
| **Senior** | Designs the full test documentation standard across four artefact types — test plan, test case specification, execution record, and traceability matrix — satisfying both engineering and regulatory audiences, with a review and approval process, immutable execution records, and a rollout programme that builds team capability |

## Key Terms

| Term | Definition |
|------|------------|
| **Traceability matrix** | A document mapping requirements to test cases and recording test execution status — demonstrating that all requirements have been verified |
| **Test Plan** | A release-level document specifying testing scope, approach, entry/exit criteria, and risk assessment — the governing specification for a testing cycle |
| **Immutable execution record** | A test result that cannot be edited after completion — ensuring the evidence is credible and the history of failures and retests is preserved |
| **Clinical risk classification** | A classification of test cases by their clinical safety relevance — determining the required level of evidence and review |
| **MHRA (Medicines and Healthcare products Regulatory Agency)** | The UK regulator for medical devices — conducts inspections that include review of software validation and test documentation |
| **Entry and exit criteria** | Defined conditions that must be met before testing begins (entry) and before testing is considered complete (exit) — making the boundaries of a testing cycle explicit |
| **Assertable expected result** | A specific, unambiguous outcome that can be definitively confirmed as pass or fail — "The error message 'Invalid date' is displayed below the date field" rather than "the system handles the error correctly" |
| **Documentation debt** | The accumulation of test documentation that is out of date, incomplete, or inconsistent with the current product — a compliance risk in regulated environments |
