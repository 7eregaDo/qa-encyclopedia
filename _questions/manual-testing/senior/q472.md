## The Intent
The interviewer is checking whether you understand that pre-production testing has inherent limitations — real users, real data volumes, real infrastructure load, and real usage patterns create conditions that staging environments cannot replicate. At senior level, they want to see that you can design a structured, monitored approach to production validation that manages risk through controlled exposure rather than avoiding production testing entirely.

## The STAR Script
**Situation:** My organisation was releasing a significant rewrite of the search and filtering system — the most used feature in the product, handling 4 million queries per day. Pre-production testing had been thorough, but the team knew that real production query distributions and user behaviour would exercise the system in ways the staging environment could not reproduce. The risk of a full production release without any production validation was too high — but so was the risk of blocking all users on an untested system.

**Task:** Design a testing in production strategy that validated the new search system under real production conditions progressively, with structured observation and defined rollback triggers at each stage.

**Action:** I designed a four-stage production validation programme. Stage 1 — dark launch (shadow mode, 0% user exposure): I ran the new search system in shadow mode alongside the existing system for 72 hours. Every incoming search query was duplicated and processed by both systems; only the existing system's results were returned to users. I compared the two systems' outputs — result sets, response times, and error rates — without any user impact. The shadow comparison found that 0.3% of queries produced different result sets. Investigation revealed the new system handled certain special character combinations differently. The discrepancy was fixed before any user exposure. Stage 2 — internal canary (internal users only): I routed all employees and internal test accounts — approximately 200 users — to the new search system for one week. Internal users conducted real work tasks while I monitored error rates, search latency, and zero-result rates (a proxy for search quality degradation). I also ran a structured observation session with five internal users, watching them perform their typical search tasks and noting any confusion or unexpected results. One user identified that the new relevance ranking was de-prioritising exact-match results in favour of semantically similar results — technically correct but contrary to user expectation. Stage 3 — 5% canary (real external users): I expanded to 5% of external users, using feature flag routing to ensure the same users consistently saw the new system (not randomised per-session). I monitored four quality signals: error rate (must stay below 0.1%), p95 search latency (must remain below 300ms), zero-result rate (must not increase by more than 1 percentage point), and search-to-click rate (a product metric indicating result quality). The 5% canary ran for 48 hours before expanding. Stage 4 — staged expansion to 100%: I expanded in three steps — 5% → 25% → 75% → 100% — with a 24-hour monitoring window at each step. Automated rollback was configured to trigger if error rate exceeded 0.5% for more than 10 minutes.

**Result:** The shadow mode comparison caught the special character bug before any user saw it. The internal canary caught the relevance ranking expectation mismatch — the ranking algorithm was tuned before external exposure. The 5% canary ran cleanly for 48 hours. The staged expansion completed without triggering rollback. Zero user-reported search quality issues in the 30 days post-release — compared to 47 support tickets in the 30 days after the previous major search change, which had been released without production validation.

## Key Terms

| Term | Definition |
|------|------------|
| **Dark launch** | Running new functionality in production without user-visible effect — processing real inputs and comparing outputs without serving the new results to users |
| **Shadow mode** | A dark launch pattern where every production request is duplicated and processed by both the old and new system simultaneously — enabling comparison without user impact |
| **Canary release** | Routing a small, defined subset of production users to a new version while the majority continue on the stable version |
| **Staged rollout** | The progressive expansion of a canary from a small percentage to full traffic — expanding only when quality signals meet defined thresholds |
| **Zero-result rate** | The proportion of search queries returning no results — an increase indicates search quality degradation |
| **Search-to-click rate** | The proportion of searches followed by a result click — a proxy metric for search result quality and relevance |
| **Rollback trigger** | A defined, measurable condition (error rate, latency, business metric) that initiates automatic reversion to the stable version |
| **Feature flag routing** | Using feature flags to consistently route the same users to the same version across sessions — maintaining a stable, comparable canary population |
