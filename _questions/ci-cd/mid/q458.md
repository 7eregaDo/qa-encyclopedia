## The Intent
The interviewer is checking whether you have thought about what the pipeline produces beyond a pass/fail signal. Artefact management — what to keep, for how long, where, and how to find it — is a practical engineering concern that directly affects incident response time, audit compliance, and developer experience when diagnosing failures. At mid level, they want to see concrete decisions about storage, retention, and report structure.

## The STAR Script
**Situation:** Our CI pipeline produced test results, screenshots on failure, code coverage reports, and Docker images — but none of them were managed deliberately. Test results were only visible in the GitHub Actions UI for 90 days, screenshots from failing tests were attached to the run but buried under 30 other artefact folders, Docker images were tagged only with `latest` which was overwritten on every build, and coverage reports were generated but not published anywhere accessible. When a production incident required finding the test results from a deployment 6 months earlier, nothing was retrievable.

**Task:** Design a coherent artefact management strategy that made failure diagnosis fast, audit evidence retrievable, and container images traceable.

**Action:** I redesigned artefact management across four categories. Test results and failure evidence: I published JUnit XML results to GitHub's native test reporting (providing inline PR feedback), and separately uploaded all artefacts to an S3 bucket with a path structure of `{year}/{month}/{service}/{branch}/{run-id}/`. Screenshots and video recordings from failing tests were named with the test name and failure timestamp — `checkout_flow_payment_step_FAILED_2024-03-15T14:23:11.png` — making them immediately identifiable without opening each file. Retention: test results were retained for 365 days; screenshots for 90 days; coverage reports for 365 days. Code coverage: I published HTML coverage reports to GitHub Pages for the main branch, and to a short-lived S3 presigned URL for PR branches — the URL was posted as a PR comment so reviewers could check coverage without running the pipeline locally. Container images: I introduced semantic versioning for images — every main branch build was tagged with the git SHA (`service:abc1234`), the semver tag if a release (`service:1.4.2`), and `latest`. PR builds were tagged with the branch name and SHA (`service:feature-payment-abc1234`) and retained for 14 days before automatic deletion. A `docker-compose.override.yml` in the repo used the SHA tag for local integration testing — ensuring developers were testing against a specific, known version. Traceability: I added a `build-info.json` to every Docker image containing the git SHA, branch, pipeline run ID, and build timestamp — accessible via `docker inspect`.

**Result:** The average time to find and open a failing test's screenshot dropped from 8 minutes (navigating the GitHub Actions UI) to under 90 seconds (direct S3 URL in the Slack failure notification). A compliance audit request for evidence of test execution on a specific deployment was fulfilled in 20 minutes from the S3 path. Three production incidents were traced to their source commit using the SHA tag on the deployed container.

| **Mid** | Designs artefact naming conventions, retention policies, and storage structure; publishes coverage reports accessibly; implements semantic image tagging with traceability metadata |

## Key Terms

| Term | Definition |
|------|------------|
| **Build artefact** | Any file produced by a CI pipeline run — compiled code, container images, test results, coverage reports, or failure evidence |
| **Retention policy** | A defined period for which artefacts are stored before automatic deletion — balancing storage cost against audit and investigation needs |
| **Semantic versioning (images)** | Tagging container images with meaningful identifiers — git SHA for traceability, semver for releases, branch name for PR builds |
| **JUnit XML** | A standard test result format consumed by CI platforms and test reporting tools to display pass/fail data inline on PRs |
| **S3 presigned URL** | A time-limited, authenticated URL for accessing a private S3 object — used to share coverage reports or artefacts without making the bucket public |
| **build-info.json** | A metadata file embedded in a container image recording its git SHA, pipeline run ID, and build timestamp — enabling deployed containers to be traced to their source |
| **Artefact path structure** | A hierarchical naming convention for stored artefacts enabling fast retrieval by service, date, branch, or run ID |
| **Coverage report** | An HTML or XML output showing which lines of code were executed during test runs — published as a pipeline artefact for developer and reviewer access |
