## The Intent
The interviewer is checking whether you treat feature flags as testable code — not just a deployment mechanism. Feature flags introduce branch points in the application that can each contain defects, and pipelines that only test the enabled or disabled state are leaving half the application's code paths unverified. At mid level, they want to see that you have designed test coverage for both flag states and integrated it into the CI pipeline.

## The STAR Script
**Situation:** My team used LaunchDarkly for feature flags, with approximately 15 active flags at any time controlling everything from experimental UI features to infrastructure-level behaviour changes. The pipeline ran tests only against the staging environment's current flag configuration — which meant tests only covered one flag state, and bugs in the disabled path were invisible until the flag was toggled. A production incident had occurred when a flag was disabled as a rollback measure, revealing a defect in the disabled code path that had been present for months but never tested.

**Task:** Design a CI/CD approach for feature flag testing that verified both enabled and disabled states for flags relevant to the current release, without requiring the full suite to run twice for every flag combination.

**Action:** I designed the testing approach across three levels of flag coverage. Level 1 — unit and API tests (both states, always): I configured the test suite to inject flag state via environment variables rather than reading from LaunchDarkly in CI — this gave deterministic, fast control of flag state without network dependency. For every flag that controlled a code path covered by unit or API tests, the test suite ran twice in parallel: once with the flag enabled (`LD_FLAGS_NEW_CHECKOUT=true`) and once with it disabled. I added a flag matrix to the GitHub Actions workflow that enumerated the active flags and ran the test job for each state combination. To prevent combinatorial explosion (15 flags × 2 states = 32,768 combinations), I scoped the matrix to only the flags changed in the current PR — typically one or two. Level 2 — E2E tests (relevant states, targeted): for each flag affecting a user journey, I tagged the relevant E2E tests with the flag name (`@flag-new-checkout`). The pipeline ran these tagged tests against two environments — one with the flag enabled and one with it disabled — using environment-specific LaunchDarkly configurations. Level 3 — flag hygiene checks: I added a pipeline step that audited the flag configuration — checking for flags that had been fully rolled out to 100% of users for more than 30 days (candidates for removal from the codebase) and flags that had no associated test tags (coverage gap). These were reported as warnings rather than failures.

**Result:** The dual-state testing approach caught a defect in the disabled code path within the first sprint — a null pointer exception in the disabled path of the new checkout flag that would have been triggered if the flag had been disabled as a rollback. The flag hygiene check identified six flags that were 100% rolled out and had been for over 30 days — their removal reduced codebase complexity and eliminated the testing overhead for those paths. The approach added an average of 4 minutes to PR pipeline time for PRs touching flagged code.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Runs tests against the current environment flag configuration; aware that flags control different code paths |
| **Mid** | Designs dual-state testing for both flag-enabled and flag-disabled paths; scopes the matrix to changed flags only to prevent combinatorial explosion; adds flag hygiene checks as pipeline steps |
| **Senior** | Designs the organisation-wide feature flag testing strategy — flag state management across environments, flag debt governance, integration with the feature flag platform's audit API, and long-lived flag detection |

## Key Terms

| Term | Definition |
|------|------------|
| **Feature flag** | A configuration mechanism that enables or disables application behaviour at runtime without a code deployment, used for progressive rollouts and rollback capability |
| **Flag state matrix** | A CI configuration running tests for multiple flag state combinations — typically enabled and disabled for each flag changed in the current PR |
| **Combinatorial explosion** | The exponential growth in test combinations when multiple flags are tested in all state permutations — controlled by scoping to changed flags only |
| **Dual-state testing** | The practice of running the same tests against both the flag-enabled and flag-disabled code paths, verifying correctness in both states |
| **Flag hygiene** | The practice of removing feature flags from the codebase after they have been fully rolled out or abandoned, reducing code complexity and test coverage overhead |
| **LaunchDarkly** | A widely used feature flag management platform providing flag evaluation, targeting rules, and audit logging |
| **Flag injection via environment variable** | Setting flag state through environment variables in CI rather than reading from the feature flag service, providing deterministic, network-independent flag control in tests |
| **Disabled code path** | The code executed when a feature flag is in its disabled (default) state — frequently under-tested because teams focus automation on the new enabled behaviour |
