## The Intent
The interviewer is checking whether you understand parallelisation as a CI engineering problem distinct from framework-level concurrency. At mid level, they want to see that you have split and distributed tests across runners in practice, know how to handle the isolation requirements, and have measured the result — not just enabled a configuration flag and hoped for the best.

## The STAR Script
**Situation:** Our Playwright E2E suite of 180 tests was running serially in the CI pipeline, taking 52 minutes. This had become the critical path bottleneck — PRs were queuing for pipeline capacity and developers were losing a full working hour waiting for results. Enabling Playwright's built-in workers locally made it run in 14 minutes on a developer laptop, but the CI runner was a single two-core machine that could not support the same concurrency.

**Task:** Implement parallelisation in the CI pipeline that achieved meaningful speed reduction within the available infrastructure budget — adding runners rather than upgrading the single runner.

**Action:** I implemented parallelisation using GitHub Actions matrix strategy across four dedicated runners. Step 1 — splitting strategy: I rejected simple file-count splitting (dividing 180 tests into four groups of 45 by alphabetical order) because historical timing data showed the tests varied from 8 seconds to 4 minutes each — equal file counts would produce unequal runner completion times. I implemented time-based splitting using a historical duration file committed to the repo. Each CI run updated this file with actual test durations, and the splitting script assigned tests to runners to minimise the longest-running runner's completion time — the "longest job" optimisation. Step 2 — runner configuration: I added four `ubuntu-latest` runners in the GitHub Actions matrix, each receiving a shard index and total shards. The Playwright config read `process.env.CI_SHARD_INDEX` and `process.env.CI_SHARD_TOTAL` to select its subset of tests. Step 3 — isolation requirements: because each runner had its own ephemeral environment (Docker Compose), the parallel execution was already isolated at the environment level. For any tests that wrote to shared external services (the email delivery mock, the Stripe test API), I added a per-runner prefix to all test-created entity names to prevent cross-runner collisions. Step 4 — result aggregation: each runner produced a JUnit XML report. After all four runners completed, a final aggregation job merged the four XML files into a single report and published it to the PR as a combined test summary.

**Result:** Total E2E pipeline duration dropped from 52 minutes to 16 minutes — a 69% reduction using four runners. The time-based splitting reduced runner variance to under 2 minutes between the fastest and slowest runner — far better than the 18-minute variance that alphabetical splitting would have produced. The combined JUnit report gave a single pass/fail view across all four runners without needing to inspect each runner's output individually.

## Key Terms

| Term | Definition |
|------|------------|
| **Matrix parallelisation** | A CI configuration pattern running the same job simultaneously across multiple parameter combinations — used to distribute tests across multiple runners |
| **Time-based splitting** | A test distribution strategy assigning tests to runners based on historical execution times to minimise the longest-running runner's completion time |
| **Shard** | A subset of the test suite assigned to a specific parallel runner for execution |
| **Runner variance** | The difference in completion time between the fastest and slowest parallel runner — high variance indicates uneven test distribution and wasted capacity |
| **Result aggregation** | The combination of test reports from multiple parallel runners into a single consolidated report for PR feedback |
| **Ephemeral runner** | A CI runner provisioned fresh for each pipeline run and discarded afterwards — providing natural isolation between parallel jobs |
| **Longest job optimisation** | A test splitting strategy minimising the time taken by the slowest runner — the effective duration of the parallel run |
