## The Intent
The interviewer is checking whether you approach flakiness as a pipeline engineering problem, not just a test authoring problem. At mid level, they want to see that you have designed the pipeline-level mechanisms — quarantine, tracking, alerts, and remediation workflow — that manage flakiness as an ongoing operational concern rather than something fixed once and forgotten.

## The STAR Script
**Situation:** Our CI pipeline had a 14% flakiness rate. The team's response was to add automatic retries — up to three attempts per failing test — which had hidden the problem in the pass rate while adding significant pipeline duration overhead (some runs took 35 extra minutes due to retries). Developer trust had degraded: when a test failed, the default assumption was "probably flaky, just re-run." Genuine defects were being dismissed at the same rate as flaky failures.

**Task:** Design a pipeline-level flakiness management system that made flakiness visible, isolated it from the quality signal, and created a time-bounded remediation workflow — without requiring every flaky test to be fixed before the system was operational.

**Action:** I built the flakiness management system in four components. Component 1 — detection infrastructure: I replaced the retry configuration with a flakiness detection job. When a test failed, instead of retrying immediately, the pipeline ran the failed test in isolation three times. If it passed at least once in those three runs, it was classified as flaky rather than a genuine failure — the classification was recorded in a flakiness database (a simple JSON file committed to the repo, updated by the CI job). If it failed all three times, it was classified as a genuine failure. Component 2 — quarantine workflow: tests classified as flaky three or more times within a 7-day window were automatically moved to the quarantine suite by the CI job — a separate pipeline step that ran after the main suite but did not gate the PR. The move was implemented by adding a `@flaky` tag to the test and committing the change via a bot account. Quarantined tests appeared in a weekly flakiness report but did not block PRs. Component 3 — remediation SLA: each quarantined test was assigned to the squad that owned the feature it covered. The SLA was 14 days — after 14 days a quarantined test still not fixed was escalated to the engineering manager's weekly review. The flakiness report included an "overdue" section showing tests past their SLA. Component 4 — graduation back to main suite: once a quarantined test had been fixed, the engineer removed the `@flaky` tag, and the detection job ran the test 10 times in isolation to verify consistency before allowing it back into the main suite.

**Result:** The main pipeline pass rate rose from 86% to 97% within two weeks of quarantine rollout — without fixing a single flaky test. Developer trust in pipeline failures as genuine signals recovered, measured by the time-to-investigate metric (from "ignored for a day" to "investigated within 2 hours"). The 14-day SLA with escalation resulted in 23 of 31 quarantined tests being fixed within the SLA window. Retries were removed entirely, reducing pipeline duration by an average of 22 minutes.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Re-runs flaky tests manually; adds retries to the pipeline when tests are inconsistent |
| **Mid** | Designs pipeline-level flakiness detection, quarantine workflow with SLA, remediation tracking, and graduation criteria — treating flakiness as an operational pipeline concern rather than an individual test problem |
| **Senior** | Builds automated flakiness scoring and quarantine as a pipeline infrastructure component; integrates flakiness data into the engineering health dashboard; defines organisation-wide flakiness SLAs |

## Key Terms

| Term | Definition |
|------|------------|
| **Quarantine suite** | A separate, non-blocking test suite for tests classified as flaky — maintaining visibility without polluting the primary pipeline quality signal |
| **Flakiness detection job** | A CI job that re-runs a failed test in isolation to distinguish genuine failures from inconsistent tests |
| **Remediation SLA** | A defined time limit within which a quarantined flaky test must be fixed before it is escalated to management review |
| **Graduation criteria** | The conditions a fixed test must meet before being returned to the main suite — typically passing consistently in isolation for a defined number of runs |
| **Pipeline quality signal** | The reliability of the pipeline pass/fail status as an indicator of genuine code quality — degraded by flaky tests that create false failures |
| **Bot commit** | An automated git commit made by a CI job — used to update quarantine tags without requiring manual developer intervention |
| **Retry overhead** | The additional pipeline duration caused by automatic test retries — a hidden cost of masking flakiness rather than addressing it |
