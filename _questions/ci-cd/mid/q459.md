## The Intent
The interviewer is checking whether you treat environment promotion as a deliberate quality engineering concern, not just a deployment automation concern. The key distinction is that promotion gates are quality decisions — not just "did it deploy successfully" but "has it satisfied the defined quality criteria for this stage." At mid level, they want to see specific gate criteria, enforcement mechanisms, and what happens when a promotion is rejected.

## The STAR Script
**Situation:** My team had four environments: development, test, staging, and production. The progression between them was informal — developers merged to main, which triggered a deployment to test, and then someone would manually deploy to staging and eventually production. There were no defined quality criteria for each promotion. As a result, staging frequently received builds that had not completed test-environment validation, and production occasionally received builds that had passed test but had known open defects.

**Task:** Design a formal environment promotion strategy with explicit, automated quality gates between each stage.

**Action:** I designed the promotion strategy around a promote-on-evidence model — each environment would only receive a build if the preceding environment's quality evidence had been recorded and met defined criteria. Development → Test promotion (triggered automatically on merge to main): gate criteria — all unit and API tests pass; no new critical SAST findings; no new critical dependency CVEs. Evidence recorded: test result JSON with run ID, timestamp, and pass count. Test → Staging promotion (triggered manually with automation enforcing criteria): gate criteria — integration test suite passes in the test environment; contract tests pass for all registered consumers; the build has been in the test environment for a minimum of 2 hours without a critical alert from synthetic monitoring. Evidence recorded: integration test results, contract verification results, monitoring alert log for the environment. Staging → Production promotion (triggered manually with automation enforcing criteria): gate criteria — E2E smoke suite passes against staging; no open Sev-1 or Sev-2 defects tagged to the release; QE sign-off recorded in the release management system; staging has been stable for 4 hours post-deployment. Evidence recorded: E2E results, defect query output, QE approval record, monitoring stability log. Implementation: I implemented promotion as a GitHub Actions workflow with an `environment` scope — each environment was defined in GitHub with required reviewers and protection rules. The promotion job fetched the evidence file from S3 and validated it programmatically before proceeding. If any criterion was not met, the job failed with a specific message identifying which criterion was violated and what evidence was missing.

**Result:** The structured promotion process caught three builds in the first month that would previously have reached staging with unresolved issues — a failed contract test on a provider service, an open Sev-1 defect that had been opened but not associated with the release, and a build where the test environment had had a monitoring alert within its stability window. All three were resolved before promotion. Production incidents attributed to quality gaps in the release process dropped by 60% in the two quarters following implementation.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Understands that environments serve different purposes; follows an existing promotion process |
| **Mid** | Designs a promote-on-evidence model with explicit gate criteria per boundary; implements automated criterion enforcement; defines what evidence is recorded at each stage and what happens when promotion is rejected |
| **Senior** | Designs the full environment strategy including ephemeral environments, environment templating, drift detection, and a risk-tiered promotion model that adapts gate criteria to the release's risk profile |

## Key Terms

| Term | Definition |
|------|------------|
| **Environment promotion** | The process of advancing a specific build artefact from one environment to the next — development, test, staging, production |
| **Promote-on-evidence** | A promotion model requiring recorded, structured evidence that quality criteria have been met before an artefact advances to the next environment |
| **Promotion gate** | The automated check that validates promotion evidence before allowing a build to advance — distinct from deployment automation |
| **Release stability window** | A defined minimum period during which an environment must run without critical alerts before a build is eligible for promotion |
| **Environment protection rule** | A CI/CD platform configuration requiring named approvers and passing automated checks before a deployment to a protected environment proceeds |
| **Sev-1 / Sev-2 defect gate** | A promotion criterion blocking advancement if any open defects of the specified severity are associated with the current release |
| **Evidence file** | A structured record of quality check outcomes — test results, alert logs, approval records — stored per build and validated by the promotion job |
| **QE sign-off** | An explicit approval recorded by a QA engineer in the release management system, confirming that the quality criteria have been reviewed and met |
