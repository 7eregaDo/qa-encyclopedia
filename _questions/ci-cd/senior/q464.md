## The Intent
The interviewer is checking whether you can solve the compliance-velocity tension that many regulated organisations struggle with. At senior level, they want to see that you have designed compliance as an engineering property of the pipeline rather than an external audit activity — and that you have worked across the law-engineering boundary to make this happen without turning every deployment into a bureaucratic event.

## The STAR Script
**Situation:** My organisation was a financial services company subject to FCA oversight and SOC 2 Type II audit. The existing compliance process required manually collecting evidence for each production deployment: a screenshot of the test results, a copy of the security scan report, an email from the QE lead confirming sign-off, and a change management ticket. This took 45–90 minutes per deployment and had become the primary bottleneck limiting deployment frequency. The compliance team and the engineering team had an adversarial relationship because compliance requirements were seen as incompatible with continuous delivery.

**Task:** Redesign the compliance evidence process to be generated automatically by the pipeline, satisfying the auditor's requirements without requiring manual evidence collection.

**Action:** I worked with the compliance manager and the external SOC 2 auditor to understand exactly what evidence was required for each control — not what the team had been collecting, but what the auditor actually needed. This produced a list of six evidence requirements: proof that automated tests ran and passed, proof that security scanning ran and found no critical findings, proof that the code had been reviewed by at least one other engineer, proof of who approved the deployment, a record of what was deployed and when, and evidence that the deployment was tested in a non-production environment first. I then implemented automated evidence generation for each. Automated test evidence: the pipeline published JUnit XML results and a summary JSON to an immutable S3 bucket with versioning enabled — the S3 object metadata (timestamp, uploader identity, pipeline run ID) provided the tamper-evident audit trail the auditor required. Security scan evidence: the Semgrep and Trivy scan reports were stored in the same S3 structure alongside the test results. Peer review evidence: GitHub's required reviewers feature — requiring at least one approved review before merge — was directly accepted by the auditor as sufficient evidence of the code review control. Deployment approval evidence: GitHub Actions environment protection rules required a named QE approver before production deployment; the pipeline log recorded the approver's identity and timestamp. Deployment record: I generated a `deployment-manifest.json` at deployment time containing the service name, version, git SHA, pipeline run ID, deployer identity, and timestamp — stored in S3 and in the service's deployment history table. Staging evidence: the staging deployment step produced a staging-test-results artefact proving the code had been validated in a non-production environment.

**Result:** Manual compliance evidence collection was eliminated. The SOC 2 auditor reviewed the automated evidence collection design and accepted it as fully satisfying all six controls. Deployment frequency increased from 3 deployments per week to 12 — the compliance bottleneck was gone. The compliance manager reported that the audit evidence was more complete and reliable than the manual collection process had produced, because the automated evidence could not be forgotten or substituted with an incorrect version.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Provides test results to the compliance team when asked; understands that regulated environments require evidence of testing |
| **Mid** | Stores test results and scan reports as pipeline artefacts; understands which compliance controls require what evidence |
| **Senior** | Designs automated compliance evidence generation across all pipeline controls; works with auditors to confirm evidence acceptability; eliminates manual compliance collection as a bottleneck; presents the design to the CISO and compliance manager |

## Key Terms

| Term | Definition |
|------|------------|
| **Compliance gate** | An automated pipeline step that generates, stores, and verifies compliance evidence — replacing a manual collection step |
| **Tamper-evident storage** | An artefact store configured to prevent modification of previously written records — S3 with versioning and object lock, or an immutable audit log — satisfying regulatory evidence integrity requirements |
| **Deployment manifest** | A structured record generated at deployment time capturing the deployed version, approver, timestamp, and pipeline run ID — the primary deployment audit trail |
| **SOC 2 Type II** | A compliance framework assessing the continuous operation of security controls over a 12-month period — requiring timestamped evidence of control operation, not just design |
| **Control mapping** | The process of identifying which pipeline steps and artefacts satisfy which specific regulatory control requirements — the foundation of automated compliance evidence design |
| **Immutable artefact** | A pipeline output that cannot be modified after creation, providing the integrity guarantee required for regulatory audit evidence |
| **Evidence acceptability** | The formal confirmation from an auditor that a specific automated evidence collection mechanism satisfies the corresponding compliance control — obtained before building the system, not after |
| **Compliance velocity** | The rate at which compliance activities can be completed without impeding delivery — maximised when compliance is embedded in the pipeline rather than performed as a separate manual activity |
