## The Intent
The interviewer is checking whether you treat blue/green deployments as a system of quality concerns requiring systematic testing — not just a deployment mechanism that is assumed to work. At senior level, they want to see a comprehensive strategy covering pre-cutover validation, switchover mechanics, in-flight request handling, and rollback — with evidence that you have verified these properties rather than assumed them.

## The STAR Script
**Situation:** My organisation was migrating from rolling deployments to blue/green deployments for six critical services. The platform team had built the infrastructure — AWS ALB target group switching — but there was no testing strategy for the blue/green pattern itself. The first production blue/green deployment had caused a 3-minute outage because the green environment had not been validated before cutover, and session tokens from the blue environment were not recognised by the green application.

**Task:** Design a comprehensive testing strategy for the blue/green deployment pattern, covering pre-cutover validation, switchover mechanics, session continuity, and rollback.

**Action:** I designed the strategy across four test dimensions. Dimension 1 — green environment pre-validation: before any traffic switched, I ran a parallel validation suite against the green environment — routing a synthetic test user's traffic directly to green via a test header while all real users remained on blue. The validation suite covered: all critical user journeys (smoke suite), database connectivity and migration state (the green environment ran against the production database, so schema correctness was essential), third-party integration health (payment processor, email, auth provider), and a 10-minute synthetic load test at 50% of baseline traffic to verify the green environment handled production-level load before receiving it. Any failure in the validation suite blocked the cutover. Dimension 2 — switchover mechanics testing: I wrote a switchover verification test that ran during the ALB target group switch. It sent requests to the ALB every 500ms for 60 seconds spanning the cutover and asserted: no request received a 5xx response (zero-downtime verification), no response took longer than 3× the baseline p95 (latency spike detection), and response headers confirmed traffic was reaching the green environment within 10 seconds of switchover initiation. Dimension 3 — session continuity: the original incident stemmed from session tokens. I designed a session continuity test: authenticate a test user against blue, capture the session token, initiate the switchover, then immediately use the captured token against green and verify it was accepted. This required the session store (Redis) to be shared between environments — which I verified was the case and documented as a requirement. Dimension 4 — rollback testing: before every production blue/green deployment, I ran a rollback drill in staging: deploy green, switch traffic, then immediately switch back to blue, verifying that 100% of traffic returned to blue within 30 seconds and no requests were dropped during the re-switch.

**Result:** The pre-validation suite caught two issues before production cutover: a missing environment variable in the green environment that would have broken a third-party integration, and a database migration that had run on green but left the schema in a state incompatible with an active feature flag. Both were resolved before cutover. The session continuity test is now a standard pre-cutover gate — the original production incident has not recurred.

## Key Terms

| Term | Definition |
|------|------------|
| **Blue/green deployment** | A deployment strategy maintaining two identical production environments — blue (current) and green (new) — with instantaneous traffic switchover via a load balancer |
| **ALB target group** | An AWS Application Load Balancer configuration grouping the instances that receive traffic — switching between blue and green target groups achieves zero-downtime cutover |
| **Pre-cutover validation** | A test suite run against the green environment before any production traffic is routed to it, verifying functional and performance correctness under production conditions |
| **Session continuity** | The property that authenticated sessions from the blue environment remain valid in the green environment — requiring a shared session store between environments |
| **Switchover mechanics** | The specific behaviour of the traffic routing system during cutover — response time, error rate, and traffic distribution during the transition window |
| **Zero-downtime verification** | The confirmation that no user-visible errors occurred during the traffic switchover — measured by monitoring requests spanning the cutover window |
| **Rollback drill** | A planned, non-emergency execution of the green-to-blue rollback in staging, verifying that the rollback completes within the SLA and produces no dropped requests |
| **Parallel validation** | Running tests against the green environment while production traffic continues on blue — using test-specific routing headers to direct synthetic traffic without affecting real users |
