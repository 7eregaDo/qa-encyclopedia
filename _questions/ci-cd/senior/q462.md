## The Intent
The interviewer is checking whether you understand database migrations as one of the highest-risk parts of continuous delivery — and whether you have designed the patterns and tests that make them safe. At senior level, they want to see the expand/contract migration pattern, the CI pipeline enforcement that prevents unsafe migrations from being merged, and evidence that you have tested the overlap window specifically.

## The STAR Script
**Situation:** My organisation operated 14 microservices with PostgreSQL databases, deploying continuously. Two production incidents in a quarter had been caused by database migrations: one where a column rename broke the currently-running application version during a rolling deployment, and one where a `NOT NULL` constraint was added to a column before the application was updated to populate it. The engineering team had no shared understanding of what constituted a safe migration.

**Task:** Design a zero-downtime migration framework — patterns, tooling, and CI verification — that made safe migrations the easy path and blocked unsafe ones automatically.

**Action:** I designed the framework around the expand/contract pattern and a migration safety CI check. Expand/contract pattern: I documented the three-release pattern as the company standard for all destructive schema changes. Release N (expand): add new column/table as optional and nullable alongside the old structure. Release N (application): update the application to read from and write to both old and new structures simultaneously. Release N+1 (contract): remove the old column/table once all instances run the new application code. I provided worked examples for the five most common migration scenarios: column rename, column type change, table split, nullable-to-not-null, and index addition on a large table. Migration safety CI check: I wrote a migration analyser that ran on every PR containing a migration file. The analyser parsed the migration SQL and classified each statement as safe (adding nullable column, adding index concurrently, creating new table) or unsafe (renaming column, dropping column, adding NOT NULL constraint, non-concurrent index on existing table). Unsafe statements failed the pipeline with a specific message explaining why the statement was unsafe and referencing the expand/contract documentation for the correct multi-release approach. Overlap window testing: for each migration, I wrote a compatibility test that ran the migration against a test database and then ran the previous application version against the migrated schema — verifying that the application continued to function correctly after the migration, specifically in the overlap window where old and new application code would coexist. Timing tests: for migrations touching tables with more than 100,000 rows in production, I ran the migration against a staging clone and measured execution time — any migration taking longer than 5 seconds generated a warning recommending a concurrent or batched approach.

**Result:** The migration analyser caught four unsafe migrations in the first month — all column rename or NOT NULL attempts that would have caused incidents. Two of these were from engineers who had not read the migration guide; the CI message's link to the documentation made self-service resolution straightforward. The overlap window test caught one migration that had been correctly classified as safe but still broke the previous application version due to a foreign key constraint timing issue. Zero database-related production incidents occurred in the 9 months following the framework rollout.

## Key Terms

| Term | Definition |
|------|------------|
| **Expand/contract pattern** | A three-release migration strategy: add new structure alongside old (expand), update application to use both, then remove old structure (contract) — ensuring no release breaks the running application |
| **Overlap window** | The period during a rolling or blue/green deployment where old and new application versions coexist and must both function against the same database schema |
| **Migration safety analyser** | A CI tool that parses migration SQL and classifies statements as safe or unsafe for zero-downtime deployment, blocking unsafe migrations before merge |
| **Concurrent index creation** | PostgreSQL's `CREATE INDEX CONCURRENTLY` syntax that builds an index without locking the table — required for adding indexes to large tables without downtime |
| **NOT NULL constraint** | A database constraint preventing null values in a column — unsafe to add to an existing column without a default value while the current application version does not populate the column |
| **Backwards-compatible migration** | A schema change that the currently-running application version can operate against correctly — a prerequisite for zero-downtime deployment |
| **Overlap window test** | A CI test that runs the previous application version against the migrated schema to verify backwards compatibility during the deployment transition period |
| **Destructive migration** | A schema change that removes or modifies existing structures (column drop, rename, type change) — must be deferred to a subsequent release in the expand/contract pattern |
