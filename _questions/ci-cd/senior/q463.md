## The Intent
The interviewer is checking whether you can redesign a quality approach for a delivery model that eliminates the traditional QA-at-the-end pattern. Trunk-based development with continuous integration means code is always in a potentially releasable state — which requires quality to be embedded in every commit, not verified at the end of a branch. At senior level, they want to see how you have restructured the quality programme to work with this constraint.

## The STAR Script
**Situation:** My organisation was transitioning from a gitflow model (two-week feature branches with a QA phase at the end) to trunk-based development with branches living no longer than one day. The QA team had been running a structured testing phase at the end of each sprint. That phase would no longer exist — all validation had to happen in CI, on every commit.

**Task:** Redesign the quality strategy to work within the trunk-based constraint — maintaining the same defect detection rate while eliminating the end-of-sprint testing phase.

**Action:** I restructured quality across four dimensions. Pre-merge quality bar: I raised the automated quality requirements for every PR significantly. The pre-merge pipeline had to complete in under 12 minutes and include: all unit tests, all API tests, all contract tests, security SAST, and a curated 25-test E2E smoke suite covering the highest-risk journeys. Anything not in this set moved to the scheduled nightly run. Test suite architecture: the 12-minute constraint required architectural discipline. I worked with the team to identify and remove the 40 slowest tests from the pre-merge suite (moving them to nightly), eliminating redundant E2E coverage that duplicated API test assertions, and parallelising remaining tests across four runners. The result was a pre-merge suite with higher genuine confidence than the old manual phase, delivered in under 12 minutes. Feature flag discipline: all incomplete features shipped behind flags. I implemented the flag testing contract — every flag had both states tested before the flag shipped — and added a CI lint step that enforced a maximum branch age of 24 hours (warning at 12, failing at 24). This reinforced the cultural norm that branches were short-lived. Exploratory testing as a continuous practice: the sprint-end QA phase had also included exploratory testing, which automation could not replace. I replaced it with a weekly 90-minute exploratory session covering the week's releases — scheduled, time-boxed, and structured around a specific charter derived from the week's feature changes. Findings went directly to the backlog rather than blocking release.

**Result:** The defect escape rate to production was 18% lower in the six months after the transition than in the six months before — despite removing the manual QA phase. The pre-merge pipeline's breadth meant defects were caught earlier and more specifically. The weekly exploratory sessions surfaced two significant usability issues in the first month that automated tests had not caught — confirming that structured exploratory testing remained valuable even without a dedicated testing phase.

## Key Terms

| Term | Definition |
|------|------------|
| **Trunk-based development** | A branching strategy where all developers commit to a single shared branch continuously, with branches living for hours or at most one day |
| **Pre-merge quality bar** | The mandatory automated checks that must pass before any code is merged to trunk — the primary quality gate in trunk-based development |
| **Pipeline time-boxing** | A hard constraint on pre-merge pipeline duration that forces test suite architecture to prioritise speed and genuine confidence over coverage breadth |
| **Feature flag discipline** | The organisational practice of deploying all incomplete features behind flags — decoupling code deployment from feature activation in a trunk-based context |
| **Branch age lint** | A CI check that warns or fails when a branch has lived beyond a defined maximum age — enforcing the cultural norm of short-lived branches |
| **Continuous exploratory testing** | A scheduled, structured exploratory testing practice that replaces the sprint-end QA phase — providing the human quality perspective that automation cannot deliver |
| **Exploratory charter** | A brief statement defining the focus, tools, and intent of an exploratory testing session — derived from the week's feature changes in a trunk-based context |
| **Defect escape rate** | The proportion of defects reaching production — the primary metric for evaluating quality strategy effectiveness across deployment model transitions |
