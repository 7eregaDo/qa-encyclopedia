## The Intent
The interviewer is checking whether you treat defects as individual events to fix or as signals about systemic process gaps to address. At mid level, they want to see that you can trace a defect beyond its immediate cause ("the developer made a mistake") to its process cause ("we had no review step for this type of change") and translate that into a concrete improvement.

## The STAR Script
**Situation:** In a two-month period, my team shipped four defects to production that all had a similar pattern — they involved edge cases in data validation logic that had test cases in the suite, but the test cases were not being executed because they were tagged as regression-only and the regression suite was being skipped for hotfix deployments. The same class of defect was escaping through the same gap repeatedly.

**Task:** I was asked to lead a root cause analysis after the fourth production incident, with the goal of identifying why this pattern kept recurring and recommending systemic fixes rather than just fixing each defect individually.

**Action:** I ran a structured root cause analysis using the five-whys technique applied to all four defects collectively. Why did defects reach production? → The regression suite was not executed before hotfix deployments. Why was the regression suite not executed? → The team had an informal rule that hotfixes only needed a sanity check, not full regression. Why did this informal rule exist? → Full regression took 3 hours, which felt disproportionate for a hotfix. Why was the regression suite 3 hours long? → It had never been partitioned into a fast critical-path subset and a full suite. Why had no fast subset been defined? → Nobody had ever formally categorised tests by criticality for deployment type. I documented the root cause as: an undocumented deployment policy (sanity check for hotfix) interacting with an unpartitioned regression suite (no critical-path subset) created a gap where data validation edge cases were routinely deferred for hotfix deployments. The four individual defects were all symptoms of this one systemic gap. I proposed two fixes: create a 30-minute critical-path regression subset that always ran for any deployment (including hotfixes), and document the deployment testing policy formally so the informal rule was replaced by an explicit, reviewed policy. I presented the analysis and recommendations to the team in a 20-minute retrospective session, framing it as a process finding rather than a blame finding.

**Result:** The critical-path subset was created within one sprint — 28 test cases, 28-minute execution time. The deployment testing policy was documented and reviewed by the engineering lead. In the following six months, zero production defects were traceable to the same gap. The RCA framework — five-whys applied to defect populations rather than individual defects — was adopted as the team's standard approach for any recurring defect pattern.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Can identify the immediate cause of a defect and describe what the fix was |
| **Mid** | Applies five-whys to trace a defect to its process root cause, classifies the cause category, and translates findings into specific process improvements that prevent recurrence |
| **Senior** | Runs RCA at programme level — analysing defect populations across multiple releases, classifying systemic causes, presenting findings to engineering leadership, and designing the process changes that address the most impactful cause categories |

## Key Terms

| Term | Definition |
|------|------------|
| **Root cause analysis (RCA)** | A structured investigation technique that identifies the underlying process cause of a defect or failure, rather than stopping at the immediate symptom |
| **Five-whys** | An RCA technique that repeatedly asks "why?" (typically five times) to trace a problem from its symptom to its root cause |
| **Immediate cause** | The proximate reason a defect occurred — for example, "a validation rule was not implemented" |
| **Process cause** | The systemic reason the immediate cause was possible — for example, "there was no review step that would have caught the missing validation rule" |
| **Defect population analysis** | The examination of multiple defects collectively to identify shared patterns and common root causes |
| **Blameless RCA** | A root cause analysis conducted without attributing fault to individuals — focusing on process gaps rather than personal error |
| **Recurrence prevention** | The goal of root cause analysis — implementing changes that make the same class of defect unlikely or impossible in future |
