## The Intent
The interviewer is checking whether you understand independence as a quality principle rather than just a process rule. At mid level, they want to see that you have applied independence deliberately — not just as organisational policy but as a deliberate technique for catching what individual testers miss — and that you have run peer reviews of test work that improved quality.

## The STAR Script
**Situation:** Our team had a pattern of shipping releases with defects that, in retrospect, were obvious — edge cases that the test cases simply had not considered, or expected results that were subtly wrong because the test author had the same misunderstanding as the developer. The same blind spots appeared repeatedly.

**Task:** I proposed introducing structured peer review of test cases as a lightweight practice to catch these gaps before execution — not as a heavyweight approval process but as a focused, collaborative quality check.

**Action:** I introduced a peer review rotation: for any test suite covering a story rated medium or high risk, a second QA engineer reviewed the test cases before execution began. I defined what the review should look for to make it productive rather than a rubber stamp. The reviewer checked four specific things. Coverage completeness: were all acceptance criteria covered? Were negative cases present for each positive case? Were boundary values included for any numeric or date inputs? Assertion accuracy: were the expected results specific and assertable, or vague ("the system behaves correctly")? Did any expected result reflect an assumption the reviewer questioned? Independence from implementation: had the test author assumed the same implementation path as the developer? Were there alternative valid paths through the feature that the tests did not exercise? Test data realism: did the test data reflect realistic user behaviour, or only idealised inputs? I also introduced the practice of developers reviewing their own stories' test cases — not to approve them, but to flag any test that was testing something not in the acceptance criteria (scope creep) or that had a factually incorrect expected result. I made explicit that this was not the developer approving the tests — it was a factual accuracy check on expected results, where the developer had information the tester might not.

**Result:** In the first two sprints after introducing peer review, reviewers caught 14 issues across 8 test suites: 6 missing negative test cases, 4 vague expected results that were rewritten to be specific, 2 boundary values not included, and 2 tests with incorrect expected results. All 14 would have either produced false positives or missed genuine defects in execution. The developer review of expected results caught 3 cases where the tester had misunderstood a business rule — the expected result was wrong — which would have caused a genuine defect to be marked as a false positive.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Understands that it is harder to find your own mistakes; participates in peer reviews when asked |
| **Mid** | Designs and runs a structured peer review rotation with defined review criteria; measures the defects caught through review; introduces developer review of expected results for accuracy |
| **Senior** | Builds test quality review into the team's definition of done; designs multi-level independence (QE peer review, developer factual check, stakeholder review for complex scenarios); measures the impact of review on escape rate and false positive rate |

## Key Terms

| Term | Definition |
|------|------------|
| **Test independence** | The separation of test authorship from the code being tested — reduces confirmation bias and blind spots in defect detection |
| **Peer review (test cases)** | A structured review of test cases by a second engineer to catch missing coverage, weak assertions, and incorrect expected results |
| **Confirmation bias** | The tendency to test what you expect to work rather than what might fail — mitigated by test independence |
| **Assertable expected result** | A specific, unambiguous outcome that can be definitively marked pass or fail — "The error message 'Password must be at least 8 characters' appears below the password field" |
| **False positive** | A test that passes when it should fail — often caused by an incorrect expected result where the test is verifying incorrect behaviour as if it were correct |
| **Coverage completeness** | The property that a test suite covers all acceptance criteria including negative cases, boundary values, and alternative paths |
| **Developer factual review** | A developer's review of test expected results for factual accuracy — not approval of the test approach, but verification that the expected behaviour is correctly described |
