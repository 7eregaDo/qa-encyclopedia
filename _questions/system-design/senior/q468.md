## The Intent
The interviewer is checking whether you treat chaos engineering as a structured discipline rather than random disruption. At senior level, they want to see hypothesis-driven experiments with defined blast radius, a finding-to-improvement pipeline, and a programme that builds organisational confidence over time — not one-off GameDay events that produce a list of unfixed problems.

## The STAR Script
**Situation:** My organisation had 18 microservices that had never been subjected to controlled failure testing beyond standard unit and integration tests. The system had been designed with resilience patterns — retries, circuit breakers, timeouts, fallbacks — but nobody could confirm these patterns worked correctly under real failure conditions. A major customer had asked for a resilience attestation as part of enterprise procurement due diligence.

**Task:** Design and implement a chaos engineering programme that would systematically validate the system's resilience properties, produce findings that drove genuine improvements, and generate evidence suitable for the customer's due diligence request.

**Action:** I structured the programme in four phases. Phase 1 — steady state definition: before running any experiments, I defined the steady state for each critical service — the specific observable metrics (error rate below 0.5%, p95 latency below 300ms, synthetic monitor passing) that constituted normal healthy operation. These were measured for two weeks before any experiment began. Without a defined steady state, there was no way to determine whether an experiment had caused degradation. Phase 2 — experiment design and prioritisation: I identified six experiment categories based on the system's actual failure modes from incident history: network latency injection, service unavailability, resource exhaustion (CPU and memory), data store unavailability, message queue unavailability, and clock skew. I prioritised experiments by risk score — combinations of failure likelihood and potential business impact. Each experiment had a written hypothesis: "When service A experiences 2-second latency in its calls to service B, we believe the circuit breaker will open within 10 seconds and service A will return a degraded but successful response to its callers, maintaining steady state." Phase 3 — controlled execution: I used Chaos Toolkit for experiment orchestration and Pumba for container-level fault injection. I ran all experiments initially in staging, then selected low-blast-radius experiments for production during low-traffic windows. Every experiment had a defined abort condition — if steady state was breached beyond the hypothesised impact, the experiment was halted and the abort procedure executed. Phase 4 — finding-to-improvement pipeline: every experiment produced one of three outcomes. Hypothesis confirmed (system behaved as designed), hypothesis disconfirmed — minor finding (system deviated slightly, a configuration improvement was needed), or hypothesis disconfirmed — significant finding (the resilience pattern did not work, a design fix was required). Significant findings were tracked as P1 engineering tasks with a 30-day remediation SLA. I produced a quarterly resilience report showing experiments run, hypotheses confirmed vs disconfirmed, and improvements implemented.

**Result:** 23 experiments were run in the first two quarters. 14 confirmed the hypothesis. 9 disconfirmed it — producing 4 minor configuration fixes and 5 significant design improvements. The most impactful finding: the payment service circuit breaker was configured in a half-open state that never fully opened — a configuration error that meant it provided no protection under sustained failures. The fix was implemented before the customer due diligence visit. The quarterly resilience report was accepted by the customer's security team as sufficient evidence of resilience testing maturity.

## Key Terms

| Term | Definition |
|------|------------|
| **Steady state** | The observable normal operating condition of a system — defined in terms of specific metrics — used as the baseline against which chaos experiment impact is measured |
| **Chaos hypothesis** | A specific, testable prediction about system behaviour under a defined failure condition — the core scientific unit of chaos engineering |
| **Blast radius** | The scope of potential impact if a chaos experiment produces unexpected results — controlled by limiting the experiment to a specific service, namespace, or traffic percentage |
| **Abort condition** | A defined metric threshold that, if breached during an experiment, triggers immediate halting and rollback of the fault injection |
| **Chaos Toolkit** | An open-source chaos engineering framework for defining and executing experiments with declarative experiment specifications |
| **Pumba** | A chaos engineering tool for Docker and Kubernetes containers providing network emulation (latency, packet loss) and container disruption (kill, pause, stress) |
| **GameDay** | A structured chaos engineering event where teams collectively run experiments and observe system behaviour — typically a one-time exercise rather than a continuous programme |
| **Resilience attestation** | Documentation of a chaos engineering programme's scope, methodology, and findings, provided as evidence of resilience testing maturity to customers or auditors |
