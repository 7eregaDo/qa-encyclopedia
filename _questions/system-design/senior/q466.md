## The Intent
The interviewer is checking whether you understand the service mesh as a testable infrastructure layer with its own failure modes, distinct from the application code running within it. At senior level, they want to see that you test mesh policies explicitly — not just assume they work — and that you verify distributed tracing as a quality property of the system, not just an operational concern.

## The STAR Script
**Situation:** My organisation operated a 14-service platform on Kubernetes with Istio as the service mesh. The mesh had been configured with retry policies, circuit breakers, and mTLS enforcement across all service pairs. However, nobody had tested whether these policies actually behaved as configured — they were specified in YAML but had never been verified to activate under the conditions they were meant to address. A production incident where a downstream service degraded had revealed that the circuit breaker had never triggered, allowing the upstream service to continue queuing requests until it exhausted its thread pool.

**Task:** Design a testing strategy for the service mesh policies and for distributed tracing correctness across the platform.

**Action:** I designed the strategy across three areas. Area 1 — traffic management policy testing: I wrote a set of policy verification tests using a fault injection approach. For each configured retry policy, I deployed a fault injection VirtualService that introduced HTTP 503 responses for a specified percentage of requests, then verified that the calling service retried the configured number of times before returning an error to its caller — confirmed via the Envoy access logs in the test environment. For circuit breaker testing, I generated sustained errors exceeding the configured threshold (50% error rate for 10 consecutive requests) and asserted that the circuit breaker opened — visible as 503 responses with the `x-envoy-overloaded` header — and that it recovered correctly after the cooldown window. For timeout policies, I introduced artificial latency via fault injection and verified that requests exceeding the configured timeout were terminated with 504 rather than waiting indefinitely. Area 2 — mTLS verification: I wrote tests confirming that service-to-service calls without a valid certificate were rejected — I attempted calls using a pod with a manually injected invalid certificate and verified the mesh denied them. I also verified that `PeerAuthentication` policies in STRICT mode rejected plain-text connections, using a test pod with Istio injection disabled to simulate a non-mesh workload attempting to call a mesh-protected service. Area 3 — distributed tracing correctness: I wrote a tracing completeness test — a scripted user journey through four services, with the test asserting that the resulting Jaeger trace contained spans from all four services, that each span included the mandatory custom attributes our standard required (user ID, correlation ID, service version), and that no orphaned spans existed (spans without a parent that should have one). I ran this test against the staging environment after every deployment to catch any service that had been updated without trace context propagation.

**Result:** The circuit breaker test confirmed the production incident's root cause — the circuit breaker had been configured with a threshold that was never reachable given the service's request rate. The configuration was corrected. The tracing completeness test caught three services over the following two months that had been updated with a dependency upgrade that removed the OpenTelemetry instrumentation — all three were caught before they reached production.

## Key Terms

| Term | Definition |
|------|------------|
| **Service mesh** | An infrastructure layer (e.g. Istio, Linkerd) that manages service-to-service communication, providing traffic management, mTLS, and observability without application code changes |
| **Fault injection (mesh)** | An Istio feature that deliberately introduces HTTP errors or latency into traffic at the mesh layer, enabling resilience policy testing without modifying service code |
| **VirtualService** | An Istio resource defining traffic routing rules and fault injection configurations for a specific service |
| **Circuit breaker (mesh)** | An Envoy-level policy that stops forwarding requests to a service that has exceeded defined error thresholds — distinct from application-level circuit breakers |
| **mTLS (mutual TLS)** | A security configuration requiring both parties in a service-to-service connection to present valid certificates — enforced by the mesh without application code changes |
| **PeerAuthentication** | An Istio policy defining the mTLS mode (STRICT, PERMISSIVE, DISABLE) for service-to-service communication within a namespace or across the mesh |
| **Tracing completeness** | The property that a distributed trace contains spans from every service in the request path — verifying that trace context was correctly propagated across all service boundaries |
| **Orphaned span** | A trace span without a parent span when one is expected — indicating that trace context was not propagated correctly between two services |
