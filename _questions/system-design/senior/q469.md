## The Intent
The interviewer is checking whether you understand that CQRS introduces a structural split in the system that requires a structural split in the testing approach. At senior level, they want to see that you test the projection mechanism, the consistency boundary between write and read models, and the read model's accuracy under both normal and lagged conditions — not just that commands execute and queries return data.

## The STAR Script
**Situation:** My team was building an order management system using CQRS — commands wrote to a PostgreSQL event store, event handlers projected events into read-optimised MongoDB collections, and queries read exclusively from MongoDB. The initial test suite treated the system as a simple read/write application, writing an order via command and then immediately querying the MongoDB collection to assert the result — a pattern that produced intermittent failures whenever projection lag exceeded the test's implicit wait time.

**Task:** Design a testing strategy that correctly addressed the command side, the projection mechanism, and the query side as separate concerns, and that handled the eventual consistency boundary reliably.

**Action:** I separated the test suite into three distinct layers. Layer 1 — command side tests: I tested the command handlers in isolation, verifying business rule enforcement independently of any read model. Command tests asserted on the events produced by each command — given a `PlaceOrder` command with valid input, the handler should emit an `OrderPlaced` event with the correct payload. I used an in-memory event store for these tests — fast, deterministic, and free of infrastructure dependencies. I also tested business rule rejection: invalid commands (insufficient stock, invalid address) should raise a domain exception and emit no events. Layer 2 — projection tests: I tested the event handler/projector independently of both the command handlers and the query layer. Each projector received a known event payload and I asserted the resulting MongoDB document — was it created, updated correctly, and was every field mapped from the event to the read model accurately? I tested projection idempotency explicitly: processing the same event twice should produce the same read model state as processing it once. I also tested backward compatibility: old event versions (from events still in the event store) should still project correctly after a schema evolution. Layer 3 — consistency boundary integration tests: for end-to-end flows, I used a polling assertion utility (consistent with the team's eventual consistency standard) that polled the read model until the projected state appeared or a 10-second timeout was reached. I set the timeout at the 99th percentile projection lag measured from production monitoring, plus a 3-second safety margin. These tests covered the full journey: command accepted → event emitted → projection updated → query returns expected result. I also wrote a read model accuracy audit test that ran nightly — comparing a sample of read model documents against the authoritative event stream and alerting if any discrepancy was found (signs of a projection bug or missed events).

**Result:** The intermittent failures caused by implicit timing assumptions were eliminated — replaced by explicit, timeout-bounded polling. The projection tests caught three bugs: a field mapping error where the currency code was projected as the currency symbol, a projection idempotency failure where re-processing an event duplicated a line item, and a backward compatibility failure where the projector did not handle the v1 event schema for orders placed before a schema migration. All three were caught before they reached staging.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Tests that a command produces the expected result when queried — often not separating command and query layers |
| **Mid** | Writes separate tests for command handlers and query endpoints; uses polling assertions for eventual consistency |
| **Senior** | Designs a three-layer strategy — command side (event production), projection (read model accuracy, idempotency, schema compatibility), and consistency boundary (polling integration) — with a nightly read model accuracy audit |

## Key Terms

| Term | Definition |
|------|------------|
| **CQRS (Command Query Responsibility Segregation)** | An architectural pattern separating the write model (commands, events, domain logic) from the read model (queries, projections, read-optimised views) |
| **Command handler** | The component that processes a command, enforces business rules, and emits domain events — the authoritative write-side component |
| **Projector** | A component that consumes domain events and updates the read model, translating the event stream into query-optimised representations |
| **Read model** | A denormalised, query-optimised data structure derived from the event stream — used exclusively for query operations |
| **Event store** | A persistent store recording the full history of domain events — the source of truth in an event-sourced CQRS system |
| **Projection idempotency** | The property that a projector produces the same read model state whether it processes an event once or multiple times — required for safe event replay |
| **Read model accuracy audit** | A scheduled test comparing read model documents against the authoritative event stream to detect projection bugs or missing events |
| **Schema evolution (events)** | The change of an event's structure over time — projectors must correctly handle all historical event versions still present in the event store |
