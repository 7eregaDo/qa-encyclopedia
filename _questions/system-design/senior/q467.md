## The Intent
The interviewer is checking whether your quality thinking extends to the operational runtime environment. At senior level, they want to see that you test the application's behaviour under Kubernetes-specific failure conditions — not just whether the application works in isolation. Many applications that pass all functional tests fail in production because they do not handle pod restarts, readiness probe failures, or resource limits correctly.

## The STAR Script
**Situation:** My organisation ran all services on Kubernetes. Three production incidents in a quarter had been caused by Kubernetes-specific failure modes rather than application bugs: one where a pod eviction during a node maintenance window caused in-flight requests to fail, one where a new deployment had health check timeouts set too short and the pod was killed before it had finished initialisation, and one where a memory limit was set below the application's working memory under load, causing OOMKill restarts.

**Task:** Design a testing strategy that would catch these classes of failure before they reached production.

**Action:** I designed the strategy across four areas. Area 1 — Kubernetes manifest validation: I added kube-score and kubeval to the CI pipeline for all manifest changes — catching misconfigurations such as missing resource limits, missing liveness/readiness probes, and containers running as root. I also added a custom OPA policy check that enforced our organisation's specific standards: minimum memory request of 128Mi, maximum CPU limit of 4 cores, and required anti-affinity rules for services with more than one replica. Area 2 — health check correctness: I wrote health check verification tests that deployed the service in a local kind (Kubernetes in Docker) cluster and asserted three properties. The readiness probe returned HTTP 200 only after the application had completed its full startup sequence (database connection pool warmed, caches populated). The liveness probe returned HTTP 200 under normal operation but returned HTTP 500 when the application detected an internal failure condition (I injected a simulated database connection failure). The startup probe allowed sufficient time for slow initialisation without the kubelet killing the pod prematurely. Area 3 — graceful termination testing: I wrote a SIGTERM handling test — sending SIGTERM to the application process while it had in-flight requests and asserting that the application drained existing requests within the `terminationGracePeriodSeconds` window before exiting, returning no 5xx errors to callers during the drain period. This test caught two services that had not implemented SIGTERM handling and would have dropped in-flight requests during rolling deployments. Area 4 — resource constraint testing: I ran load tests against the application at 150% of expected peak traffic in a resource-constrained environment (memory limit set to the production value) and measured whether the application remained stable or triggered OOMKill. If it triggered OOMKill, the memory limit was raised and the incident root cause was reproduced before production.

**Result:** The health check correctness tests caught four misconfigurations across the platform. The graceful termination test caught two services that dropped requests during rolling deployments — both were invisible to functional testing. The resource constraint tests caused one service's memory limit to be tripled before its next release — the OOMKill pattern matched exactly what had occurred in the production incident.

## Key Terms

| Term | Definition |
|------|------------|
| **Pod eviction** | The Kubernetes process of terminating a pod from a node due to resource pressure or node maintenance — applications must handle this gracefully |
| **OOMKill** | The kernel's termination of a container that has exceeded its configured memory limit — detectable in Kubernetes events and often misconfigured |
| **Liveness probe** | A Kubernetes health check that determines whether a pod should be restarted — if it fails, the pod is killed and restarted |
| **Readiness probe** | A Kubernetes health check that determines whether a pod is ready to receive traffic — if it fails, the pod is removed from service load balancing |
| **Startup probe** | A Kubernetes health check specifically for slow-starting containers that allows more time for initialisation before the liveness probe takes over |
| **Graceful termination** | The application behaviour during SIGTERM — draining in-flight requests and releasing resources before the process exits |
| **terminationGracePeriodSeconds** | The Kubernetes configuration specifying how long to wait for graceful termination before sending SIGKILL |
| **kind (Kubernetes in Docker)** | A tool for running Kubernetes clusters inside Docker containers — used for local cluster testing without cloud infrastructure |
