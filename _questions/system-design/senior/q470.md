## The Intent
The interviewer is checking whether you recognise the API gateway as a testable system with its own failure modes, distinct from the services it routes to. At senior level, they want to see that you test gateway-specific behaviours — routing correctness, auth enforcement, rate limiting, caching — explicitly, not by inference from end-to-end tests that cannot isolate gateway behaviour from service behaviour.

## The STAR Script
**Situation:** My organisation used AWS API Gateway with a Lambda authoriser in front of 12 microservices. The gateway performed: JWT validation via the Lambda authoriser, rate limiting per API key, request routing to downstream services, request/response transformation (stripping internal headers, adding correlation IDs), and caching for certain read endpoints. All of these behaviours had never been tested independently of the downstream services — they were inferred to be working because end-to-end tests passed. A production incident revealed that a gateway caching configuration had been caching authenticated user data without user-specific cache keys, serving one user's data to another.

**Task:** Design a testing strategy for the API gateway and edge layer that tested each gateway concern independently from the downstream services.

**Action:** I designed the test suite by gateway concern, using a gateway-only test environment where downstream services were replaced by WireMock stubs returning controlled responses. This allowed me to test gateway behaviour in complete isolation. Authentication and authorisation: I tested that requests with no token, expired tokens, malformed tokens, and tokens signed with the wrong secret all received 401 responses from the Lambda authoriser — before any request reached a downstream service. I also tested that tokens with insufficient scopes received 403 for the relevant endpoints. I verified authoriser caching — a cached authorisation decision for one token should not apply to a different token. Rate limiting: I sent requests exceeding the configured rate limit (100 requests per minute per API key) and verified that the 429 response included a `Retry-After` header and that the rate limit reset correctly after the window. I also tested per-key isolation — exhausting one API key's limit should not affect another key's requests. Routing correctness: I sent requests for all documented API paths and verified they were routed to the correct WireMock stub — catching any path configuration error that would misroute requests. Request transformation: I verified that internal headers (service-to-service auth tokens, internal correlation IDs) were stripped from inbound requests before they reached downstream services, and that the gateway added the expected outbound headers (X-Correlation-ID, X-Request-ID) consistently. Caching: I specifically tested cache key composition — sending requests for the same resource from two different authenticated users and asserting they received distinct, user-specific responses rather than a shared cached response. I also tested cache invalidation behaviour — a write operation to a resource should result in subsequent reads returning fresh data, not the cached value.

**Result:** The caching test immediately reproduced the production incident — the test confirmed that the cache key was missing the user ID, serving cross-user data. The fix added the user ID to the cache key. The rate limiting isolation test found that the rate limiter was using the API key's account ID rather than the specific API key, meaning all keys under the same account shared a single rate limit quota — an undocumented behaviour that several customers had been experiencing as unexplained 429 responses.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Tests that authenticated requests reach downstream services correctly via the gateway |
| **Mid** | Tests authentication rejection, rate limiting, and basic routing correctness using a live gateway in a test environment |
| **Senior** | Designs a gateway-isolated test suite covering authentication, authorisation, rate limiting, routing, request transformation, and cache key composition — using stub downstream services to isolate gateway behaviour from service behaviour |

## Key Terms

| Term | Definition |
|------|------------|
| **API gateway** | A managed component that fronts multiple downstream services, providing cross-cutting concerns including authentication, rate limiting, routing, and transformation |
| **Lambda authoriser** | An AWS API Gateway integration that invokes a Lambda function to validate request authentication before forwarding to downstream services |
| **Gateway-isolated testing** | A test approach that replaces downstream services with stubs, enabling gateway behaviour to be tested independently of service logic |
| **Cache key composition** | The set of request attributes used to generate the cache key — incorrect composition can cause cross-user or cross-tenant cache collisions |
| **Rate limit isolation** | The property that one API key or consumer exhausting its rate limit does not affect the quota of other keys or consumers |
| **Request transformation** | Gateway-level modification of request or response headers, bodies, or parameters before forwarding to downstream services |
| **Authoriser caching** | API Gateway's optional caching of Lambda authoriser decisions — must be configured with per-token cache keys to prevent authorisation bleed between requests |
| **Cross-user cache collision** | A caching defect where one user's cached response is served to a different user — caused by insufficient cache key specificity |
