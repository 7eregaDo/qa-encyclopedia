## The Intent
The interviewer is checking whether you understand that different data types require different testing approaches. Many data quality techniques (null checks, type validation, referential integrity) apply only to structured data — and a QA engineer working on AI systems needs to be able to reason about quality for the unstructured data that most ML models are trained on.

## The STAR Script
**Situation:** My team was building a document classification model. The training dataset consisted of 12,000 PDFs scraped from a regulatory website, and the model's test inputs were free-text customer support emails. Neither dataset was structured — there were no rows, no columns, and no schema to validate against. I was asked to assess the quality of both datasets before the data science team used them.

**Task:** I needed to design a quality assessment approach for two unstructured datasets — the PDF training corpus and the email test set.

**Action:** For the PDF training corpus, I applied four checks. Format validity: I wrote a Python script using PyPDF2 to attempt to open every file and flag any that were corrupted, password-protected, or zero bytes — 47 files failed (0.4% of the corpus). Content sampling: I opened a random sample of 50 PDFs and manually verified they were regulatory documents matching the described source, not blank pages, error pages, or duplicated files — I found 3 clearly irrelevant documents (terms of service pages from the website). Metadata checks: I extracted document length (page count and character count) distributions — documents with under 100 characters were likely extraction failures rather than real content. Label quality: I spot-checked 30 of the human-assigned category labels against the document content to assess labelling consistency. For the email test set, I applied: encoding check (were all emails UTF-8? Non-UTF-8 characters could break the feature extraction pipeline), length distribution (emails under 10 characters were likely system notifications, not real support queries), language detection (did the sample contain non-English emails the model had not been trained on?), and PII scan (did the test set contain real customer names, emails, or account numbers that should have been anonymised?).

**Result:** The PII scan found 23 emails containing real customer names and account numbers — these were anonymised before the test set was used. The length filter removed 140 emails that were automated system notifications. The label quality check found 4 mislabelled training documents that would have introduced noise into the model's training. None of these issues would have been caught by a standard structured-data test suite.

## Key Terms

| Term | Definition |
|------|------------|
| **Structured data** | Data organised into a defined schema with rows, columns, and typed fields — typical of relational databases and CSV files |
| **Unstructured data** | Data without a predefined schema — including text, images, audio, and documents — requiring content-aware quality techniques |
| **Format validity** | A check that a file can be successfully opened and parsed by the expected tool — detecting corruption, truncation, or wrong file type |
| **Content sampling** | Manual or automated review of a random subset of unstructured records to assess whether the content matches its described purpose and category |
| **Label quality** | The accuracy and consistency of human-assigned category labels in a training dataset — a significant determinant of model quality |
| **PII (Personally Identifiable Information)** | Information that can identify an individual — such as name, email address, or account number — requiring anonymisation before use in test or training datasets |
| **Length distribution** | The statistical distribution of document or text lengths in a dataset — extreme outliers (very short or very long) often indicate quality issues |
