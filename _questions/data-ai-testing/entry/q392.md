## The Intent
The interviewer is checking whether you can reason about a pipeline as a sequence of stages with distinct failure modes, not as a black box where data goes in and comes out. A tester who only checks the final output will miss defects that were introduced in the middle and may be amplified by subsequent stages.

## The STAR Script
**Situation:** I was asked to write tests for an ETL pipeline that extracted customer order data from a REST API, transformed it to calculate order values in GBP (converting from multiple currencies), and loaded the results into a reporting database. The pipeline had been running for two months with no tests — a recent discrepancy between the reporting database and the finance team's manual reconciliation had prompted the investigation.

**Task:** I designed tests for each of the three stages to identify where the discrepancy was being introduced.

**Action:** I tested each stage separately using a controlled set of known test records. Extract stage: I verified that the number of records returned by the API matched the count my tests expected (completeness), that the schema of the extracted records matched the documented API contract (no missing or renamed fields), and that the extractor correctly handled pagination — records from the last page of a paginated API response were being dropped, which I found by comparing the API's `total_count` field against the number of records extracted. Transform stage: I tested the currency conversion logic with known inputs — I fed the transform function a record with a USD amount and the exchange rate from the test date, and asserted the GBP output matched my manual calculation. I also tested edge cases: zero amounts, null exchange rates (should raise an error, not silently produce null), and records with unrecognised currency codes. Load stage: I verified that re-running the load with the same data did not create duplicate records (idempotency), that the destination table's constraints (not-null on order_id, positive-only for order_value) were enforced, and that the record count in the destination matched the record count after transformation.

**Result:** The pagination bug in the extract stage was the root cause of the discrepancy — approximately 3% of records were being dropped each run. The currency conversion logic also had a bug for records with null exchange rates: it was substituting a hardcoded fallback rate of 1.0 rather than raising an error, silently treating those amounts as if they were already in GBP. Both were fixed. The stage-by-stage test approach made it straightforward to identify exactly where each bug lived.

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Can name the three ETL stages, describe the main defect type at each, and write basic tests for each stage using known inputs |
| **Mid** | Designs a comprehensive ETL test suite with unit tests on transformation logic, integration tests on stage-to-stage flow, and automated assertions on the final output — integrated into CI/CD |
| **Senior** | Defines the ETL testing standard across the data platform, introduces contract testing at extract boundaries, and builds reusable test frameworks that domain teams can apply to new pipelines |

## Key Terms

| Term | Definition |
|------|------------|
| **Extract** | The first ETL stage: reading raw data from a source system (API, database, file) — subject to completeness failures, schema mismatches, and pagination bugs |
| **Transform** | The middle ETL stage: cleaning, reshaping, and calculating derived values — the most logic-intensive stage and the most common location of business rule defects |
| **Load** | The final ETL stage: writing transformed data to the destination — subject to duplicate record creation, constraint violations, and silent truncation |
| **Pagination** | A source API mechanism returning large datasets in multiple pages — a common source of record loss when an extractor does not handle all pages correctly |
| **Idempotency** | The property that running a pipeline multiple times on the same input produces the same output without creating duplicate records |
| **Fallback value** | A default value substituted when an expected input is missing — can silently mask data quality issues if not surfaced as an error |
| **Constraint violation** | A load-stage failure where the data being written violates a rule defined on the destination table — such as a null in a required column or a negative value in a positive-only field |
