## The Intent
The interviewer is checking whether you can work directly with data rather than relying on applications to surface quality issues. A QA engineer who can write SQL can test data independently of any UI or API — going directly to the source to verify that values are correct, records are complete, and relationships are intact.

## The STAR Script
**Situation:** I was testing a CRM migration where customer records were being moved from a legacy SQL Server database to a new Postgres warehouse. The migration team had run the ETL and declared it complete, but there was no automated verification — the sign-off process was a manual spot-check of five records.

**Task:** I was asked to design a SQL-based verification suite that would give confidence the migration was complete and correct before the legacy system was decommissioned.

**Action:** I wrote a set of SQL verification queries across four dimensions. Completeness: I compared the row count in the source against the destination — `SELECT COUNT(*) FROM legacy.customers` versus `SELECT COUNT(*) FROM warehouse.customers`. The counts matched (47,382 records each), but I also checked for records present in the source but absent in the destination using a LEFT JOIN anti-pattern: `SELECT l.customer_id FROM legacy.customers l LEFT JOIN warehouse.customers w ON l.customer_id = w.customer_id WHERE w.customer_id IS NULL`. This returned 14 records — customers who had been soft-deleted in the legacy system were excluded by the ETL logic but the team had not documented this. Uniqueness: `SELECT customer_id, COUNT(*) FROM warehouse.customers GROUP BY customer_id HAVING COUNT(*) > 1` — returned zero rows, confirming no duplicate IDs. Referential integrity: `SELECT o.order_id FROM warehouse.orders o LEFT JOIN warehouse.customers c ON o.customer_id = c.customer_id WHERE c.customer_id IS NULL` — returned 3 orders referencing customer IDs that did not exist in the customers table. Null checks on required fields: `SELECT COUNT(*) FROM warehouse.customers WHERE email IS NULL OR first_name IS NULL` — returned 0. Value constraints: `SELECT COUNT(*) FROM warehouse.orders WHERE order_total < 0` — returned 2 records with negative totals, a data error in the source that had not been caught by the ETL.

**Result:** The 14 missing records were investigated and the exclusion logic documented as intentional. The 3 orphaned orders were traced to a bug in the ETL join condition and corrected. The 2 negative order totals were flagged to the data team as a source data quality issue. The migration was declared complete only after all queries returned expected results. The SQL suite was committed to the project repository as the regression test for any future migrations.

## Key Terms

| Term | Definition |
|------|------------|
| **Row count assertion** | A SQL query comparing the number of records in a table or query result against an expected value — the simplest completeness check |
| **Anti-join** | A SQL pattern using LEFT JOIN … WHERE right_table.key IS NULL to identify records present in one table but absent in another |
| **Referential integrity** | A data quality constraint requiring that foreign key values in one table correspond to existing records in the referenced table |
| **Duplicate check** | A SQL query using GROUP BY and HAVING COUNT(*) > 1 to identify repeated values in a column that should be unique |
| **Null check** | A SQL assertion verifying that required columns contain no null values — a completeness test |
| **Value constraint** | A rule that a column's values must satisfy — such as non-negative order totals or valid date ranges — testable with a WHERE clause and COUNT |
| **Soft delete** | A record marked as inactive or deleted using a status flag rather than physically removed from the database — a common source of row count discrepancies in migrations |
