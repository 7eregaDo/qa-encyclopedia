## The Intent
The interviewer is checking whether you can design evaluation with rigour — defining what quality means for a specific LLM application, choosing appropriate measurement methods for each dimension, and building the infrastructure to run evaluation consistently at release time and in production. At senior level, this is an architectural question as much as a testing question.

## The STAR Script
**Situation:** My organisation had six LLM-powered features in production: a customer support chatbot, a contract summarisation tool, a code review assistant, a marketing copy generator, a document Q&A feature, and an internal policy search. Each had been launched with minimal evaluation — a manual review of a handful of outputs before launch. Model updates from the provider were being applied automatically without any quality gate. Two incidents had occurred: the contract summarisation tool had begun omitting key clauses after a model update, and the code review assistant had started recommending deprecated APIs.

**Task:** I was asked to design a unified LLM evaluation framework that would serve as a release gate for all six features and detect quality regressions from model updates.

**Action:** I designed the framework in three layers. Layer 1 — feature-specific quality taxonomy: I worked with the owner of each feature to define the quality dimensions specific to their use case. For the contract summarisation tool: accuracy (are all material clauses present?), completeness (is nothing significant omitted?), and format compliance (correct section structure). For the code review assistant: technical correctness (are recommendations syntactically valid and non-deprecated?), relevance (do recommendations apply to the specific code submitted?), and safety (no recommendations introducing security vulnerabilities). I documented these taxonomies in a quality specification document per feature — the input to test design. Layer 2 — measurement method selection per dimension: I classified each quality dimension by its measurability. Deterministically measurable: format compliance (regex and length checks), deprecated API detection (static analysis against a known deprecated API list), structured output schema. LLM-as-judge: accuracy, completeness, relevance, technical correctness — I wrote judge prompts calibrated against human ratings for each dimension. For each judge prompt I ran a calibration exercise: 50 human-rated examples, measuring agreement between the judge and human raters. I required Cohen's kappa above 0.6 before accepting a judge prompt for production use. Human evaluation: safety, tone, and any dimension where the LLM-as-judge calibration was below threshold. Layer 3 — release gate infrastructure: I built a versioned evaluation pipeline that ran on every model provider update, every prompt change, and every feature configuration change. The pipeline ran each feature's golden test set (100–200 curated inputs per feature), computed all dimension scores, and compared against the stored baseline from the previous passing evaluation. A regression of more than 3 percentage points on any dimension was a release blocker. I stored all evaluation runs with their configuration state — model version, prompt version, feature configuration — enabling precise attribution of any quality change.

**Result:** The framework was operational within six weeks. The first model provider update after deployment triggered the evaluation pipeline and detected a 7-point regression in the contract summarisation tool's completeness score — the same class of defect that had caused the previous production incident. The update was held until the prompt was adjusted to compensate. Over the following four months the framework caught three provider-side regressions and two prompt change regressions before they reached users.

## Key Terms

| Term | Definition |
|------|------------|
| **Quality taxonomy** | A structured definition of the quality dimensions relevant to a specific LLM feature — the foundation for test design |
| **LLM-as-judge** | A technique using a second LLM, prompted with scoring criteria, to evaluate the quality of a primary model's outputs at scale |
| **Cohen's kappa** | A statistical measure of agreement between two raters that accounts for chance agreement — used to validate that an LLM judge is sufficiently aligned with human judgment |
| **Golden test set** | A curated, versioned set of inputs with stored baseline quality scores — used to detect regressions across model or prompt updates |
| **Judge calibration** | The process of validating an LLM judge prompt against human ratings on a representative sample, ensuring the judge's scores reflect human quality judgment |
| **Release gate pipeline** | An automated evaluation run triggered by any change to the model, prompt, or configuration — comparing against the stored baseline and blocking releases that regress beyond defined thresholds |
| **Baseline** | The stored quality scores from the previous passing evaluation run — the reference against which new evaluation results are compared |
