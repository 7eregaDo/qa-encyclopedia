## The Intent
The interviewer is checking whether you treat model versioning as a testable engineering property rather than an informal convention. Models that cannot be reproduced cannot be audited, compared, or safely rolled back — and in regulated industries, reproducibility is a compliance requirement. At senior level, they want to see that you have built the infrastructure to make it verifiable.

## The STAR Script
**Situation:** My organisation had experienced two incidents where rolling back a model after a production quality regression had failed: in the first case, the previous model version's preprocessing pipeline had been overwritten; in the second, the training data used for the previous version could not be identified because dataset versioning had not been implemented. Both rollbacks required retraining from scratch, causing extended degradation windows.

**Task:** I was asked to design a model versioning and reproducibility testing strategy that would guarantee safe rollback capability for all production models.

**Action:** I designed the strategy around four versioned artefacts and a suite of reproducibility tests. Versioned artefacts: I defined that every model release must produce and store four artefacts as an immutable unit in our MLflow registry — the trained model weights, the preprocessing pipeline (as a serialised scikit-learn Pipeline object), the training dataset reference (a pointer to the exact versioned dataset in our Delta Lake, not a copy), and a training configuration file specifying all hyperparameters, random seeds, and library versions. These four artefacts were tagged with the same version identifier and stored with a retention policy of 24 months minimum. Reproducibility tests: I wrote a scheduled monthly reproducibility test for each Tier 1 model — the test retrieved the artefacts for a specified historical version, re-executed the training pipeline using the stored dataset reference and configuration, and compared the resulting model's evaluation metrics against the stored evaluation results. I defined a tolerance of ±0.5 percentage points on the primary metric — differences within this range were accepted as expected variation from random initialisation; differences above it indicated a reproducibility failure. I also tested rollback mechanics: a quarterly rollback drill where I actually deployed a previous version to a staging environment using only the stored artefacts, verifying the full process took under 30 minutes and required no manual steps. Preprocessing parity test: I verified that the stored preprocessing pipeline produced identical feature values as the current production serving pipeline for a set of known inputs — preventing the scenario where the model weights and preprocessing logic drifted apart between storage and serving.

**Result:** The monthly reproducibility test identified a failure in month two: a dependency on a third-party data enrichment API had changed its response format, meaning the training pipeline could not be re-executed without a code fix. This was addressed before it became a rollback emergency. The rollback drill revealed the process had been taking 4 hours, not 30 minutes, due to undocumented manual steps — these were automated, bringing it within the target SLA. The quarterly drills gave the team genuine confidence in rollback capability rather than assumed capability.

## Key Terms

| Term | Definition |
|------|------------|
| **Model artefact** | A file produced during model training that is required for inference or reproducibility — including model weights, preprocessing pipeline, and configuration |
| **MLflow** | An open-source platform for managing the ML lifecycle, including experiment tracking, model versioning, and model registry |
| **Reproducibility** | The property that re-executing a training pipeline with the same inputs produces a model with equivalent performance — a requirement for audit, comparison, and safe rollback |
| **Preprocessing parity** | The condition where the feature transformations applied during training are identical to those applied at serving time — a prerequisite for model correctness in production |
| **Rollback drill** | A scheduled exercise where a previous model version is actually deployed to a staging environment, validating the rollback process and its SLA |
| **Delta Lake** | An open-source storage layer providing versioning and ACID transactions for data lake tables — enabling reproducible dataset references in model training |
| **Training configuration** | A versioned record of all training parameters — hyperparameters, random seeds, library versions — required to reproduce a training run |
