## The Intent
The interviewer is checking whether you are at the frontier of AI testing practice. Multi-agent systems are moving from experimental to production rapidly, and the testing challenges they introduce — emergent behaviour, inter-agent trust, cascading failure, and irreversible action chains — are not addressed by any existing testing framework. At senior level, they want to see original thinking grounded in engineering principles.

## The STAR Script
**Situation:** My team was building a multi-agent AI system for automated software delivery pipeline management. An orchestrator agent received a natural language instruction ("deploy version 2.4 to staging and run the smoke tests"), decomposed it into sub-tasks, and delegated to specialised agents: a deployment agent that interfaced with Kubernetes, a test execution agent that ran the test suite, and a notification agent that sent Slack messages. I was asked to design the testing approach before any production traffic.

**Task:** I needed to design tests that went beyond individual agent capability testing and addressed the correctness and safety of the multi-agent system as a whole.

**Action:** I designed the test suite across five layers. Layer 1 — individual agent unit tests: I tested each agent in isolation with controlled inputs and asserted correct tool calls and outputs. This was standard but necessary as a baseline — a failing individual agent made multi-agent behaviour uninterpretable. Layer 2 — inter-agent communication contract tests: I defined a message schema for each agent-to-agent communication channel and wrote contract tests verifying that the orchestrator's output messages were correctly formed for each specialised agent's input schema. This caught a case where the deployment agent expected a `namespace` field that the orchestrator was not including. Layer 3 — task completion correctness: I created 40 scripted end-to-end scenarios with defined expected outcomes — the deployment should happen to the correct environment, the correct test suite should run, and the notification should reference the correct version number. I asserted on final state, not intermediate steps, to allow agent flexibility in execution path while enforcing outcome correctness. Layer 4 — failure propagation tests: I injected failures at each agent (deployment agent returns a failure, test execution agent times out, notification agent is unavailable) and verified: the orchestrator correctly detected the failure, took the appropriate recovery action (retry, rollback, or escalate), and did not proceed to subsequent steps that would be invalid given the earlier failure. Critically, I verified the system never sent a success notification after a failed deployment — a false confirmation was the highest-risk failure mode. Layer 5 — emergent behaviour and constraint tests: I tested scenarios designed to elicit unexpected inter-agent interactions — giving the orchestrator ambiguous instructions, conflicting sub-tasks, and instructions that would require one agent to override another agent's previous action. I verified the system recognised ambiguity and escalated to a human rather than attempting resolution, and that no agent chain could execute an irreversible action (deleting a production resource) without an explicit confirmation step.

**Result:** Layer 4 found the most critical defect: when the deployment agent failed after partial completion (3 of 5 Kubernetes pods updated), the orchestrator treated the partial deployment as a failure and attempted a rollback — but the rollback agent did not receive enough context to know which pods had been updated and rolled back all 5, including the 2 that had not been updated in the failed run. The orchestrator was updated to pass a deployment state object to the rollback agent. The constraint tests confirmed that the irreversible action guard was working — no production resource deletion could be triggered without a confirmation step.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Understands what a multi-agent system is and that agents interacting create testing challenges beyond individual agent testing |
| **Mid** | Tests individual agents and basic inter-agent communication, and verifies failure handling for simple two-agent flows |
| **Senior** | Designs a multi-layer test suite covering individual agents, inter-agent contracts, end-to-end task correctness, failure propagation, and emergent behaviour constraints — with explicit irreversibility guards and human escalation verification |

## Key Terms

| Term | Definition |
|------|------------|
| **Multi-agent system** | An AI architecture where multiple AI agents interact, delegate tasks to each other, and collectively pursue a goal — introducing emergent behaviour not present in individual agents |
| **Orchestrator agent** | An agent responsible for decomposing high-level instructions into sub-tasks and delegating them to specialised agents |
| **Inter-agent contract** | A schema defining the message format exchanged between two agents — analogous to an API contract between services |
| **Emergent behaviour** | System behaviour arising from the interaction of components that cannot be predicted from testing those components individually |
| **Failure propagation** | The behaviour of a multi-agent system when one agent fails — determining whether the failure is correctly detected, contained, and recovered |
| **Irreversibility guard** | A safeguard requiring explicit confirmation before an agent executes an action that cannot be undone — preventing automated systems from making unrecoverable mistakes |
| **Partial completion** | A state where a multi-step task has been partially executed when a failure occurs — requiring the system to correctly track and communicate what was and was not completed |
