## The Intent
The interviewer is checking whether you understand the technical differences between batch and real-time feature computation and can design appropriate tests for each. Many ML platforms run both — batch for training, real-time for serving — and the consistency between them is a critical and frequently untested quality property.

## The STAR Script
**Situation:** My team's ML platform computed 47 features for our fraud detection model. Thirty-two were computed nightly in a batch Spark job and stored in an offline feature store. Fifteen were computed in real time from a Kafka stream and stored in an online Redis store. The model had been trained using the batch features and served using the real-time features — an architecture that assumed the two pipelines produced equivalent values. A model quality investigation revealed the real-time `transaction_velocity_24h` feature (number of transactions by the same card in the past 24 hours) was returning values up to 40% lower than the batch version for the same time window.

**Task:** I was asked to design testing that would catch this class of discrepancy and verify each pipeline type with appropriate techniques.

**Action:** I designed separate test suites for each pipeline type and a consistency test between them. Batch pipeline tests: I wrote deterministic input/output tests using a fixed set of synthetic transaction records with known feature values. I tested idempotency (same input, same output on re-run), completeness (all expected feature rows present in the output), and edge cases (no transactions in the window producing a zero velocity, transactions exactly on the window boundary). Real-time pipeline tests: I wrote latency tests verifying that feature values were available in Redis within 500ms of the triggering transaction event being published to Kafka. I tested concurrent event handling — sending 50 transactions for the same card in rapid succession and verifying the velocity count was exactly 50, not a race-condition-corrupted lower value. I also tested late-arriving events by publishing a transaction with a timestamp 2 hours in the past and verifying the pipeline correctly placed it in the historical window rather than treating it as current. Consistency tests: I designed a point-in-time consistency test — for a set of 200 cards, I retrieved the `transaction_velocity_24h` feature from both the batch store (using the most recent batch run's values) and the real-time store, and asserted the values were within 5% of each other. This test ran daily and caught the existing 40% discrepancy immediately when I first executed it. Root cause: the real-time pipeline was counting transactions from the Kafka event stream but only receiving events from one regional Kafka cluster — transactions from a second region were not being consumed. The batch pipeline read from a unified database view including all regions.

**Result:** The missing Kafka cluster topic was added to the real-time pipeline subscription. The 40% discrepancy was eliminated. The daily consistency test was retained as a monitoring check, and over the following six months it detected two further inconsistencies introduced by infrastructure changes.

## Key Terms

| Term | Definition |
|------|------------|
| **Batch feature pipeline** | A pipeline that computes features on a scheduled basis (e.g., nightly) from historical data — used to generate training datasets and populate the offline feature store |
| **Real-time feature pipeline** | A pipeline that computes features continuously from a live event stream — used to populate the online feature store for low-latency model inference |
| **Transaction velocity** | A feature representing the number of transactions by the same entity (card, user, account) within a defined time window — commonly used in fraud detection |
| **Point-in-time consistency test** | A test comparing the same feature value computed by two different pipelines at the same logical time — used to detect training-serving skew |
| **Late-arriving event** | A streaming event with a timestamp earlier than the current processing time — requiring correct windowing logic to place it in the right historical computation window |
| **Race condition** | A concurrency defect where the outcome depends on the relative timing of concurrent operations — a risk in real-time feature computation under high event throughput |
| **Latency SLA** | A defined maximum time within which a real-time feature must be available for model inference after the triggering event — a testable performance requirement |
