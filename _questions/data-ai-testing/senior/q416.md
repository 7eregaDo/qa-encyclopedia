## The Intent
The interviewer is checking whether you understand that the architectural choice between warehouse and lakehouse changes where quality guarantees come from — and therefore what you need to test explicitly. At senior level, they want to see that you can adapt your quality strategy to the architecture, not apply the same tests to both.

## The STAR Script
**Situation:** My organisation was migrating from a Snowflake data warehouse to a Delta Lake-based lakehouse on Azure. I was responsible for ensuring the quality testing approach was updated to reflect the architectural differences — the existing test suite had been written assuming warehouse-enforced schema constraints and would not provide equivalent coverage on the lakehouse.

**Task:** I needed to identify the quality guarantees the warehouse had provided automatically, determine which of those were now the testing layer's responsibility, and design tests to cover the gaps.

**Action:** I mapped the warehouse's automatic guarantees against the lakehouse's behaviour in four areas. Schema enforcement: In Snowflake, writing a string to an integer column raised an error at write time. In Delta Lake with schema-on-read, the same write would succeed — the type mismatch would only surface when a consumer read the column expecting an integer. I added explicit schema enforcement tests using Delta Lake's `enforceSchema` option in all write operations, and added post-write schema validation using Great Expectations on every table that had previously relied on warehouse enforcement. ACID transactions: Delta Lake supports ACID transactions, but only if writers use the Delta protocol correctly. I added tests verifying that concurrent writes (simulating two pipeline jobs writing to the same table simultaneously) did not produce corrupt results or missing records — something the warehouse had handled transparently. Time travel and versioning: Delta Lake's time-travel capability meant I could query table state at any previous version. I wrote tests verifying that time-travel queries returned the correct historical state, and tested that the `VACUUM` operation (which deletes old versions to reclaim storage) was not configured to delete versions within the 30-day audit retention window. Partition quality: Lakehouse tables are typically partitioned by date or another high-cardinality column. I added partition completeness checks — verifying that every expected partition (every date in the past 90 days) was present and non-empty — a check that was unnecessary in the warehouse because partitioning was transparent to the writer.

**Result:** The schema enforcement gap was confirmed immediately: one pipeline writing to the new lakehouse was silently writing nulls to an integer column that the warehouse had previously rejected. The concurrent write test found that two pipelines writing to an unbucketed table were causing occasional record loss — fixed by adding table bucketing. The test suite was updated and the migration proceeded with equivalent quality coverage to the original warehouse.

## Key Terms

| Term | Definition |
|------|------------|
| **Data warehouse** | A structured, schema-enforced analytical data store — typically column-oriented, with types and constraints enforced at write time |
| **Data lakehouse** | An architecture combining a data lake's flexible storage with warehouse-like ACID transactions and metadata management — implemented by formats such as Delta Lake, Apache Iceberg, and Apache Hudi |
| **Schema-on-read** | A data lake pattern where schema is applied when data is read rather than enforced at write time — enabling flexibility but requiring explicit quality testing |
| **Delta Lake** | An open-source storage layer providing ACID transactions, schema enforcement, and time travel for data lake tables |
| **Time travel** | A Delta Lake feature enabling queries against historical table versions by specifying a version number or timestamp |
| **VACUUM** | A Delta Lake operation that deletes old table versions to reclaim storage — must be configured to preserve versions within audit retention requirements |
| **Partition completeness** | A check verifying that all expected partitions (e.g., all dates in a date-partitioned table) exist and contain data |
