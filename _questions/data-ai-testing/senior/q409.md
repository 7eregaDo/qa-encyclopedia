## The Intent
The interviewer is checking whether you can manage quality across the full RAG system lifecycle — from knowledge base to production monitoring — rather than treating evaluation as a one-time pre-launch activity. At senior level, RAG quality is a continuous operational concern, not a release gate.

## The STAR Script
**Situation:** My organisation ran a RAG-powered internal legal knowledge assistant used by 200 lawyers to query case law, internal policies, and contract templates. The system had been launched with a pre-release RAGAS evaluation but had no production monitoring. Lawyers were reporting that answers were sometimes outdated (the knowledge base had not been updated since launch), occasionally cited documents that did not support the stated conclusion, and sometimes failed to find relevant precedents that lawyers knew existed.

**Task:** I was asked to design a quality programme that addressed the full RAG pipeline in production — knowledge base, retrieval, and generation — with ongoing monitoring and a feedback loop.

**Action:** I designed the programme across four components. Component 1 — knowledge base quality: I introduced a knowledge base audit process. Every document in the corpus had a `valid_until` metadata field; I built a weekly job that flagged documents where `valid_until` was in the past and alerted the legal operations team. I also implemented ingestion quality checks: every new document added to the knowledge base was run through a validation pipeline verifying PDF parsability, minimum content length (filtering blank pages and cover sheets), and deduplication against existing content. Component 2 — retrieval quality: I built a retrieval evaluation set of 150 queries with ground-truth relevant document lists assembled by two senior lawyers. I measured recall@5 (were the relevant documents in the top 5 results?) and mean reciprocal rank weekly. Declining retrieval quality triggered a review of the embedding model and chunking strategy. I also ran a coverage test: 20 queries known to have highly relevant precedents in the corpus, verifying they were retrieved — a sentinel set for retrieval degradation. Component 3 — generation quality: I sampled 50 answered queries daily and evaluated them on three dimensions using a legal-domain LLM judge: faithfulness (every claim in the answer attributable to the retrieved documents), citation accuracy (cited documents actually contain the stated information), and completeness (no material relevant information omitted from the retrieved context). Component 4 — user feedback loop: I implemented a thumbs-down button on every answer. Each thumbs-down triggered a review queue. I classified negative feedback into three categories — wrong answer, outdated information, missing relevant precedent — and routed each category to the appropriate fix: knowledge base update, retrieval tuning, or generation prompt adjustment.

**Result:** The knowledge base audit found 34 documents that were outdated — including three case summaries that had been superseded by appeal judgments. The retrieval sentinel set revealed a recall@5 regression after the embedding model provider updated their model — caught within one week rather than discovered through user complaints. The feedback classification showed that 62% of negative feedback was categorised as "missing relevant precedent" — indicating a systematic retrieval gap for certain legal domains that the team addressed with domain-specific re-indexing.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Understands what RAG is and that retrieval and generation are separate components with separate failure modes |
| **Mid** | Designs and executes component-isolated tests for the retrieval layer (recall@k, MRR) and generation layer (faithfulness, hallucination rate) |
| **Senior** | Owns the full production RAG quality programme — knowledge base curation, retrieval monitoring, generation sampling, and user feedback loop — as a continuous operational discipline |

## Key Terms

| Term | Definition |
|------|------------|
| **Knowledge base audit** | A scheduled review of the documents in a RAG corpus to identify outdated, duplicated, or malformed content |
| **Recall@k** | A retrieval metric measuring the proportion of relevant documents present in the top k results returned for a given query |
| **Mean reciprocal rank (MRR)** | A retrieval metric measuring the average reciprocal of the rank of the first relevant result across a query set |
| **Faithfulness** | A RAGAS metric measuring whether all claims in a generated answer are supported by the retrieved context — the primary hallucination detection metric |
| **Citation accuracy** | A verification that documents cited in an LLM answer actually contain the information attributed to them |
| **Sentinel set** | A fixed set of queries with known correct retrieval results, run regularly to detect retrieval degradation before it is apparent from general metrics |
| **Feedback classification** | The categorisation of user-reported quality failures into actionable types — enabling systematic routing to the correct remediation path |
