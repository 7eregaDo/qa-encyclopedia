## The Intent
The interviewer is checking whether you can operate privacy testing as an engineering discipline at scale — not a one-off audit or a manual checklist, but an automated, continuous programme that catches privacy defects in the same way functional tests catch bugs. At senior level, this is about architecture and systematic enforcement, not individual pipeline checks.

## The STAR Script
**Situation:** My organisation's data platform had grown to 80 tables containing personal data across 14 domains. A GDPR audit by an external firm found three issues: PII was present in two tables that were supposed to be anonymised, one pipeline was retaining data beyond its documented retention period, and a development environment contained a copy of production data including unmasked customer email addresses. The audit cost £180K and had taken six weeks. The DPO asked me to design a programme that would catch these issues continuously rather than waiting for an annual audit.

**Task:** I was asked to design and implement a data privacy testing programme covering PII detection, anonymisation correctness, retention enforcement, and environment data segregation — automated and running on a continuous basis.

**Action:** I designed the programme across four enforcement layers. Layer 1 — PII detection scanning: I deployed Microsoft Presidio as a scanning service that ran weekly against all tables in the platform catalogued as containing personal data, sampling 1,000 rows per table and applying entity recognition for names, email addresses, phone numbers, national ID numbers, and financial account numbers. Tables tagged as anonymised but returning PII hits above a 0.1% rate generated an alert. I also ran Presidio against the data catalogue metadata — column names like `customer_email` in supposedly anonymised tables were flagged for review. Layer 2 — anonymisation correctness testing: For each anonymisation pipeline, I wrote a property-based test that generated synthetic PII-containing records, ran them through the pipeline, and asserted the output contained no detectable PII. I used `hypothesis` (a Python property-based testing library) to generate varied synthetic records rather than fixed examples — ensuring the tests covered edge cases such as names embedded in free-text fields and non-standard email formats. Layer 3 — retention enforcement testing: I built a retention compliance check that ran monthly against every table with a documented retention period. The check computed the age of the oldest record in each table and compared it against the retention policy. Tables retaining data beyond policy triggered a deletion workflow review. I also tested the deletion workflow itself: I created synthetic records with a backdated timestamp, ran the deletion workflow, and verified the records were physically deleted (not merely soft-deleted with a flag). Layer 4 — environment data segregation: I implemented a data classification tag on every table (public, internal, confidential, restricted) and a policy check that verified no table tagged confidential or restricted was present in the development or staging environments. The check ran on every environment provisioning event.

**Result:** The Presidio scanner found PII in a table that had been partially anonymised — the free-text `notes` field had not been included in the anonymisation pipeline. The environment segregation check caught a data copy event in week two — an engineer had manually copied a restricted table to staging for debugging. Both were caught within days, not months. The DPO confirmed the programme addressed all three audit findings and reduced the scope of the next annual audit to a review of the programme's controls rather than a full data scan.

## Key Terms

| Term | Definition |
|------|------------|
| **Microsoft Presidio** | An open-source PII detection and anonymisation toolkit providing entity recognition for names, emails, phone numbers, and other identifiers in text and structured data |
| **Property-based testing** | A testing technique where tests are defined as properties that must hold for any valid input, with the testing framework generating varied inputs automatically — more thorough than fixed example-based tests |
| **Hypothesis** | A Python property-based testing library that generates diverse synthetic inputs to test defined invariants — useful for anonymisation correctness testing across varied PII formats |
| **Retention policy** | A defined maximum period for which personal data may be retained — a GDPR obligation that must be enforced technically, not just documented |
| **Data classification tag** | A metadata label on a data asset indicating its sensitivity level (public, internal, confidential, restricted) — used to enforce access and environment segregation policies |
| **Environment data segregation** | A control ensuring that production personal data does not appear in development or staging environments — a fundamental GDPR principle of purpose limitation |
| **Soft delete** | Marking a record as deleted using a status flag without removing it from storage — insufficient for GDPR retention compliance, which requires physical deletion |
