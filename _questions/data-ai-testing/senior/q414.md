## The Intent
The interviewer is checking whether you apply the shift-right testing mindset to data systems — recognising that production failures cannot be fully anticipated and that resilience must be demonstrated through deliberate fault injection, not just assumed from the absence of observed failures. At senior level, they want structured methodology, not random experimentation.

## The STAR Script
**Situation:** My organisation's data platform served 30 downstream consumers from 18 pipelines. The pipelines had functional tests and quality monitors, but no resilience testing. We had experienced two production incidents where a source system failure caused unexpected behaviour: in one case a pipeline had run successfully but written stale data because a source API had returned cached data without error; in the other, a schema change in an upstream system had caused a pipeline to fail silently — logging success but writing no records.

**Task:** I was asked to design a chaos engineering programme for the five highest-criticality pipelines to surface resilience gaps before they caused production incidents.

**Action:** I structured the programme around four failure categories with defined hypotheses and blast radius controls for each. Category 1 — source unavailability: Hypothesis: the pipeline detects source unavailability, raises an alert, and does not write stale or empty data to the destination. Method: I used a network policy to block the pipeline's access to the source system for 10 minutes during a scheduled run in the staging environment. Expected behaviour: pipeline fails with an explicit error, no records written, alert fires. Actual finding: two pipelines wrote an empty dataset without raising an error — a silent failure. Category 2 — schema corruption: Hypothesis: the pipeline detects an unexpected schema change and halts rather than writing incorrectly typed data. Method: I temporarily altered a field type in the source schema and ran the pipeline. Expected behaviour: schema validation fails, pipeline halts, alert fires. Finding: one pipeline wrote records with null values in the affected field and logged a warning rather than an error — downstream consumers received data with unexplained nulls. Category 3 — volume spike: Hypothesis: a 10× volume spike does not cause data loss or processing errors. Method: I replayed 10× the normal event volume against the streaming pipeline. Finding: the pipeline processed all records but with a 45-minute delay, breaching the pipeline's 30-minute SLA — an SLA failure that had never been tested. Category 4 — partial source failure: Hypothesis: when a source returns data for only 60% of expected partitions, the pipeline detects the partial failure rather than treating it as a complete successful run. Finding: no pipeline had a completeness check — all accepted partial data as a full run.

**Result:** Eight specific resilience defects were found across the five pipelines. All were fixed before the programme had run against all 18 pipelines. The most impactful fix was adding completeness checks — these subsequently caught two production partial failures that would previously have been invisible.

## Key Terms

| Term | Definition |
|------|------------|
| **Chaos engineering** | The practice of deliberately injecting failures into a system under controlled conditions to verify resilience properties and surface unknown failure modes |
| **Blast radius** | The scope of impact if a chaos experiment produces unexpected results — controlled by running experiments in staging environments and at limited scale |
| **Silent failure** | A pipeline failure mode where the system runs without error but produces no output or incorrect output — the most dangerous failure mode because monitoring does not detect it |
| **Fault injection** | The deliberate introduction of a failure condition — network block, schema corruption, resource constraint — to test a system's response |
| **Completeness check** | A post-pipeline assertion verifying that the expected number of partitions, records, or data points was processed — detecting partial source failures |
| **Resilience hypothesis** | A statement predicting how a system should behave under a specific failure condition — the test criterion for a chaos experiment |
| **SLA breach** | A failure to meet a defined performance or availability commitment — in pipeline testing, typically a latency or freshness threshold |
