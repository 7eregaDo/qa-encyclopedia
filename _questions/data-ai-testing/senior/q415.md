## The Intent
The interviewer is checking whether you can operationalise safe model deployment — recognising that ML model releases carry quality risk that is not fully predictable from offline evaluation, and that canary deployment is the mechanism for managing that risk in production. At senior level, they want the full implementation: traffic splitting, signal selection, threshold governance, and rollback automation.

## The STAR Script
**Situation:** My organisation released ML model updates by deploying directly to 100% of traffic after offline evaluation. Two production incidents had occurred: a retrained fraud model with a higher false positive rate caused a wave of legitimate transaction declines before the issue was detected, and a personalisation model update caused a measurable drop in session engagement that took 48 hours to diagnose and roll back.

**Task:** I was asked to design and implement a canary deployment process for ML model releases that would contain the blast radius of quality regressions to a small user population and enable fast automated rollback.

**Action:** I designed the canary process in four components. Component 1 — traffic splitting: I implemented model routing in the prediction service to send a configurable percentage of requests to the canary model and the remainder to the production model. I started at 5% canary traffic for all new releases, with a defined progression: 5% for 2 hours, 20% for 4 hours, 50% for 4 hours, 100% — each step requiring no threshold breaches in the preceding window. Component 2 — signal selection per model: For the fraud model: false positive rate (legitimate transactions declined), false negative rate (fraud transactions passed), and prediction latency. For the personalisation model: click-through rate and session duration (business metrics), and output distribution PSI against the production baseline. Each model's signal set was documented in a deployment runbook. Component 3 — threshold governance: I defined canary thresholds as relative comparisons against the production baseline, not absolute values, to account for natural variation. A canary model that caused a metric to move more than 2 standard deviations from the production model's baseline over a 30-minute window triggered automatic rollback. I calibrated the threshold by analysing historical production metric variance — ensuring the threshold was tight enough to catch real regressions without false-triggering on normal noise. Component 4 — automated rollback: I integrated the monitoring with the model serving layer's deployment API. When a threshold breach was detected, an automated rollback reduced the canary percentage to 0% within 60 seconds without human intervention, and posted an alert to the on-call channel with the specific metric that had triggered it.

**Result:** The first release using the canary process was a fraud model retrain. At 5% traffic, the false positive rate was 1.8 standard deviations above the production baseline — within the threshold. At 20% traffic it reached 2.3 standard deviations — triggering automatic rollback. The rollback happened in 58 seconds. The incident affected 20% of traffic for 4 hours rather than 100% for 48 hours — an order-of-magnitude improvement in blast radius. Investigation found the new model had been inadvertently trained on an imbalanced dataset; the retraining was fixed and the release redeployed successfully.

## Key Terms

| Term | Definition |
|------|------------|
| **Canary deployment** | A release strategy where a new version is exposed to a small percentage of production traffic first, allowing quality signals to be observed before full rollout |
| **Traffic splitting** | The mechanism routing a defined percentage of production requests to the canary model and the remainder to the production model |
| **Blast radius** | The scope of user impact if the canary model has a quality regression — limited by the canary traffic percentage |
| **Automated rollback** | A system that automatically reduces canary traffic to zero when quality signals breach defined thresholds — without requiring human intervention |
| **Relative threshold** | A rollback trigger defined as a deviation from the production model's baseline, measured in standard deviations — more robust than absolute thresholds for metrics with natural variance |
| **Deployment runbook** | A documented specification for a model's canary deployment — traffic progression steps, quality signals, threshold values, and rollback procedure |
| **False positive rate** | The proportion of negative instances (legitimate transactions) incorrectly classified as positive (fraudulent) — a critical quality metric for fraud models with direct user impact |
