## The Intent
The interviewer is checking whether you can own the full test scope for a pipeline, not just individual components. Unit tests on transformation functions and schema checks on outputs are necessary but not sufficient — end-to-end testing catches the class of defects that only emerge when all stages run together, such as ordering dependencies, state management bugs, and timing issues.

## The STAR Script
**Situation:** My team operated a pipeline that ingested webhook events from a payment provider, enriched them with customer data from an internal API, aggregated daily payment totals per customer, and loaded them into a Snowflake reporting table. The pipeline had unit tests on the enrichment logic and schema checks on the output, but no end-to-end test. A production incident had occurred where a network timeout between the enrichment API call and the aggregation step caused some records to be aggregated without enrichment data — producing totals attributed to a null customer ID.

**Task:** I was asked to design an end-to-end test that would have caught this incident and would protect against similar failures.

**Action:** I built the end-to-end test suite in three parts. Part 1 — controlled input fixture: I created a synthetic set of 50 webhook events covering the scenarios I wanted to test: standard payment events, a refund event, a duplicate event (the same event ID appearing twice), and three events with a customer ID that did not exist in the enrichment API (to test the not-found handling). I seeded these into a test copy of the ingestion queue. Part 2 — full pipeline execution against test environment: I ran the complete pipeline in a dedicated test environment where the enrichment API was a WireMock stub returning known responses. I configured one stub to simulate a 30-second timeout (exceeding the pipeline's configured timeout threshold) for one specific customer ID, to reproduce the conditions of the production incident. Part 3 — output assertions: After the pipeline completed, I queried the Snowflake test schema and asserted: the output contained exactly 47 rows (50 events minus 3 refunds that reduced totals below zero and were excluded by business logic — this number required me to understand the pipeline's rules precisely), no rows had a null customer ID, the duplicate event had been deduplicated (appearing only once in the output), the timeout event had produced a row with an explicit `enrichment_status: failed` flag rather than a null customer ID, and the aggregate total for each customer matched my manual calculation from the fixture data.

**Result:** The timeout test exposed the original bug: the pipeline was producing a null customer ID row rather than a flagged enrichment failure row. The deduplication test also found that duplicate events were not being deduplicated — they were being counted twice. Both were fixed. The end-to-end test suite was committed to CI and ran on every deployment, catching a further aggregation logic regression introduced during a performance optimisation two months later.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Can describe what end-to-end pipeline testing means and write basic output assertions against a known input |
| **Mid** | Designs and implements a full end-to-end pipeline test suite with controlled fixtures, failure scenario coverage, and precise output assertions — integrated into CI |
| **Senior** | Architects the end-to-end test infrastructure across multiple pipelines, defines fixture management standards, and introduces production traffic replay as a complementary validation technique |

## Key Terms

| Term | Definition |
|------|------------|
| **End-to-end pipeline test** | A test that exercises the complete data pipeline from source input to final output in a controlled environment, using known inputs to assert on known outputs |
| **Fixture data** | A synthetic, controlled dataset with known properties used as the input to a pipeline test — enabling deterministic output assertions |
| **Enrichment** | A pipeline stage that augments records with additional data from an external source — a common point of failure when that source is unavailable or slow |
| **Deduplication** | The process of identifying and removing duplicate records from a pipeline — a correctness property that must be tested explicitly |
| **Idempotency** | The property that running a pipeline multiple times on the same input produces the same output without accumulating duplicate records |
| **WireMock stub** | A simulated HTTP service that returns controlled responses — used to test pipeline behaviour under dependency failure conditions without depending on the real service |
| **Production traffic replay** | The technique of capturing real production inputs and replaying them against a pipeline in a test environment — complementing synthetic fixtures with realistic data distributions |
