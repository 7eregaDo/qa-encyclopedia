## The Intent
The interviewer is checking whether you treat data schema changes with the same rigour as API breaking changes. In data systems, schema changes are a leading cause of silent downstream failures — pipelines continue running but produce incorrect results because a field was renamed or a type was changed. At mid level, they want to see that you have a systematic approach to managing this risk.

## The STAR Script
**Situation:** Our data platform used Apache Avro schemas to define the structure of events published to Kafka topics. A data engineering team changed the `user_id` field from integer to string to support a new ID format — they considered this a minor change, merged it, and deployed. Three downstream pipelines that cast `user_id` to integer immediately failed with type errors. A fourth pipeline silently accepted the string but produced incorrect join results because the string IDs did not match the integer IDs in the customer database.

**Task:** I was asked to design a schema evolution testing practice that would prevent this class of incident.

**Action:** I introduced three practices. First, a compatibility classification rule: I documented four change types and their compatibility status — adding an optional field (backwards compatible: consumers that do not use it are unaffected), adding a required field (breaking: existing producers cannot provide it), removing a field (breaking: consumers that use it will fail or silently receive null), changing a field type (breaking in almost all cases). This classification was added to the team's definition of done for any schema change. Second, automated compatibility checks in CI: I configured the schema registry (Confluent Schema Registry) to enforce backward compatibility validation on every schema change submitted. A breaking change — such as the integer-to-string type change — would fail the CI check before merge. I also wrote a test that submitted both the old and new schema versions to a local schema registry instance and asserted the compatibility check result matched the expected classification. Third, consumer impact testing: for any schema change that passed the compatibility check (i.e., was backwards compatible), I wrote a test that ran each registered consumer against a sample of messages conforming to the new schema and verified the consumer produced correct output. For breaking changes (approved via a formal deprecation process), I ran the consumer tests against both the old and new schema versions during the migration window.

**Result:** The compatibility check would have blocked the integer-to-string change as a breaking change before it was merged. After implementation, three schema change proposals were rejected by the CI check in the following two months — two were redesigned as backwards-compatible changes (the field was added as a new optional field rather than replacing the existing one), and one went through the formal breaking change process with a coordinated consumer migration.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Understands that schema changes can break downstream consumers and can identify obvious breaking changes |
| **Mid** | Classifies schema changes by compatibility, implements automated compatibility checks in CI, and runs consumer impact tests for both compatible and breaking changes |
| **Senior** | Designs the schema governance programme — compatibility policy, schema registry configuration, breaking change migration workflow, and multi-environment promotion strategy |

## Key Terms

| Term | Definition |
|------|------------|
| **Schema evolution** | The process of modifying a data schema over time — ideally managed through controlled, compatibility-aware changes |
| **Backwards compatibility** | A schema change property meaning existing consumers can continue to function correctly without modification |
| **Breaking change** | A schema modification that causes existing consumers to fail or produce incorrect results — requiring a coordinated migration |
| **Schema registry** | A centralised service that stores and versions data schemas, and can enforce compatibility rules when new schema versions are submitted |
| **Avro** | A binary serialisation format for data with a schema embedded or referenced — widely used in Kafka-based data pipelines |
| **Compatibility check** | An automated validation that a proposed schema change does not violate the defined compatibility mode (backward, forward, or full) |
| **Consumer impact test** | A test that runs a downstream consumer against data conforming to a new schema version to verify it continues to produce correct output |
