## The Intent
The interviewer is checking whether you understand the specific quality risk that feature stores are designed to solve — and whether you know how to verify that a feature store is actually solving it. Many teams adopt feature stores without testing the consistency guarantee they are meant to provide, negating much of the benefit.

## The STAR Script
**Situation:** Our ML platform used Feast as a feature store to serve features to both the offline training pipeline and the online prediction service. Three months after deploying a new churn prediction model, the data science team noticed the model's production accuracy was 8 percentage points below its offline evaluation accuracy. The most likely explanation was training-serving skew — but no tests existed to confirm or diagnose it.

**Task:** I was asked to design a test suite that would detect training-serving skew and verify that the feature store was delivering consistent feature values across both serving contexts.

**Action:** I designed tests across three consistency dimensions. Dimension 1 — transformation parity: I extracted the feature transformation code used in the offline pipeline and the online serving path and compared them side by side. I found that the offline pipeline was computing `account_age_days` as the number of days since account creation, while the online serving path was computing it as the number of days since first login — a semantic difference introduced during a refactor. I wrote a test that computed the same feature for 100 known customer records using both paths and asserted the outputs were within a tolerance of ±1 day. Dimension 2 — point-in-time correctness: Feature stores must retrieve the feature values as they existed at the time of the training event, not the current values. I tested this by writing a training example with a known historical timestamp, retrieving features from the offline store using that timestamp, and asserting the retrieved values matched the values recorded in the audit log for that customer at that point in time. Dimension 3 — online/offline value distribution parity: I sampled 500 customer records and retrieved their features from both the offline batch store and the online real-time store within a one-minute window, then computed summary statistics (mean, standard deviation, null rate) for each feature. Features where the online and offline distributions differed by more than 5% were flagged for investigation.

**Result:** The transformation parity test confirmed training-serving skew as the root cause of the accuracy gap. The `account_age_days` semantic difference meant the model had been trained on one version of the feature and served a different version — an invisible bug that no amount of model evaluation could have caught without this test. The fix aligned both pipelines to the same definition. The distribution parity test was added as a weekly scheduled check and caught a further skew in a different feature four months later.

## Key Terms

| Term | Definition |
|------|------------|
| **Feature store** | A centralised system for storing, serving, and managing ML features — providing the same features to both offline training and online serving to prevent skew |
| **Training-serving skew** | A defect where features used during model training differ from features served at prediction time — causing model performance degradation that is not detectable from evaluation metrics alone |
| **Offline store** | The feature store component serving historical feature values for model training — typically backed by a data warehouse or object store |
| **Online store** | The feature store component serving low-latency feature values for real-time model inference — typically backed by a key-value store such as Redis |
| **Point-in-time correctness** | The property that historical feature retrieval returns the value the feature had at the specified timestamp, not the current value — essential for preventing data leakage in training |
| **Transformation parity** | The condition where the feature transformation logic in the offline pipeline is identical to the logic in the online serving path |
| **Feast** | An open-source feature store that provides both offline and online serving of ML features with support for multiple storage backends |
