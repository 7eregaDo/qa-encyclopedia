## The Intent
The interviewer is checking whether you can solve the test data problem in data and AI contexts — where using real data creates privacy risk, but using unrealistic synthetic data produces tests that pass in CI but miss production defects. At mid level, they want to see that you can both generate and validate synthetic data, not just produce it.

## The STAR Script
**Situation:** My team was building a new data pipeline that would process financial transaction records containing customer names, account numbers, and transaction amounts. We needed a realistic test dataset for CI testing and local development, but using real transaction data was prohibited under the organisation's data handling policy.

**Task:** I was asked to generate synthetic transaction data that was realistic enough to test the pipeline thoroughly while containing no real customer information.

**Action:** I approached the task in two phases — generation and validation. Generation: I used the Python library `Faker` for identifier and name fields (generating realistic-looking but fake names and account numbers), and `scipy.stats` to sample numerical fields (transaction amounts, account balances) from fitted distributions derived from summary statistics of the real data — I obtained mean, standard deviation, and percentile breakdowns from the data science team without accessing the raw data itself. I also deliberately generated edge cases that the real data might not contain in sufficient quantity: zero-amount transactions, transactions in unusual currencies, accounts with single-character names, and timestamps at midnight and at daylight saving time transitions. I structured the synthetic dataset as 10,000 records with a documented composition: 9,000 "normal" records, 500 edge cases, and 500 deliberately invalid records (nulls in required fields, negative amounts, malformed account numbers) for testing the pipeline's validation and rejection logic. Validation: I validated the synthetic data on three dimensions. Statistical representativeness: I computed the same summary statistics on the synthetic data as I had obtained from real data and confirmed they were within 10% — the synthetic data had the right shape. Schema conformance: I ran the synthetic data through the same schema validator used in production to confirm it was structurally correct. Pipeline coverage: I ran the full pipeline against the synthetic data and confirmed all 10 code paths I had identified in the transformation logic were exercised by at least one record.

**Result:** The synthetic dataset caught a timezone handling bug in the pipeline — one of my deliberately crafted daylight saving time transition records triggered a timestamp subtraction error that real data had not yet exposed. The "deliberately invalid" records verified that all 500 rejection cases were handled correctly. The dataset was committed to the repository and used in CI for all subsequent development.

## Key Terms

| Term | Definition |
|------|------------|
| **Synthetic data** | Artificially generated data that mimics the statistical properties and structure of real data without containing information about real individuals |
| **Faker** | A Python library for generating fake but realistic-looking identifiers — names, addresses, emails, phone numbers, and account numbers |
| **Statistical representativeness** | The property that a synthetic dataset has the same distributional characteristics as the real data it represents — ensuring tests reflect realistic conditions |
| **Fitted distribution** | A statistical distribution whose parameters are derived from real data summary statistics — used to generate synthetic numerical values with the correct shape |
| **Edge case generation** | The deliberate creation of synthetic records at the boundaries of expected data behaviour — values not present in sufficient quantity in real data to test specific code paths |
| **Code path coverage** | A measure of whether a test dataset exercises all branches of the transformation logic — ensuring that edge-case code paths are tested, not just the common case |
| **Privacy validation** | A check confirming that a synthetic dataset contains no real personal information — typically including a scan for patterns matching real identifiers |
