## The Intent
The interviewer is checking whether you treat deduplication and idempotency as first-class testable properties. Both are critical for data reliability — duplicate records corrupt aggregations and ML training data, and non-idempotent pipelines cannot be safely retried after failure. At mid level, they want concrete test design, not just a definition.

## The STAR Script
**Situation:** Our event ingestion pipeline received clickstream events from a JavaScript SDK. Due to network retries in the SDK, the same event could be sent multiple times with an identical `event_id`. The pipeline was supposed to deduplicate on `event_id`, but a post-launch audit found that the events table contained 7% duplicate records — the deduplication logic was only active in the initial load and not in the incremental update path.

**Task:** I was asked to write tests that would have caught this and that would protect deduplication and idempotency going forward.

**Action:** I designed a test suite covering four scenarios. Scenario 1 — exact duplicate detection: I sent a batch of 100 events where 20 had a duplicate `event_id` (the same ID appearing exactly twice). I ran the pipeline and asserted the output contained exactly 100 records, not 120 — verifying that one record from each duplicate pair was removed. I further asserted that the retained record was the one with the earlier `received_at` timestamp (the pipeline's documented tie-breaking rule). Scenario 2 — near-duplicate handling: I sent events where two records had the same `event_id` but slightly different `properties` payloads (the second delivery of an event sometimes contained additional fields populated by a later SDK flush). I verified the pipeline retained the first record and did not merge or split properties — a deliberate business rule decision I had confirmed with the product team. Scenario 3 — distinct record preservation: I sent 50 events with unique `event_id` values that shared other attributes (same `user_id`, same `event_type`, same timestamp to the second). I verified all 50 were retained — the deduplication key was `event_id` only, not a combination of fields. Scenario 4 — idempotency: I ran the pipeline against a batch of 100 events, confirmed 100 records in the output, then ran the exact same batch again. I asserted the output still contained 100 records, not 200. I ran this test against both the full-load path and the incremental update path — this is where the existing bug lived, and the test confirmed it by failing on the incremental path before the fix.

**Result:** The incremental path idempotency test failed immediately, confirming the bug. The fix extended the deduplication logic to the incremental path. All four scenarios were added to the CI pipeline. A further deduplication regression was caught three months later when a performance optimisation accidentally removed the deduplication step from a specific partition of the incremental path.

## Key Terms

| Term | Definition |
|------|------------|
| **Deduplication** | The process of identifying and removing duplicate records from a dataset, typically using a unique key such as an event ID |
| **Deduplication key** | The field or combination of fields used to identify records as duplicates — choosing the wrong key either misses duplicates or incorrectly removes distinct records |
| **Near-duplicate** | Two records that share a deduplication key but differ in one or more other fields — requiring a defined business rule about which to retain and whether to merge fields |
| **Tie-breaking rule** | A defined criterion for choosing which record to retain when multiple duplicates exist — such as the earliest or latest timestamp |
| **Idempotency** | The property that running a pipeline multiple times on the same input produces the same output without accumulating additional records |
| **Incremental path** | A pipeline execution mode that processes only new or changed records since the last run — as opposed to a full reload of all records |
| **Full-load path** | A pipeline execution mode that reprocesses all input records from scratch — typically used for initial loads or full refreshes |
