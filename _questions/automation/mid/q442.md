## The Intent
The interviewer is checking whether you treat flakiness as a systematic engineering problem rather than an irritation to be managed by retries. At mid level, they want to see a diagnostic methodology — categorising root causes, applying targeted fixes, and preventing recurrence — not just "we added retries and moved on." Retries mask flakiness; the right answer is eliminating it.

## The STAR Script
**Situation:** Our Playwright suite had grown to 280 tests with a 19% flake rate — nearly one in five test runs produced a different result from the previous run on the same code. The team had responded by adding automatic retries (up to three attempts per test), which had hidden the problem from the CI pass rate while tripling the average pipeline duration for affected tests. Developer trust in the suite had eroded — failures were routinely dismissed as "probably flaky."

**Task:** I was asked to investigate the root causes systematically and reduce the flake rate to below 5% within two months.

**Action:** I ran a structured flakiness investigation over two weeks. Step 1 — flakiness inventory: I ran the full suite 10 times in sequence in a clean CI environment without retries and recorded every test that produced at least one inconsistent result. This identified 53 flaky tests. Step 2 — root cause categorisation: I examined each of the 53 tests and categorised them into five root cause buckets. Timing issues (31 tests): tests relying on `waitForTimeout` with hardcoded delays rather than waiting for specific application state — the most common cause. Fix: replace all `waitForTimeout` calls with `waitForSelector`, `waitForResponse`, or `waitForLoadState` appropriate to the specific condition being waited for. Shared state (9 tests): tests that modified shared user accounts or records and left them in a changed state for subsequent tests. Fix: implement per-test data creation and teardown using API calls in `beforeEach`/`afterEach` hooks. Test order dependence (6 tests): tests that assumed a previous test had completed a setup step. Fix: make each test self-contained with its own setup. Environment flakiness (4 tests): tests failing only in CI due to resource constraints — animation timings, slower rendering. Fix: disable CSS animations in CI via a test configuration flag and increase viewport-specific timeouts. Non-deterministic data (3 tests): tests asserting on dynamically ordered lists without specifying a sort order. Fix: sort the list before asserting or assert on set membership rather than exact order. Step 3 — remediation and measurement: I fixed each category systematically rather than test-by-test, applying the same pattern fix across all tests with the same root cause. I removed the retry configuration to surface any remaining flakiness honestly.

**Result:** After remediation, the flake rate dropped from 19% to 2.8%. Pipeline duration dropped by 35% (the retries had been adding significant overhead). Developer trust recovered — the team began treating failures as genuine signals again. I introduced a flakiness tracking metric in the weekly quality report, with a threshold of 5% triggering an automatic investigation sprint.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Can identify that a test is flaky and describe common causes such as timing issues; knows that retries exist |
| **Mid** | Categorises flakiness by root cause, applies targeted fixes appropriate to each category, tracks flake rate as a suite health metric, and removes retries as a crutch once root causes are addressed |
| **Senior** | Designs a flakiness detection and remediation programme at scale — automated flakiness scoring per test, quarantine workflow for chronically flaky tests, and flakiness prevention patterns enforced through code review standards |

## Key Terms

| Term | Definition |
|------|------------|
| **Flaky test** | A test that produces inconsistent results (sometimes passing, sometimes failing) for the same code under the same conditions |
| **Flake rate** | The proportion of test runs producing at least one inconsistent result — a key suite health metric |
| **waitForTimeout** | A hardcoded time delay in test code — the most common source of timing-related flakiness, masking rather than addressing the underlying timing assumption |
| **waitForSelector / waitForResponse** | Playwright methods that wait for a specific application condition before proceeding — the correct replacement for hardcoded delays |
| **Test order dependence** | A flakiness root cause where a test assumes a previous test has completed a setup step — eliminated by making each test self-contained |
| **Retry** | Automatically re-running a failed test — masks flakiness in pass rate metrics without addressing root cause, and adds pipeline duration overhead |
| **Quarantine** | The practice of isolating chronically flaky tests from the main suite while their root cause is investigated — preventing them from generating noise while remaining tracked |
