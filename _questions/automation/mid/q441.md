## The Intent
The interviewer is checking whether you understand POM beyond the textbook definition — they want to see that you have hit the scaling problems and made deliberate architectural decisions to address them. Many candidates describe POM as the solution; senior mid-level candidates describe the specific ways POM breaks down at scale and what they did about it.

## The STAR Script
**Situation:** I joined a team with a 200-test Playwright suite that used POM throughout. The page objects had grown organically over two years — the `DashboardPage` class had 340 lines and 47 methods covering everything from navigation to data export to user management. When a UI change affected the dashboard, updating the page object required understanding which of the 47 methods were relevant to the change. New team members found the objects intimidating and avoided touching them.

**Task:** I was asked to redesign the POM architecture to be maintainable, focused, and navigable by any team member — without rewriting the entire suite.

**Action:** I introduced four design principles and refactored incrementally over six weeks. Principle 1 — single responsibility per object: I decomposed the `DashboardPage` god object into focused objects by functional area — `DashboardNavigation`, `DashboardFilters`, `DashboardExport`, `UserManagementSection`. Each had under 15 methods and a clear, named responsibility. Tests composed these objects as needed rather than inheriting from a single sprawling class. Principle 2 — no test logic in page objects: I audited every page object for assertion code and conditional logic. Page objects should describe how to interact with a page, not what to verify or decide. I moved all assertions back into test files and replaced conditional flow in page objects with simple, unconditional interaction methods. Principle 3 — component objects for shared UI elements: the modal dialogs, notification banners, and data tables appeared in multiple pages but were being re-implemented in each page object. I extracted `ModalDialog`, `NotificationBanner`, and `DataTable` as standalone component objects that page objects composed rather than duplicated. Principle 4 — avoid deep inheritance: the suite had a three-level inheritance chain (`BasePage` → `AuthenticatedPage` → `AdminPage` → `DashboardPage`). Changes to `BasePage` broke all descendants unpredictably. I replaced the inheritance chain with composition — objects included a `Navigation` component rather than inheriting navigation from a parent.

**Result:** The refactored suite reduced average page object size from 180 lines to 40 lines. New team members reported being able to locate and modify the relevant page object within 5 minutes of receiving a failing test report — previously this had taken 20–30 minutes. When a major UI redesign affected the filter controls, the change required updating one `DashboardFilters` object rather than hunting through a 340-line god class.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Can define POM and implement a basic page object for a single page with locators and interaction methods |
| **Mid** | Identifies POM anti-patterns (god objects, test logic in page objects, deep inheritance), refactors toward single responsibility and component composition, enforces boundaries through code review |
| **Senior** | Designs the full automation object model architecture — page objects, component objects, fixtures, and data factories — with explicit boundary rules and automated linting to enforce them |

## Key Terms

| Term | Definition |
|------|------------|
| **Page Object Model (POM)** | An abstraction pattern encapsulating page locators and interactions behind a class interface, separating test intent from implementation detail |
| **God object** | An anti-pattern where a single class grows to contain methods for many unrelated concerns — the most common POM failure mode at scale |
| **Single responsibility** | The principle that each class or object should have one clearly defined purpose — applied to POM by decomposing large page objects into focused objects by functional area |
| **Component object** | A reusable automation object representing a shared UI element (modal, table, navigation) that multiple page objects compose rather than re-implement |
| **Composition over inheritance** | A design principle preferring objects that include other objects over objects that extend parent classes — more flexible and less tightly coupled |
| **Test logic leakage** | The anti-pattern of placing assertions or conditional branching inside page objects — coupling test decisions to page implementation |
| **Incremental refactoring** | Improving code architecture gradually without rewriting the entire codebase — the pragmatic approach to addressing accumulated technical debt in a live suite |
