## The Intent
The interviewer is checking whether you understand visual regression testing as a workflow problem as much as a tooling problem. Many candidates describe taking screenshots and comparing pixels; at mid level, they want to see that you have addressed the hard parts — dynamic content producing false positives, baseline management, and the review process for deciding which visual diffs are genuine regressions versus intentional changes.

## The STAR Script
**Situation:** Our design system had 45 reusable components shared across four product areas. CSS changes to shared components frequently introduced unintended visual regressions in downstream areas — a colour change intended for the button component would inadvertently affect the notification banner, which used the same CSS variable. These regressions were caught in manual QA but not consistently and not quickly.

**Task:** I was asked to implement visual regression testing for the component library that would automatically detect unintended visual changes without generating excessive noise from expected updates.

**Action:** I implemented visual regression testing using Playwright's built-in screenshot comparison, with Percy for the review workflow. Implementation: I added `expect(page).toHaveScreenshot()` assertions to a dedicated visual test suite covering each of the 45 components in isolation (using Storybook as the rendering host) and five full-page snapshots of critical product views. Running components in isolation (rather than in full page contexts) made comparisons stable and reduced false positives from dynamic surrounding content. Dynamic content handling: timestamps, user-specific data, and animated elements were the primary sources of false positives. I masked dynamic regions in screenshots using Playwright's `mask` option — passing locators for timestamp fields, avatar images, and any element with CSS animations. I also disabled CSS transitions globally in the test configuration using `page.addStyleTag({ content: '* { transition: none !important; animation: none !important; }' })` — eliminating animation-timing false positives. Baseline management: I configured Percy for the review workflow. Every PR with visual differences opened a Percy build for team review — diffs were presented side-by-side with the changed percentage. Reviewers approved intentional changes (updating the baseline) or rejected unintended ones (creating a bug). I established a rule: visual test baselines could only be approved by two reviewers — the QA engineer and a designer. This prevented developers from self-approving visual changes that were actually regressions. Threshold configuration: for pixel-level differences caused by anti-aliasing or font rendering variation across environments, I set a 0.1% difference threshold below which changes were auto-approved — eliminating the noise from sub-pixel rendering differences.

**Result:** In the first month, visual regression testing caught three unintended component regressions that had not been noticed in manual review — a hover state colour shift, a button padding change that affected alignment in a card component, and a font weight regression introduced by a dependency update. The dual-reviewer approval process caught two instances where developers had approved visual changes without realising they represented regressions. Percy build review became part of the PR process for any CSS or component change.

## Key Terms

| Term | Definition |
|------|------------|
| **Visual regression testing** | Automated detection of unintended visual changes by comparing screenshots against approved baselines |
| **Baseline** | A stored screenshot of the accepted appearance of a UI element or page — the reference against which future screenshots are compared |
| **Pixel-by-pixel comparison** | The comparison method that identifies every changed pixel between a new screenshot and the baseline |
| **Dynamic content masking** | Configuring specific regions of a screenshot to be excluded from comparison — used for timestamps, user-specific content, and animation frames |
| **Baseline drift** | The gradual accumulation of approved but incorrect baselines — when visual regressions are approved without being identified as such |
| **Percy** | A cloud visual review platform that presents screenshot diffs for human approval and manages baseline versioning |
| **Difference threshold** | A configured maximum pixel difference percentage below which changes are auto-approved — used to tolerate sub-pixel rendering variation between environments |
