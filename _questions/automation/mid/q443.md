## The Intent
The interviewer is checking whether you can design a practical, risk-based cross-device strategy — not just list tools. The challenge is making the strategy concrete enough to be deliverable: which devices, which tests, at which pipeline stage, using which infrastructure, at what cost. At mid level, they want to see specific decisions rather than the aspiration of testing on everything.

## The STAR Script
**Situation:** Our product was a responsive web application used across desktop, tablet, and mobile. Analytics showed 38% of sessions on mobile, but the automation suite ran only on a desktop Chromium viewport. Two mobile-specific layout bugs had reached production in the past quarter — the navigation collapsed incorrectly on 375px-wide viewports, and form inputs were not scrolling into view on iOS Safari when the keyboard opened.

**Task:** I was asked to design a cross-device testing strategy that would catch mobile-specific issues before production without dramatically increasing CI pipeline duration or cost.

**Action:** I designed the strategy across three tiers based on risk and user share. Tier 1 — emulated viewports in CI (every PR, zero additional cost): I added Playwright device profiles for the three highest-volume device categories — `iPhone 13` (mobile portrait, 390×844), `iPad Air` (tablet, 820×1180), and `Desktop 1280`. For every PR, the smoke suite ran against all three viewports in parallel — adding approximately 3 minutes to the pipeline. I identified the tests most likely to surface layout issues (navigation, forms, modals, data tables) and tagged them `@responsive` — these ran against all three viewports; the remainder ran against desktop only. Tier 2 — real device testing on BrowserStack for release candidates: emulation does not reproduce all iOS Safari behaviours — specifically the keyboard viewport-resize behaviour that had caused our production bug. I integrated BrowserStack into the release candidate pipeline, running the `@responsive` tagged suite against five real devices: iPhone 14 (iOS 16 Safari), Samsung Galaxy S22 (Chrome Android), iPad Pro (Safari), Pixel 6 (Chrome), and an older iPhone SE (iOS 15) to represent the lower end of our supported range. This added 18 minutes to the release candidate pipeline — acceptable given the frequency. Tier 3 — scheduled monthly full real-device regression: once a month, the full suite ran against the BrowserStack real device matrix. This caught cumulative cross-device regressions that the targeted runs might miss.

**Result:** The first Tier 1 PR run immediately caught a regression — a CSS change had broken the hamburger menu on the 390px viewport. The BrowserStack release candidate run caught the iOS Safari keyboard behaviour on the following release — the same class of bug that had previously reached production. Real-device testing cost was contained to approximately £180/month through targeted test selection rather than running the full suite on every device.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Understands that applications behave differently across devices and can configure a test to run against an emulated mobile viewport |
| **Mid** | Designs a tiered cross-device strategy — emulated viewports in CI, real device testing on cloud platforms for release candidates, targeted test selection based on risk — with defined device matrices from analytics |
| **Senior** | Architects the cross-device testing programme at scale — native mobile automation with Appium, visual regression across devices, device farm governance, and performance benchmarking per device category |

## Key Terms

| Term | Definition |
|------|------------|
| **Device matrix** | The defined set of device types, screen sizes, and operating systems against which tests are executed — derived from real user analytics |
| **Playwright device profiles** | Pre-configured viewport and user agent combinations in Playwright simulating specific mobile devices — enabling emulated cross-device testing without real hardware |
| **BrowserStack** | A cloud platform providing access to real physical and virtual devices for automated and manual browser and mobile testing |
| **Emulation vs real device** | Emulation replicates screen size and user agent but not hardware-specific behaviours (GPS, gyroscope, camera, keyboard resize) — real devices reproduce these faithfully |
| **Tiered device strategy** | A cross-device testing approach applying different device coverage at different pipeline stages — proportionate to risk and execution cost |
| **Responsive testing** | Verification that a web application's layout and interactions function correctly across the range of supported viewport sizes |
| **Viewport-resize behaviour** | The change in available viewport height when a mobile keyboard opens — a common source of mobile-specific layout bugs not reproducible in desktop emulation |
