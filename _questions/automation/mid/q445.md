## The Intent
The interviewer is checking whether you have moved beyond ad-hoc `beforeEach` blocks toward structured, reusable approaches to test state management. At mid level, they want to see that you understand the difference between fixtures (dependency injection for tests) and factories (object construction with controlled variation), and that you can apply both to make tests readable, isolated, and maintainable.

## The STAR Script
**Situation:** Our Playwright test suite had grown to 180 tests, and test setup code had proliferated in three ways that were making the suite hard to maintain: identical `beforeEach` blocks were copy-pasted across multiple test files (creating 12 versions of the same authentication setup), test files were directly calling API endpoints to create test data (exposing low-level HTTP details in business-level tests), and some tests had 40 lines of setup before the first meaningful assertion.

**Task:** I was asked to refactor the test setup approach to make tests concise, readable, and reusable — reducing duplication without making each test's dependencies invisible.

**Action:** I introduced fixtures and factories as complementary patterns. Fixtures for authentication and session state: I used Playwright's `test.extend()` to create custom fixtures. I defined an `authenticatedPage` fixture that handled login, cookie persistence, and navigation to the authenticated state — any test that needed an authenticated session declared it as a parameter and received it pre-configured. I defined scope variants: `authenticatedPage` (session-scoped — one login per test file), `freshAuthenticatedPage` (test-scoped — fresh login for each test), and `adminPage` (admin role session). Tests declared which fixture they needed; the framework handled setup and teardown. Factories for test data construction: I created a `UserFactory`, `OrderFactory`, and `ProductFactory` — each providing a `create()` method with sensible defaults and an `overrides` parameter for targeted variation. `UserFactory.create({ role: 'admin' })` created a user with all required fields populated and the specified role overridden. The factory made the API call internally — tests declared what they needed without knowing the HTTP details. Composing fixtures and factories: I extended the `authenticatedPage` fixture to accept a `user` parameter sourced from a factory — tests could request `authenticatedPage` with a specific user configuration in a single line. Teardown was handled by the fixture's `afterEach` hook — tests declared dependencies and received cleaned-up state without managing their own teardown.

**Result:** The average test setup code dropped from 25 lines to 4 lines. The 12 duplicated authentication setups were replaced by two fixture declarations. A test that previously read as 45 lines of HTTP calls and state manipulation now read as 8 lines expressing its intent clearly: request an authenticated admin session, perform the action, assert the result. New team members could write a new test by declaring the fixture they needed rather than copying a setup block and adapting it — which had been introducing subtle bugs when the copy was not perfectly adapted.

## Key Terms

| Term | Definition |
|------|------------|
| **Fixture** | A reusable, scoped dependency injected into tests on demand — providing setup and teardown without the test managing it directly |
| **Factory pattern** | A design pattern encapsulating object construction with sensible defaults and targeted overrides — used in testing to create test data objects without exposing construction details in test code |
| **test.extend()** | A Playwright API for defining custom fixtures that extend the base test object with additional dependencies |
| **Fixture scope** | The lifecycle of a fixture — test-scoped (created and destroyed per test), file-scoped (per test file), or session-scoped (once per suite run) |
| **Dependency injection** | The principle of providing a component's dependencies from outside rather than having it create them — fixtures apply this principle to tests |
| **Sensible defaults** | Factory-provided values for all fields that most tests do not care about — allowing tests to specify only the fields relevant to their scenario |
| **Teardown** | The cleanup performed after a test or fixture scope ends — deleting created test data, closing sessions, resetting state |
