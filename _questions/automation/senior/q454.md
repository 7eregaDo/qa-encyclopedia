## The Intent
The interviewer is checking the depth of your software engineering knowledge applied to automation. At senior level, they expect you to draw on broader software design patterns rather than treating POM as the only tool in the architecture toolkit. They want to see specific patterns applied to specific automation problems — with concrete examples of when and why you chose each.

## The STAR Script
**Situation:** I was redesigning the automation architecture for a complex financial services platform. POM was in place but the suite had three recurring maintenance problems: test data construction was duplicated across 40 test files (each building its own version of complex nested objects like loan applications), third-party API interactions (credit bureau, payment processor) were scattered throughout the test code, and complex multi-step actions (complete a loan application workflow) were re-implemented in multiple tests with slight variations.

**Task:** Identify which software design patterns would address each maintenance problem and implement them in the automation framework.

**Action:** I applied three patterns to address the three distinct problems. Problem 1 — complex test data construction: I applied the **builder pattern**. A loan application involved 12 nested objects (applicant, employment, income, assets, liabilities, requested loan details, guarantor details, documents). Creating this in tests produced 50+ lines of construction code per test. I built a `LoanApplicationBuilder` class with a fluent interface — `LoanApplicationBuilder.standard().withApplicant(applicant).withRequestedAmount(50000).build()`. The builder provided sensible defaults for all fields, allowing tests to override only the fields relevant to their scenario. A test verifying the income verification step only needed to specify income-related fields — the builder handled everything else. Problem 2 — third-party API interactions: I applied the **facade pattern**. The credit bureau API required OAuth authentication, specific header configuration, request signing, and response normalisation. Five test files had their own version of this setup code. I built a `CreditBureauFacade` class exposing simple methods — `CreditBureauFacade.getReport(applicantId)`, `CreditBureauFacade.simulateDefaultRisk(applicantId)` — hiding all integration complexity behind a clean interface. When the credit bureau API changed its authentication mechanism, one facade update propagated correctly to all 5 consumers. Problem 3 — multi-step actions: I applied the **command pattern**. The "complete loan application" workflow was a 9-step process implemented differently in 8 tests. I built a `CompleteLoanApplication` command class with a single `execute(actor, loanApplicationData)` method encapsulating the full workflow. Tests that needed a completed loan application as a precondition called the command — they did not re-implement the workflow. When the workflow changed (a new compliance step was added), one command update applied to all 8 tests.

**Result:** The builder pattern reduced test data construction code by approximately 75% — tests that previously had 50 lines of setup had 8. The facade pattern centralised all third-party integration code — the authentication change required 30 minutes, not 3 hours. The command pattern meant the compliance step addition required one code change, not eight. I documented all three patterns in the framework ADR with the specific problem each solved — enabling future engineers to choose the right pattern for new problems.

## Key Terms

| Term | Definition |
|------|------------|
| **Builder pattern** | A creational design pattern providing a fluent interface for constructing complex objects with defaults and targeted overrides — used for complex test data construction |
| **Facade pattern** | A structural pattern providing a simplified interface to a complex subsystem — used to hide third-party API integration complexity behind clean test-facing methods |
| **Command pattern** | A behavioural pattern encapsulating an action and its parameters as an object — used to make complex multi-step test workflows reusable and single-responsibility |
| **Repository pattern** | An abstraction layer over data access — used in automation to hide database or API data retrieval behind a domain-language interface |
| **Fluent interface** | A method chaining API style — `Builder.withField(value).withOtherField(value).build()` — enabling readable, declarative object construction |
| **Sensible default** | A pre-populated field value in a builder that most tests do not need to override — allowing tests to specify only the fields relevant to their scenario |
| **Architecture Decision Record (ADR)** | A document recording a significant architectural decision, its context, and the rationale for the chosen approach — essential for communicating pattern choices to future engineers |
