## The Intent
The interviewer is checking whether you have depth in automation architecture beyond POM — and whether you can evaluate when an architectural pattern is the right tool for a given context rather than applying it universally. Screenplay is genuinely more expressive and composable than POM for certain problems; it is also more complex to implement and learn. At senior level, they want to see the trade-off reasoning, not just the pattern description.

## The STAR Script
**Situation:** I was redesigning the automation architecture for a complex B2B SaaS platform with four user roles — admin, manager, analyst, and viewer — each performing overlapping sets of actions in different contexts. The POM-based suite had grown to 280 page objects, many of which were nearly identical for different roles performing the same action (approving a report as a manager vs approving as an admin had 90% identical code but were separate page objects). Maintenance was expensive and the tests did not read like user behaviour — they read like UI navigation scripts.

**Task:** Evaluate whether the screenplay pattern would address the maintenance problem and improved readability, implement a proof of concept, and make a recommendation on migration scope.

**Action:** I built a screenplay pattern proof of concept in TypeScript using the Serenity/JS library, covering the most duplicated section of the suite — report approval across multiple roles. In screenplay terms: an `Actor` (manager, admin) uses an `Ability` (browse the web) to perform `Tasks` (approve a report) using `Interactions` (click the approve button, fill the comment field) and ask `Questions` (is the report status now "Approved"?). The key architectural benefit I identified: the `ApproveReport` task was defined once and could be performed by any actor. The actor's role determined what they could see and access — the task definition did not change. In POM, I had `ManagerReportPage.approveReport()` and `AdminReportPage.approveReport()` — the screenplay pattern collapsed these into one `ApproveReport` task that both actors performed. I implemented 20 tests covering report approval across all four roles using screenplay. Readability comparison — the POM test read: `managerReportPage.navigateToReport(reportId); managerReportPage.clickApproveButton(); managerReportPage.fillApprovalComment('Approved');` The screenplay test read: `await actor.attemptsTo(ApproveReport.withComment('Approved'))`. The screenplay test expressed intent; the POM test expressed implementation. Trade-off assessment: screenplay had three costs — steeper learning curve (5–7 days for an experienced automation engineer to become productive), more upfront design work to define the task and interaction hierarchy, and framework dependency (Serenity/JS added library lock-in). For our specific problem — multi-role overlap and god page objects — the benefits outweighed the costs. For a simpler application with one user role, POM was the better choice.

**Result:** I recommended migrating the multi-role sections of the suite (approximately 30% of tests) to the screenplay pattern and retaining POM for single-role sections where the pattern overhead was not justified. The 20 proof-of-concept tests replaced 60 POM-based tests (three role variants of 20 tests) with no duplication. Maintenance for the migrated section required zero cross-role updates when the approval UI changed — one interaction change propagated correctly to all actors.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Is familiar with POM; may have heard of screenplay but has not used it |
| **Mid** | Understands the screenplay pattern's actor/task/interaction model; can implement basic screenplay tests |
| **Senior** | Evaluates when screenplay offers genuine advantages over POM; implements a proof of concept; makes a bounded migration recommendation; articulates trade-offs including learning curve, framework dependency, and the specific problem contexts where each pattern excels |

## Key Terms

| Term | Definition |
|------|------------|
| **Screenplay pattern** | An automation architecture modelling tests as actors who perform tasks using abilities to interact with interfaces — separating who, what, how, and where into distinct composable layers |
| **Actor** | A screenplay entity representing a user or system persona — carries abilities and performs tasks |
| **Task** | A high-level, business-language action an actor performs — composed of lower-level interactions |
| **Interaction** | A specific UI operation (click, fill, navigate) — the lowest layer of the screenplay pattern |
| **Question** | A screenplay element that retrieves and returns information about the state of the system — the equivalent of an assertion data source |
| **Ability** | A capability an actor possesses that enables interactions — typically "browse the web" wrapping the browser driver |
| **Serenity/JS** | A TypeScript/JavaScript implementation of the screenplay pattern with Cucumber and Playwright integration |
| **Task composability** | The ability to build complex workflows from simpler task primitives — a key advantage of screenplay over POM for multi-step, multi-role tests |
