## The Intent
The interviewer is checking whether you understand accessibility testing as a hybrid discipline — automated tools catch a specific category of issues but cannot replace human testing with assistive technology. At senior level, they want to see that you have integrated accessibility automation meaningfully into a delivery pipeline, understand its coverage limitations honestly, and have designed a complementary approach to manual accessibility testing.

## The STAR Script
**Situation:** My organisation was a UK public sector supplier whose contracts required WCAG 2.1 AA compliance. The accessibility audit conducted six months after the product had launched found 47 accessibility violations — most of which could have been prevented if accessibility testing had been part of the development process. The audit remediation cost three sprints and delayed a contract renewal. I was asked to integrate accessibility testing into the pipeline to prevent recurrence.

**Task:** Design and implement an accessibility automation strategy covering both automated scanning and integration with the manual accessibility testing process — with CI gates that prevented accessibility regression without blocking delivery for every minor violation.

**Action:** I designed the programme across four components. Component 1 — automated scanning with axe-core: I integrated `@axe-core/playwright` into the existing Playwright test suite. After every page navigation in the UI tests, I added an accessibility scan: `const results = await new AxeBuilder({ page }).analyze()`. Rather than failing tests on every violation (which would have blocked delivery immediately given our backlog of existing violations), I implemented a progressive approach. First, I ran a baseline scan across all 30 application pages and catalogued all existing violations — 47 violations across 12 WCAG criteria. These were logged as known violations and excluded from the CI gate using axe's `withTags()` filter to specify which WCAG criteria to enforce. New violations in the enforced criteria blocked the PR. Component 2 — remediation sprint: I ran a focused remediation sprint addressing all 47 baseline violations, clearing them category by category — starting with the highest-impact criteria (WCAG 4.1.2 Name, Role, Value; 1.3.1 Info and Relationships). After each category was clear, I added it to the CI gate. Within four weeks, all known violations were resolved and the full WCAG 2.1 AA criterion set was enforced in CI. Component 3 — component-level scanning: for the design system component library, I integrated axe-core scanning into Storybook using `jest-axe` — every component rendered in Storybook was scanned automatically on every build. This caught accessibility issues at the source before they propagated to page-level tests. Component 4 — manual testing protocol: I documented the 60–70% of accessibility issues that automated tools cannot detect — keyboard navigation flows, screen reader announcement order, focus management after dynamic content changes, and cognitive accessibility issues. I created a manual accessibility test charter for each release covering these areas, and maintained a relationship with a screen reader user who conducted quarterly expert reviews.

**Result:** In the 12 months after implementation, zero new WCAG 2.1 AA violations reached the accessibility audit. The CI gate caught three new violations introduced by developers: a button without an ARIA label added by a developer unfamiliar with accessibility requirements, a colour contrast issue from a design change, and a form input with a missing `<label>` association. Each was caught in the PR and fixed in minutes rather than discovered in audit. The component-level scanning caught two further violations at the design system level before they appeared in any page.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Can run an axe-core scan and read the output; understands that WCAG defines accessibility standards |
| **Mid** | Integrates axe-core into a CI pipeline with severity-based gates; catalogues and manages baseline violations; distinguishes what automated tools can and cannot detect |
| **Senior** | Designs the full accessibility automation programme — baseline management, progressive CI gate enforcement, component-level scanning, and a complementary manual testing protocol that addresses the 60–70% of issues automation cannot find |

## Key Terms

| Term | Definition |
|------|------------|
| **axe-core** | An open-source accessibility testing engine embedded in many testing tools — scans rendered pages for WCAG violations detectable through DOM inspection |
| **WCAG 2.1 AA** | Web Content Accessibility Guidelines version 2.1 at the AA conformance level — the standard required by UK public sector contracts and referenced in the Equality Act 2010 |
| **Automated accessibility coverage** | The proportion of accessibility issues detectable by automated scanning — approximately 30–40%; the remainder require human and assistive technology testing |
| **Baseline violation** | An existing accessibility issue catalogued before CI gate enforcement begins — used to prevent immediate pipeline blockage while remediation is in progress |
| **Progressive gate enforcement** | Adding WCAG criteria to the CI gate incrementally as each category is remediated — preventing a full backlog from blocking the gate |
| **jest-axe** | An axe-core wrapper for Jest that enables accessibility scanning in unit and component tests — catching issues at component level before page-level integration |
| **Screen reader testing** | Manual testing with assistive technology (NVDA, JAWS, VoiceOver) that reproduces the experience of users who navigate by audio — not reproducible through automated scanning |
