## The Intent
The interviewer is checking whether you understand the fundamental testing challenge that asynchronous systems introduce — there is no immediate response to assert on. At senior level, they want to see a concrete design for how to observe, wait for, and verify asynchronous outcomes — including failure handling and the assertion patterns that work for eventually consistent systems.

## The STAR Script
**Situation:** My team was building an order processing system using an event-driven architecture — a customer placed an order via the API, which published an `OrderCreated` event to Kafka, consumed by three downstream services: inventory (reserving stock), fulfilment (scheduling delivery), and notification (sending confirmation email). The entire processing flow was asynchronous — the API returned a 202 Accepted immediately and the downstream effects happened within seconds to minutes. Our existing functional tests only verified the API response (202 and an order ID) — they had no visibility into whether the downstream processing had actually succeeded.

**Task:** Design an automated test strategy for the event-driven processing pipeline — covering event production, downstream consumption, failure handling, and eventual consistency verification.

**Action:** I designed the strategy across five test categories. Category 1 — event production verification: after the API call, I consumed the Kafka topic directly in the test using a Kafka consumer client and asserted on the event schema and payload — the event was produced with the correct order ID, customer ID, product list, and timestamp format. I set a timeout of 5 seconds for the event to appear; if it did not, the test failed. Category 2 — downstream state polling: for each of the three downstream services, I polled their read APIs with retry logic until the expected state appeared or a timeout was reached. For inventory: `await pollUntil(() => inventoryApi.getReservation(orderId) !== null, { timeout: 30000, interval: 1000 })`. The `pollUntil` utility retried every second for up to 30 seconds — the documented processing SLA. If the state did not appear within the SLA, the test failed with the elapsed time. Category 3 — failure mode testing: I published malformed events directly to the Kafka topic (bypassing the API) and verified the downstream services handled them gracefully — logging the error, sending to a dead letter queue, and not corrupting their internal state. Category 4 — duplicate event handling: I published the same `OrderCreated` event twice (simulating a retry scenario) and verified that the downstream services were idempotent — the inventory reservation was not doubled, the notification was sent only once. Category 5 — out-of-order event testing: I published `OrderShipped` before `OrderCreated` for the same order and verified the system queued the out-of-order event and processed it correctly once the prior event arrived, rather than processing it immediately in an invalid state.

**Result:** The test suite provided end-to-end coverage of the asynchronous pipeline — something the API-level tests had completely missed. In the first month it caught three defects: a notification service that was sending duplicate emails when the same event appeared twice (idempotency failure), an inventory service that processed out-of-order events without waiting for the prior event (state corruption risk), and a malformed event that crashed the fulfilment service rather than routing to the dead letter queue (unhanded error case).

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Understands that asynchronous systems have a time delay between action and effect; uses simple polling to wait for state |
| **Mid** | Implements event production verification and state polling with configurable timeout and retry; tests basic failure handling |
| **Senior** | Designs the full async system test strategy — event production, downstream state polling with SLA timeouts, failure mode testing, idempotency verification, and out-of-order event handling — using a reusable polling utility and Kafka consumer integration |

## Key Terms

| Term | Definition |
|------|------------|
| **Event-driven architecture** | A system design where components communicate by producing and consuming events rather than direct synchronous calls |
| **Eventual consistency** | A property of distributed systems where state changes propagate to all components within a defined time window rather than immediately |
| **State polling** | A test technique that repeatedly queries a system's state with retry logic until the expected state appears or a timeout is reached |
| **Dead letter queue** | A message queue receiving events that could not be processed — a resilience mechanism that tests should verify is used for malformed events |
| **Idempotency** | The property that processing the same event multiple times produces the same result as processing it once — critical for systems where duplicate events are expected |
| **Out-of-order event** | An event that arrives before a preceding event it depends on — systems must queue or handle it rather than processing it in an invalid state |
| **SLA timeout** | The maximum time within which an asynchronous process should complete — used as the timeout for state polling assertions |
