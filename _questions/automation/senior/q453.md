## The Intent
The interviewer is checking whether you can design contract testing as an organisational programme rather than a team-level technique. At senior level, they want to see the governance, rollout, and prioritisation decisions that make contract testing sustainable at scale — not just a description of how Pact works.

## The STAR Script
**Situation:** My organisation had 18 microservices with 47 documented service-to-service dependencies. Integration failures in the shared staging environment were causing 3–4 delays per sprint — a service team would deploy a breaking API change, discover it had broken downstream consumers 24 hours later, and require a rollback or emergency coordination. Contract testing had been proposed as a solution but all previous attempts had stalled after two or three service pairs because there was no governance model to sustain it.

**Task:** Design a contract testing programme that would achieve sustainable coverage across the highest-risk service dependencies, with a governance model that made it self-sustaining rather than dependent on my direct involvement.

**Action:** I designed the programme across four components. Component 1 — risk-based prioritisation: I did not try to contract-test all 47 dependencies simultaneously. I mapped all dependencies by two dimensions: change frequency (how often the provider API changed) and consumer criticality (how many consumers and what business impact a failure would have). The top 10 dependencies by combined score covered 70% of the integration failure incidents over the past year. I focused the first phase on these 10 pairs exclusively. Component 2 — governance model: I established three rules that made the programme self-sustaining. Rule 1 — contract ownership: the consumer team owned the contract file and was responsible for keeping it current with what they actually used. Rule 2 — breaking change workflow: any provider API change that would break an existing contract required the provider to notify all registered consumers, coordinate a migration window, and only merge after consumer teams had updated their contracts. This was enforced by the Pact Broker's can-i-deploy check blocking provider deployment if any consumer contract was broken. Rule 3 — new dependency rule: any new service-to-service dependency created in a PR required a corresponding consumer contract before merge. This prevented the backlog from growing while the existing contracts were being established. Component 3 — Pact Broker integration: I deployed a self-hosted Pact Broker and integrated can-i-deploy checks into every service's deployment pipeline. The check queried the broker for all registered contracts and blocked deployment if any were broken. I also configured the broker's webhook to post contract verification results to the relevant teams' Slack channels — making contract status visible without requiring teams to check the broker UI. Component 4 — rollout support: I ran a contract testing workshop for each of the 10 priority service pairs — a 2-hour session where the consumer and provider team QEs wrote their first contract together. Having both teams in the same session made the ownership model tangible rather than theoretical.

**Result:** Within 10 weeks, all 10 priority service pairs had registered contracts and can-i-deploy checks enforcing them. Integration failures caused by breaking API changes in the priority pairs dropped from 3–4 per sprint to zero in the following quarter. Two additional teams voluntarily added contracts for their dependencies without being asked — the can-i-deploy workflow had made the value visible. The new dependency rule prevented 6 new uncontracted dependencies from being introduced in the quarter following the rollout.

| **Mid** | Implements contracts for a specific service pair, publishes to a Pact Broker, and integrates provider verification into CI |

## Key Terms

| Term | Definition |
|------|------------|
| **Consumer-driven contract** | A contract defined by the consumer specifying what it requires from a provider — ensuring provider changes do not break consumers without their knowledge |
| **Pact Broker** | A central server storing contracts, verification results, and deployment compatibility data — the infrastructure enabling can-i-deploy checks |
| **can-i-deploy** | A Pact CLI check confirming whether a service version is compatible with all registered consumer contracts — used as a deployment gate |
| **Breaking change workflow** | A defined process for coordinating API changes that would break existing consumer contracts — notification, migration window, and verification |
| **Risk-based prioritisation** | Selecting which service pairs to contract-test first based on change frequency and consumer criticality — preventing programme scope from becoming unmanageable |
| **New dependency rule** | A governance mechanism requiring a consumer contract before a new service-to-service dependency can be merged — preventing the uncontracted dependency backlog from growing |
| **Self-sustaining programme** | A contract testing programme with governance mechanisms that continue operating without the initiating engineer's direct involvement |
