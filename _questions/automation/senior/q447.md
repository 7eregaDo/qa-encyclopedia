## The Intent
The interviewer is checking whether you have a calibrated, practical view of AI-assisted testing — neither dismissing it as a gimmick nor overstating it as a replacement for skilled test engineering. At senior level, they want to see that you have used these tools in practice, can describe where they added genuine value, and can articulate their limitations with specificity rather than vague caution.

## The STAR Script
**Situation:** My team was under pressure to automate a new feature area quickly — 15 API endpoints and 8 UI flows had been added in a two-week sprint with no automated coverage. Writing tests from scratch would take 3–4 weeks. I wanted to explore whether AI-assisted generation could accelerate initial coverage without compromising quality.

**Task:** Evaluate AI-assisted test generation for both API and UI test creation, establish a quality review process for generated output, and honestly assess where it added value and where it did not.

**Action:** I ran a structured evaluation across three use cases. Use case 1 — API test generation from OpenAPI spec: I fed the OpenAPI specification for the 15 new endpoints to an LLM with a prompt specifying the framework (pytest with requests), the authentication pattern, and the assertion standards we used. The generated output covered happy paths and basic error cases (missing required fields, invalid types) for all 15 endpoints. Review finding: 70% of generated tests were usable with minor corrections — variable names, endpoint paths, and status code assertions were mostly correct. 30% had incorrect assertion values (the expected response body values were plausible-sounding but wrong), missing authentication headers on some endpoints, and no coverage of business-logic-specific scenarios (e.g., creating a duplicate resource). Generation saved approximately 60% of the time that writing from scratch would have taken, but every test required human review before merging. Use case 2 — E2E test generation from user stories: I fed user story acceptance criteria to the LLM requesting Playwright test code. The generated tests used text-based locators (`getByText`, `getByLabel`) that were more brittle than our `data-testid` standard. Generated tests also missed multi-step state dependencies — the LLM generated each acceptance criterion as an independent test without recognising that some required prior state from other tests. Use case 3 — edge case suggestion: the highest-value use case with fewest downsides. I described a payment processing function to the LLM and asked for a list of edge cases and boundary conditions to test. The output included several cases I had not considered — concurrent payment requests, currency precision at specific decimal boundaries, and time zone effects on date-based billing. These were then implemented by the team rather than generated as code.

**Result:** AI-assisted generation reduced API test writing time by approximately 55% for boilerplate-heavy happy path and basic validation tests. It was not useful for E2E tests without significant re-work. Edge case suggestion was the highest ROI use case — 20 minutes of prompting surfaced 8 edge cases that the team then manually implemented correctly. I established a team guideline: generated API tests could be merged after two-engineer review; generated E2E tests required full re-implementation from scratch using generated tests as a structural reference only.

## Key Terms

| Term | Definition |
|------|------------|
| **AI-assisted test generation** | The use of large language models to generate test code, test cases, or test data from specifications, user stories, or prompts |
| **Draft test** | AI-generated test output treated as a starting point requiring human review and correction before it is production-ready |
| **Assertion accuracy** | The correctness of the expected values in AI-generated test assertions — a primary failure mode, as LLMs generate plausible but often incorrect expected values |
| **Edge case suggestion** | Using an LLM to identify boundary conditions and edge cases for human implementation — the highest-value, lowest-risk AI test generation use case |
| **Brittle locator** | A UI element selector likely to break when the UI changes — AI generation frequently produces text-based locators rather than stable `data-testid` selectors |
| **Business context** | Domain-specific knowledge about what the system should do that an LLM cannot infer from code or specs alone — required for correct assertion values and scenario design |
| **Review gate** | A defined quality process requiring human verification of AI-generated test output before it is merged — essential for maintaining suite quality when using generation |
