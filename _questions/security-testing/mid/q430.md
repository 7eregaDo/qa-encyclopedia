## The Intent
The interviewer is checking whether you treat security findings as a regression test asset, not just a remediation task to close. Security vulnerabilities have a well-documented tendency to reappear — the same class of bug is reintroduced in a new feature, a framework upgrade removes a mitigation, or a merge reintroduces patched code. At mid level, they want to see that you encode fixes as tests, not just document them.

## The STAR Script
**Situation:** My team had accumulated 28 security findings over 18 months, all marked as resolved in the defect tracker. During a penetration test, the external firm found that four of those previously-resolved findings had reappeared — including a CSRF protection bypass that had been fixed twice before. The security engineer described it as "whack-a-mole" — the team was fixing vulnerabilities without building any regression protection.

**Task:** Design and implement a security regression test suite that would detect when previously fixed vulnerabilities were reintroduced.

**Action:** I built the regression suite in three stages. Stage 1 — retroactive test creation: I reviewed all 28 closed security findings and wrote a regression test for each. I categorised them into three test types. Automated HTTP-level tests (18 findings): for findings verifiable by sending a specific request and asserting a specific response — CSRF token absence on an endpoint, a missing security header, an IDOR via a specific endpoint pattern — I wrote pytest tests using the `requests` library. Each test reproduced the exact request that had demonstrated the vulnerability and asserted the correct protective behaviour. Example: `test_csrf_token_required_on_password_change()` sent a POST to `/account/password` without a CSRF token and asserted a 403 response. Automated DAST rule tests (6 findings): for findings that OWASP ZAP could detect reliably — specific injection patterns, CORS misconfiguration — I added custom ZAP scan rules and added them to the CI ZAP scan. Documentation-based review tests (4 findings): for findings requiring configuration review (secrets manager configuration, IAM policy review) that were not directly testable via HTTP, I created a quarterly review checklist item with documented expected state. Stage 2 — CI integration: the 18 HTTP-level regression tests ran on every PR as part of the security test suite. A PR could not merge if any regression test failed — the same gate as functional tests. Stage 3 — new finding workflow: I updated the security defect template to include a "Regression Test Reference" field — any security finding that was closed required a corresponding regression test to be committed before the defect could be marked resolved.

**Result:** The regression suite caught two regressions in the first month: a framework upgrade had removed a CSRF middleware that had been protecting all state-changing routes, and a refactor had introduced a new endpoint without the standard authentication decorator — reproducing a previously fixed authentication bypass. Both were caught before code review completed.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Manually retests a security fix after it is deployed; knows that vulnerabilities can reappear |
| **Mid** | Converts confirmed security findings into automated regression tests; integrates them into CI; establishes a workflow requiring regression test creation before a security finding can be closed |
| **Senior** | Designs the security regression testing architecture; defines test categorisation by testability; integrates SAST rules for vulnerability-class regression; measures regression rate as a security programme metric |
