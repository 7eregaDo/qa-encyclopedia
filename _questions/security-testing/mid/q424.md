## The Intent
The interviewer is checking whether you can systematically verify that secrets are handled correctly across the full software lifecycle — from development through CI/CD to production. Secret exposure in source code and container images is one of the most common root causes of data breaches, and a QA engineer who can test for it adds direct security value.

## The STAR Script
**Situation:** My team was preparing for a security audit before an enterprise sales process. One of the audit criteria was evidence of secure secrets management. I was asked to perform an internal assessment before the external auditors arrived.

**Task:** Design and execute a secrets management security assessment covering the codebase, CI/CD pipeline, container images, runtime configuration, and logs.

**Action:** I tested across five layers. Source code and git history: I ran `trufflehog` against the full git repository history — including all branches and tags, not just the current HEAD. TruffleHog identified three high-entropy strings in commits from 18 months ago: a Stripe API key, an AWS access key, and a database password. All had been rotated since but remained in git history, recoverable by anyone with repository access. I also ran `gitleaks` as a second scanner for cross-validation. CI/CD pipeline: I reviewed the GitHub Actions workflow files. Two workflows were injecting secrets as environment variables into Docker build steps — these environment variables would be baked into the image layers if used in a `RUN` command. I reproduced the issue by running `docker history --no-trunc <image>` against the built image and found one database password in a `RUN` layer. Container images: I ran `trivy` against the five production container images, scanning for secrets in filesystem files and environment variables embedded at build time. One image had a `.env` file copied in during build that had not been cleaned up. Runtime configuration: I verified that the production application retrieved secrets from AWS Secrets Manager at runtime rather than from environment variables set at deployment time. I confirmed the secret access was logged in CloudTrail and that IAM roles used the minimum required permissions. Log scanning: I ran a regex search across recent application log exports for common secret patterns — AWS key format, connection strings, JWT secrets. I found database connection strings in error logs — the exception handler was logging the full connection URL including password.

**Result:** Five findings: secrets in git history (high — required history rewriting and key rotation confirmation), secret baked into Docker layer (high), `.env` file in container image (high), and database credentials in error logs (medium). All were remediated before the audit. The external auditors reviewed the remediation evidence and confirmed the secrets management posture was satisfactory.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Checks that obvious credentials are not hardcoded in source files; knows that `.env` files should not be committed |
| **Mid** | Scans full git history with automated tools, reviews Docker image layers, tests runtime secrets injection, audits log outputs for secret leakage, and verifies IAM minimum privilege for secret access |
| **Senior** | Designs the secrets management testing programme; defines secret rotation testing; reviews secrets manager access controls and audit logging; integrates secret scanning into pre-commit hooks and CI gates |

## Key Terms

| Term | Definition |
|------|------------|
| **TruffleHog** | An open-source tool that scans git repositories for high-entropy strings and known secret patterns across the full commit history |
| **Gitleaks** | An open-source secrets scanner for git repositories that uses regex patterns to detect credentials and API keys |
| **Docker layer** | A filesystem layer in a Docker image created by each instruction in the Dockerfile — secrets baked into layers during build remain accessible in the image history |
| **Trivy** | An open-source vulnerability and secrets scanner for container images, filesystems, and infrastructure as code |
| **AWS Secrets Manager** | A managed secrets service that stores, rotates, and audits access to credentials and API keys — the preferred alternative to environment variables for runtime secret injection |
| **CloudTrail** | An AWS service that logs all API calls and secret access events — used to audit who accessed which secrets and when |
| **Secret rotation** | The periodic replacement of a credential with a new value — a security practice that limits the window of exposure if a credential is compromised |
| **IAM minimum privilege** | The assignment of the narrowest AWS Identity and Access Management permissions necessary for a function to access only the specific secrets it requires |
