## The Intent
The interviewer is checking whether you understand security headers not as a checklist to tick but as mitigations with specific purposes — and whether you can evaluate whether each header's configuration actually provides the intended protection. Many applications add headers to pass automated scans without configuring them meaningfully.

## The STAR Script
**Situation:** A penetration test report had listed several missing or misconfigured security headers as medium-severity findings. The development team had added the headers to resolve the findings but had used default configurations. I was asked to verify that the headers were now providing genuine protection.

**Task:** Assess each security header for presence and whether the configuration meaningfully mitigated the intended attack.

**Action:** I evaluated six headers, testing presence and configuration quality. Content-Security-Policy (CSP): the header was present but set to `default-src *; script-src * 'unsafe-inline' 'unsafe-eval'`. This configuration permitted inline scripts and eval, making it useless as an XSS mitigation. I assessed it as technically present but effectively absent. A meaningful policy required specifying explicit trusted origins and removing `unsafe-inline`. Strict-Transport-Security (HSTS): the header was present with `max-age=300` — a 5-minute HSTS duration. This meant any user who had not visited in the past 5 minutes was vulnerable to SSL stripping on first visit. A meaningful value was at least 1 year (`max-age=31536000`), ideally with `includeSubDomains` and submitted to the HSTS preload list. X-Frame-Options: set to `SAMEORIGIN` — correct, preventing clickjacking by denying framing from third-party origins. X-Content-Type-Options: set to `nosniff` — correct, preventing MIME-type sniffing attacks where browsers execute uploaded content as scripts. Referrer-Policy: absent. I demonstrated that navigating from a page with a session token in the URL (a legacy pattern in the application) would send the full URL including the token as the `Referer` header to third-party resources (analytics scripts). `strict-origin-when-cross-origin` was recommended. Permissions-Policy: absent. The application did not use camera, microphone, or geolocation — restricting these explicitly prevented compromised third-party scripts from accessing them.

**Result:** I rated the security header posture as partially implemented — headers were present but CSP and HSTS were configured for compliance optics rather than genuine protection. I produced a header configuration specification with exact recommended values and the attack scenario each mitigated. The development team updated all six headers. The CSP policy required the most work — three weeks of iterative refinement to identify all legitimate script sources without breaking functionality.

## Key Terms

| Term | Definition |
|------|------------|
| **Content-Security-Policy (CSP)** | An HTTP header specifying which sources of scripts, styles, and other resources the browser may load — the primary browser-enforced XSS mitigation |
| **Strict-Transport-Security (HSTS)** | An HTTP header instructing the browser to only access the site over HTTPS for the specified duration — preventing SSL stripping attacks |
| **X-Frame-Options** | An HTTP header preventing the page from being embedded in a frame on a third-party origin — mitigating clickjacking attacks |
| **X-Content-Type-Options: nosniff** | A header preventing the browser from MIME-type sniffing — ensuring the browser treats responses as the declared content type and not as executable script |
| **Referrer-Policy** | An HTTP header controlling how much referrer information is included in requests from the page — preventing URL-embedded tokens from leaking to third parties |
| **Permissions-Policy** | An HTTP header restricting which browser features (camera, microphone, geolocation) the page and its embedded frames may access |
| **HSTS preload** | A browser mechanism where a domain is hardcoded as HTTPS-only in the browser's source code — providing protection even on first visit before any header has been received |
| **unsafe-inline** | A CSP directive that permits inline script execution — effectively disabling CSP's XSS mitigation, present in many nominally-CSP-compliant configurations |
