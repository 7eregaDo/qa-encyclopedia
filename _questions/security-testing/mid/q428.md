## The Intent
The interviewer is checking whether you recognise that the browser is an untrusted execution environment — and that any security control implemented only in client-side code can be bypassed by any user with developer tools. At mid level, they want to see that you examine the client as part of your security review, not just the server.

## The STAR Script
**Situation:** I was performing a security review of a single-page application built in React. The backend API had been tested separately, but I wanted to assess the client-side implementation for vulnerabilities specific to the browser environment.

**Task:** Review the React SPA for client-side security vulnerabilities — covering storage, sensitive data exposure, DOM security, and client-side access control enforcement.

**Action:** I reviewed five client-side security areas. Browser storage misuse: I opened the browser developer tools and inspected localStorage, sessionStorage, and IndexedDB. I found three items in localStorage: the user's JWT access token, the user's role (used to show/hide UI elements), and a cached copy of the user's profile including their date of birth. Storing JWTs in localStorage exposes them to XSS theft — tokens should be in HttpOnly cookies. Storing the role in client-side storage and using it for UI rendering was not itself a vulnerability but indicated the pattern of trusting client-side data. Sensitive data in JavaScript source: I searched the minified bundle and source maps for patterns matching API keys, internal endpoint paths, and hardcoded credentials. The source maps were publicly accessible at `/static/js/main.chunk.js.map` — exposing the full un-minified application source. Within the source I found a hardcoded internal admin API path and a commented-out test credential from a previous developer. HTML comment exposure: I reviewed the HTML source for comments. Several contained internal system names, developer names, and one contained a TODO referencing a security issue: `// TODO: remove test bypass for admin before prod`. Client-side access control: the application conditionally rendered admin UI components based on the user's role stored in localStorage. I modified the role value from `user` to `admin` in localStorage and refreshed. The admin UI was now visible. I then called the admin API endpoints directly to confirm they had server-side controls — they did. The client-side control was cosmetic, which was acceptable, but I flagged it as a pattern to document clearly so future developers did not add admin functionality accessible only via the UI without API protection. postMessage: I searched the codebase for `window.addEventListener('message')` and found one handler. It accepted messages from any origin (`event.origin` was not checked) and used `innerHTML` to render the message content — a DOM XSS vulnerability.

**Result:** Four findings: JWT in localStorage (medium), source maps publicly exposed (medium — enables reconnaissance), hardcoded admin path and test credential in source (high), and postMessage DOM XSS (high). The postMessage finding was the most impactful — any page that could embed the application in an iframe could inject arbitrary HTML.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Checks localStorage for sensitive data; reviews HTML source for obvious hardcoded credentials |
| **Mid** | Tests localStorage, sessionStorage, source map exposure, HTML comments, client-side access control patterns, and postMessage security; understands the distinction between cosmetic and genuine client-side security controls |
| **Senior** | Designs the client-side security review methodology; reviews JavaScript frameworks for known XSS sinks; assesses service worker security; reviews CSP for client-side XSS mitigation effectiveness |

## Key Terms

| Term | Definition |
|------|------------|
| **localStorage** | A browser storage API persisting data across sessions — accessible to any JavaScript on the same origin, making it vulnerable to XSS-based token theft |
| **Source map** | A file mapping minified JavaScript back to the original source code — when publicly accessible, it exposes application logic, internal paths, and potentially embedded secrets |
| **Client-side access control** | Security enforcement implemented in JavaScript that prevents users from seeing or interacting with functionality based on their role — bypassable without server-side backing |
| **postMessage** | A browser API for cross-origin iframe communication — insecure when the receiving handler does not validate the sender's origin before processing the message |
| **DOM XSS sink** | A JavaScript property or method that writes message content to the DOM in a way that executes scripts — including `innerHTML`, `document.write`, and `eval` |
| **HttpOnly cookie** | A cookie inaccessible to JavaScript — the recommended storage mechanism for session tokens to prevent XSS-based theft |
| **Reconnaissance** | The information-gathering phase of an attack — source map exposure aids reconnaissance by revealing application structure, internal paths, and logic |
| **Cosmetic control** | A UI restriction that hides functionality from the interface without enforcing it at the API level — not a security vulnerability if the API is protected, but a documentation risk if it is not |
