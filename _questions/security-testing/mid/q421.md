## The Intent
The interviewer is checking whether your XSS testing is systematic — covering all three XSS types across all rendering contexts — rather than submitting `<script>alert(1)</script>` in a few input fields and calling it done. XSS remains consistently in OWASP Top 10 because applications have many rendering contexts, each requiring different payloads and different output encoding, and teams routinely miss the less obvious ones.

## The STAR Script
**Situation:** I was performing security testing on a customer support portal that allowed support agents to create tickets, search existing tickets, and view rich-text notes. The application rendered user input in multiple places — search results, ticket titles, ticket bodies, and agent notes. I needed to test for XSS systematically across all three XSS types.

**Task:** Design and execute a systematic XSS test suite covering reflected, stored, and DOM-based XSS across all user-controlled rendering contexts.

**Action:** I mapped the application's rendering contexts first — six distinct places where user input appeared in the browser: search query reflected in results header, ticket title displayed in list and detail views, ticket description rendered as HTML (rich text), agent notes rendered as HTML, user display name shown in the ticket footer, and a client-side URL parameter used to pre-select a tab. I then tested each context by XSS type. Reflected XSS: I submitted `<script>alert(document.domain)</script>` in the search field. The query was reflected in the results heading — the script tags were HTML-encoded in the element text but I noticed the query also appeared as a raw parameter in a data attribute: `data-query="<user input>"`. I injected `" onmouseover="alert(1)` to break out of the attribute context — confirmed reflected XSS via attribute injection. Stored XSS: in the ticket description (rich text), the server was using a sanitisation library but with an outdated version that did not block `<img src=x onerror=alert(1)>` — confirmed stored XSS. In agent notes, I submitted `<svg onload=alert(1)>` — confirmed stored XSS via SVG. DOM-based XSS: the tab pre-selection used `location.hash` read by a JavaScript snippet that set `innerHTML`. I submitted `#<img src=x onerror=alert(1)>` in the URL hash — confirmed DOM XSS, entirely client-side with no server involvement. I also tested CSP headers — the application's Content Security Policy allowed `unsafe-inline` scripts, meaning CSP offered no meaningful mitigation.

**Result:** Four confirmed XSS findings across three types: one reflected (attribute injection), two stored (rich text and SVG), and one DOM-based. The stored XSS in ticket descriptions was highest severity — support agents viewing any ticket created by a malicious user would execute attacker-controlled script. All four were fixed: the sanitisation library was updated, the CSP was tightened to remove `unsafe-inline`, and the DOM XSS was fixed by replacing `innerHTML` with `textContent`.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Submits basic script tags in input fields; tests obvious reflected XSS; may not test stored or DOM-based XSS |
| **Mid** | Maps all rendering contexts; tests all three XSS types; uses attribute injection and event handler payloads; tests HTML sanitisation libraries for bypass; reviews CSP headers for effectiveness |
| **Senior** | Designs the XSS security testing strategy; tests CSP bypass techniques; reviews JavaScript frameworks for known XSS sinks; assesses Content-Type and X-Content-Type-Options headers; integrates SAST for XSS-prone code patterns |

## Key Terms

| Term | Definition |
|------|------------|
| **Reflected XSS** | XSS where the malicious payload is submitted in a request and immediately reflected in the response without being stored — typically exploited via a crafted link |
| **Stored XSS** | XSS where the payload is persisted to the server (database, file) and served to other users who view the affected content — generally more severe than reflected XSS |
| **DOM-based XSS** | XSS where the payload is processed entirely client-side — read from a DOM source such as `location.hash` and written to a DOM sink such as `innerHTML` — without the server being involved |
| **Rendering context** | The specific location in a page where user data appears — HTML element content, attribute value, JavaScript string, URL — determining which characters are dangerous and which encoding applies |
| **Attribute injection** | An XSS technique that breaks out of an HTML attribute value to inject event handler code — for example, `" onmouseover="alert(1)` |
| **Content Security Policy (CSP)** | An HTTP response header specifying which sources of scripts, styles, and other resources the browser may load — a mitigation layer for XSS when correctly configured |
| **DOM sink** | A JavaScript property or method that writes data to the DOM in a way that can execute scripts — including `innerHTML`, `document.write`, and `eval` |
