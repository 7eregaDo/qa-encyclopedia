## The Intent
The interviewer is checking whether you can operationalise SCA scanning — not just run a tool, but configure it meaningfully, manage the findings lifecycle, and make informed decisions about which vulnerabilities require immediate action and which represent tolerable risk. The challenge is managing signal-to-noise: a default scan of any mature application will return hundreds of findings, most requiring triage.

## The STAR Script
**Situation:** My team had never performed dependency scanning. An external security assessment recommended it as a high priority — the assessment had manually identified four vulnerable libraries in our Python and JavaScript dependencies. I was asked to implement continuous dependency scanning and establish a remediation workflow.

**Task:** Implement dependency vulnerability scanning in our CI pipeline, establish triage criteria for findings, and set up an ongoing remediation process.

**Action:** I implemented scanning in three stages. Tool selection and initial scan: I used `pip-audit` for Python dependencies and `npm audit` for JavaScript, with `trivy` as a container-level scanner covering both. I ran the initial scan against all three and received 847 findings total — a number that immediately highlighted the need for triage criteria before any CI gate could be set. Triage criteria: I defined four classification criteria for each finding. Severity (CVSS score): critical (CVSS ≥ 9.0) and high (CVSS ≥ 7.0) required action. Exploitability: was the vulnerable code path actually called in our application? Many CVEs affect library features we did not use — I documented these as accepted risk with a review date. Fix available: was an upgraded version available that resolved the vulnerability? If not, the finding required an alternative mitigation assessment. Reachability: was the vulnerable library in the production application or only in the development/test toolchain? Development-only dependencies were deprioritised. Applying these criteria to the 847 initial findings: 12 were critical or high with a fix available and a reachable code path — requiring immediate remediation. 43 were critical or high but either development-only or unreachable. 792 were medium or low. CI gate configuration: I configured the CI pipeline to fail on critical findings with a fix available. I used `trivy`'s `--exit-code 1 --severity CRITICAL --ignore-unfixed` flags to enforce this precisely — failing only on critical, fixed vulnerabilities and not on issues without available fixes. I committed a `.trivyignore` file to suppress accepted-risk findings with documented rationale and a review date. Remediation workflow: I created a monthly dependency review task to address high-severity findings and review accepted-risk entries whose review dates had passed.

**Result:** The 12 immediate findings were remediated in the first sprint — 10 by upgrading the library, 2 by replacing unmaintained libraries with maintained alternatives. The CI gate blocked one deployment in the following month when a new dependency was added that had a known critical CVE. The monthly review process caught a library where a CVE had been initially accepted as unreachable but a new code path had made it reachable.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Can run `npm audit` or `pip-audit` and read the output; understands that vulnerable dependencies introduce risk |
| **Mid** | Integrates SCA scanning into CI with severity-based gates, establishes triage criteria distinguishing exploitable from theoretical exposure, manages the findings lifecycle with a remediation workflow |
| **Senior** | Designs the SCA programme across the full technology stack; defines the vulnerability management policy; implements SBOM generation; assesses licence compliance alongside security; integrates with vulnerability management platforms |

## Key Terms

| Term | Definition |
|------|------------|
| **SCA (Software Composition Analysis)** | A security testing technique that identifies known vulnerabilities in third-party libraries and their transitive dependencies by matching them against CVE databases |
| **CVE (Common Vulnerabilities and Exposures)** | A standardised identifier for publicly disclosed security vulnerabilities — used by SCA tools to match library versions against known weaknesses |
| **CVSS (Common Vulnerability Scoring System)** | A standardised 0–10 scoring framework for rating the severity of security vulnerabilities — used to prioritise remediation |
| **Transitive dependency** | A library that your application depends on indirectly — because one of your direct dependencies requires it — and which may contain vulnerabilities not visible in your direct dependency list |
| **Reachability** | The property that a vulnerable code path in a library is actually called by the application — unreachable vulnerabilities represent theoretical rather than practical risk |
| **Trivy** | An open-source vulnerability scanner covering container images, filesystems, and IaC — supporting multiple languages and package managers |
| **SBOM (Software Bill of Materials)** | A machine-readable inventory of all components, libraries, and their versions in an application — required by some regulatory frameworks and enterprise customers |
| **Accepted risk** | A documented decision to tolerate a known vulnerability because it is unreachable, development-only, or has no available fix — with a defined review date |
