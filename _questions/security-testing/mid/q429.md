## The Intent
The interviewer is checking whether you test access control as a server-side enforcement problem, not a navigation problem. Many developers implement access control by controlling navigation — preventing lower-privilege users from seeing links or buttons — but not by enforcing it at the request level. At mid level, they want to see that you bypass the UI systematically to test what the server actually enforces.

## The STAR Script
**Situation:** I was testing a content management system with three roles: author (create content, edit own content), editor (edit all content, publish), and admin (user management, system configuration). I was asked to perform access control testing focused on the web application flows rather than the API layer.

**Task:** Design and execute web application access control tests covering forced browsing, function-level enforcement, and role-based feature access — bypassing the UI to test server-side enforcement directly.

**Action:** I tested across four access control dimensions. Forced browsing to protected pages: I logged in as an author and directly navigated to URLs I had observed while logged in as an admin — `/admin/users`, `/admin/config`, and `/admin/audit-log`. The user management page returned a 200 with full content. The server was checking authentication (I needed to be logged in) but not authorisation (any logged-in user could access admin pages). Function-level access control: from the author session, I sent a POST request to `/content/{id}/publish` — an action only editors should perform. The UI showed no publish button for authors, but the endpoint returned a 200 and the content was published. I also tested `/users/{id}/delete` from the author session — same result, the action completed without an authorisation check. Horizontal access control on content: I created a draft article as author A, captured its ID, then logged in as author B and sent `GET /content/{id}/edit` and `PUT /content/{id}` requests with author B's session. Both returned 200 — authors could read and edit each other's unpublished drafts. Parameter-based role switching: I inspected the request body for the profile update endpoint and found it included a `role` field. I submitted `"role": "admin"` and found the server applied the new role — a mass assignment vulnerability enabling self-promotion to admin.

**Result:** Four findings: admin page accessible to all roles (critical), publish and delete actions enforceable by any logged-in user (high), horizontal access on drafts (medium), and mass assignment role escalation (critical). The critical findings — admin page access and self-promotion to admin — were treated as P0 and fixed same-day. The function-level checks were added to the server-side middleware within the sprint.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Navigates to restricted pages while logged out; tests obvious role-based UI restrictions |
| **Mid** | Bypasses the UI to test server-side enforcement; tests forced browsing, function-level access, horizontal access control, and parameter-based privilege escalation across all roles |
| **Senior** | Designs the access control security architecture; maps every protected resource and action to its authorisation requirement; integrates automated access control testing using tools like Autorize in Burp Suite |

## Key Terms

| Term | Definition |
|------|------------|
| **Forced browsing** | Directly navigating to a URL without following the application's normal navigation flow — used to test whether protected pages enforce server-side authorisation |
| **Function-level access control** | Server-side enforcement that prevents a user from performing an action (create, publish, delete) based on their role — as opposed to hiding the action in the UI |
| **Horizontal access control** | Enforcement preventing a user from accessing or modifying another user's resources at the same privilege level |
| **Authorise** | A Burp Suite extension that automatically replays requests with a lower-privilege session to detect access control failures |
| **Navigation control** | Client-side access control implemented by hiding or disabling UI elements for lower-privilege users — bypassable by direct HTTP requests without server-side enforcement |
| **Mass assignment** | A vulnerability where the server applies client-supplied fields that should not be user-controlled — such as a `role` field — because input is not whitelisted |
| **Role-based access control (RBAC)** | An authorisation model assigning permissions to roles and roles to users — requires server-side enforcement on every request, not just UI-level navigation restrictions |
| **Middleware** | A server-side component that processes requests before they reach the application logic — the appropriate place to enforce access control checks consistently across all routes |
