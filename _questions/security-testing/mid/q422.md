## The Intent
The interviewer is checking whether you understand CSRF as a class of vulnerability with specific conditions and specific protections — and whether you can test the protection mechanism rather than just assert it is present. Many applications implement CSRF tokens incorrectly — absent on some endpoints, reusable, predictable, or bypassed by CORS misconfiguration.

## The STAR Script
**Situation:** I was performing a security review of a financial services web application. The development team had implemented CSRF tokens and believed CSRF was fully mitigated. I was asked to verify this assumption systematically.

**Task:** Test CSRF protection across all state-changing endpoints and verify the token implementation could not be bypassed.

**Action:** I tested CSRF protection across five dimensions. Token presence: I used Burp Suite to intercept all POST, PUT, PATCH, and DELETE requests during a standard user session and checked each for a CSRF token in either the request body or a custom header. Three endpoints were missing tokens entirely — the password change endpoint, the notification preference update, and the profile picture upload. Token validation: for endpoints that did have tokens, I tested whether the server actually validated them. I sent a request with the token parameter present but set to an empty string — the server accepted it. I then sent the request with the token parameter removed entirely — also accepted. The token was being generated client-side but never verified server-side. Token uniqueness and entropy: I captured 20 CSRF tokens from fresh requests and compared them. All 20 were identical — the same static value. A token with no randomness provides no CSRF protection. SameSite cookie attribute: I reviewed the session cookie attributes. The cookie lacked `SameSite=Strict` or `SameSite=Lax` — meaning cross-origin requests would include the session cookie in browsers that default to `SameSite=None`. CORS header interaction: I checked the CORS configuration. The `Access-Control-Allow-Origin` header was set to a wildcard for API endpoints — combined with `Access-Control-Allow-Credentials: true`, this was a CORS misconfiguration that could allow credential-bearing cross-origin requests, amplifying the CSRF risk.

**Result:** Four findings: missing tokens on three endpoints (high), token accepted when empty or absent (critical — the entire token mechanism was decorative), static non-random token (critical), and CORS misconfiguration (high). The engineering team had implemented the UI component for tokens but never wired up server-side validation. All were corrected: server-side token validation was implemented, tokens were made per-session random values, missing tokens were added, and the CORS wildcard was replaced with an explicit allowlist.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Knows what CSRF is and can check whether a CSRF token is present in a form |
| **Mid** | Tests token presence across all state-changing endpoints, validates server-side enforcement by submitting empty or absent tokens, checks token entropy and uniqueness, reviews SameSite attributes and CORS configuration |
| **Senior** | Designs CSRF test strategy; tests login CSRF, JSON-based CSRF, and multipart form CSRF; assesses framework-level CSRF middleware configuration; reviews double-submit cookie patterns for bypass |

## Key Terms

| Term | Definition |
|------|------------|
| **CSRF (Cross-Site Request Forgery)** | An attack where a malicious site causes a victim's browser to send a state-changing request to another site where the victim is authenticated |
| **CSRF Token** | An unpredictable, session-bound value included in state-changing requests and validated server-side — the standard mitigation for CSRF attacks |
| **SameSite Cookie Attribute** | A cookie attribute controlling whether the cookie is sent with cross-origin requests — `Strict` prevents all cross-origin cookie inclusion, `Lax` allows safe-method cross-origin requests |
| **Token Entropy** | The unpredictability of a CSRF token — a token with low entropy (static, predictable, or short) can be guessed or reused, negating its protection |
| **CORS Misconfiguration** | An incorrect CORS policy — such as a wildcard origin with credentials — that allows cross-origin credential-bearing requests, amplifying CSRF and data exposure risk |
| **Server-Side Validation** | The verification of a CSRF token on the server with every state-changing request — without this, a client-side token implementation provides no actual protection |
| **Login CSRF** | A CSRF attack targeting the login form to force the victim to log in as the attacker, enabling session fixation or privacy violations |
| **Double-Submit Cookie** | A CSRF mitigation pattern that sends the same random value as both a cookie and a request parameter, relying on the same-origin policy to prevent forgery |
