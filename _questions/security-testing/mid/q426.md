## The Intent
The interviewer is checking whether your authentication testing goes deeper than verifying that the login form works. Authentication is the most critical security control in any application — and its advanced mechanisms (MFA, SSO, lockout) each have specific vulnerability patterns that require deliberate adversarial testing. At mid level, they want to see coverage of at least two of these three areas with concrete test design.

## The STAR Script
**Situation:** I was performing security testing on a B2B SaaS application that had recently added TOTP-based MFA and SAML SSO for enterprise customers. The application also had an account lockout mechanism on the login endpoint. I was asked to security-test all three authentication mechanisms.

**Task:** Design and execute security tests for TOTP MFA, SAML SSO, and account lockout — targeting their specific vulnerability patterns rather than functional correctness.

**Action:** I tested each mechanism for its known security weaknesses. TOTP MFA testing: Code reuse — I obtained a valid TOTP code, used it to complete MFA, then immediately submitted the same code again in a new authentication attempt. The server accepted it — TOTP codes should be single-use, marked as consumed after first use. Code window — I generated a TOTP code for the 30-second window, waited for the window to expire, and submitted the expired code. It was accepted — the server was allowing a generous ±2 window (90-second acceptance window) which was wider than the recommended ±1. Fallback bypass — the application offered "send a backup code via email" as a fallback. I tested whether completing MFA via email backup was logged differently and whether the fallback could be triggered without the user's knowledge by an attacker who had the password and email access. SAML SSO testing: I captured a SAML assertion in Burp Suite and tested three manipulations. I modified the `NameID` attribute (the user identifier) to another user's email address — the application accepted the modified assertion without verifying the XML signature. This was a critical finding — signature verification was not implemented. I also tested XML signature wrapping: I copied the valid signature block into a crafted assertion while keeping the signed original as a decoy — a known SAML attack pattern. Account lockout testing: I submitted incorrect passwords from the same IP — lockout triggered at 10 attempts as documented. I then tested distributed brute-force: 10 attempts from IP A, then 9 attempts from IP B — no lockout, confirming the lockout was IP-bound rather than account-bound. An attacker with multiple IPs could try unlimited passwords. I also tested lockout as a DoS vector: I repeatedly triggered lockout on a known account (the CEO's email, publicly available) — the account locked immediately, confirming a targeted DoS was possible.

**Result:** Three critical/high findings: TOTP code reuse accepted (high), SAML assertion signature not verified (critical — authentication bypass), and account-level lockout not enforced (high). The SAML finding was the most severe — the SSO integration had never enforced XML signature verification, meaning any authenticated SAML IdP session could impersonate any user. Emergency fix deployed within 4 hours.

## Key Terms

| Term | Definition |
|------|------------|
| **TOTP (Time-based One-Time Password)** | An MFA mechanism generating a 6-digit code from a shared secret and the current timestamp — valid for a short time window and should be single-use |
| **Code reuse attack** | An attack exploiting a TOTP implementation that does not invalidate used codes — allowing a captured code to authenticate a second session |
| **SAML (Security Assertion Markup Language)** | An XML-based protocol for federated SSO — the identity provider issues a signed XML assertion that the service provider validates before granting access |
| **XML Signature Wrapping** | A SAML attack where the valid signature block is kept intact while the assertion content is modified — exploiting parsers that validate the signature but read data from a different node |
| **Account-level lockout** | Lockout enforced on the target account regardless of the source IP — more robust than IP-level lockout against distributed brute-force attacks |
| **Lockout DoS** | The exploitation of account lockout as a denial-of-service mechanism — repeatedly locking a victim's account by submitting incorrect credentials |
| **SAML assertion** | An XML document issued by a SAML identity provider containing the authenticated user's identity claims — must have its XML signature verified by the service provider |
| **MFA fallback** | An alternative authentication path offered when the primary MFA method is unavailable — often weaker and a bypass vector if not equally secured |
