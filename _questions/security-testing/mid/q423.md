## The Intent
The interviewer is checking whether you treat session management as a distinct security test domain with its own vulnerability taxonomy. Session attacks are consistently exploitable in applications that implement authentication correctly but session lifecycle incorrectly — a distinction many testers miss.

## The STAR Script
**Situation:** I was performing a security review of a healthcare web application handling patient records. The application used server-side sessions. I was asked to assess the security of the session management implementation.

**Task:** Design and execute a systematic test of the session management security — covering token quality, secure transmission, lifecycle management, and session isolation.

**Action:** I tested across six areas. Token entropy: I captured 50 session tokens from fresh logins and analysed their entropy using a statistical randomness test. The tokens were 32 characters but based on a timestamp-seeded pseudo-random generator — the entropy was insufficient for a high-value application. A cryptographically secure random generator was required. Secure transmission: I checked the session cookie attributes — `HttpOnly` (prevents JavaScript access), `Secure` (HTTPS only), and `SameSite`. `HttpOnly` was set; `Secure` was absent, meaning the cookie would be transmitted over HTTP if the user ever accessed an HTTP URL. Session fixation: before logging in, I captured the pre-authentication session ID, then logged in, and checked whether the session ID changed post-login. It did not — the same session ID was used before and after authentication. This is a session fixation vulnerability: an attacker who can set a victim's session ID (via URL parameter injection) will have the victim's authenticated session after they log in. Logout invalidation: I captured a session token, logged out, then used the captured token in a subsequent request. The server accepted it — the session had not been invalidated server-side on logout. Concurrent session control: the application allowed unlimited simultaneous sessions from the same account. I logged in from two browsers simultaneously — both sessions were fully active. For a healthcare application, this created a risk of undetected unauthorised parallel access. Session timeout: I left a session idle for 45 minutes and verified it was rejected on the next request. The configured timeout was 60 minutes — appropriate, but I verified the check was server-side, not relying on a client-side timer.

**Result:** Three findings: session fixation (high), no server-side session invalidation on logout (critical — any captured token remained valid indefinitely), and missing `Secure` cookie attribute (medium). The logout invalidation defect was the most severe — a session token captured via network interception, XSS, or log leakage would remain valid until the server restarted. All were fixed before the application went to production.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Checks HttpOnly and Secure cookie attributes; verifies that logout appears to work from the user's perspective |
| **Mid** | Tests session token entropy, fixation, server-side logout invalidation, timeout behaviour, concurrent session controls, and cookie security attributes comprehensively |
| **Senior** | Designs session management security architecture; tests JWT-based session patterns; reviews session store configuration; assesses distributed session handling in load-balanced environments |

## Key Terms

| Term | Definition |
|------|------------|
| **Session Fixation** | A vulnerability where an attacker can force a victim to use a known session ID, then gain authenticated access after the victim logs in |
| **Session Hijacking** | The theft of a valid session token by an attacker — through network interception, XSS, or log exposure — enabling impersonation of the authenticated user |
| **HttpOnly** | A cookie attribute preventing JavaScript from accessing the cookie value — mitigating XSS-based session token theft |
| **Secure** | A cookie attribute ensuring the cookie is only transmitted over HTTPS connections — preventing interception over unencrypted channels |
| **Server-Side Session Invalidation** | The deletion or expiry of a session record on the server when a user logs out — without this, captured tokens remain valid indefinitely |
| **Session Token Entropy** | The unpredictability of a session token — tokens with low entropy are vulnerable to brute-force or prediction attacks |
| **Concurrent Session Control** | A policy limiting the number of simultaneous active sessions per account — enforcing this limits the impact of session token theft |
| **Idle Timeout** | The maximum period of inactivity after which a session is automatically invalidated server-side — a defence against unattended authenticated sessions |
