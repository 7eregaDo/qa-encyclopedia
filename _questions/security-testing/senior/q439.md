## The Intent
The interviewer is checking whether you treat secrets rotation as a testable engineering property rather than an operational procedure that is assumed to work. Many applications fail silently or catastrophically during credential rotation — connection pool exhaustion, cached credentials causing auth failures, or hardcoded credentials that were never wired to the secrets manager. These failures are only discovered under the pressure of a real rotation event. At senior level, they want to see that you test rotation before it becomes an emergency.

## The STAR Script
**Situation:** My organisation had implemented AWS Secrets Manager for all database credentials and API keys, with automatic rotation configured for every secret. A rotation event had caused a two-hour production outage six months earlier — the application had cached the database credentials in a connection pool at startup and did not reload them when the secret rotated. I was asked to design tests that would verify rotation worked correctly for all secrets, before any future rotation event.

**Task:** Design and execute a secrets rotation test suite covering the rotation mechanism, application reload behaviour, connection pool handling, and credential caching.

**Action:** I designed the test suite across four areas. Area 1 — rotation mechanism verification: I manually triggered rotation for a non-production secret and verified the full Lambda rotation function executed correctly — the secret was updated in Secrets Manager, the new credential was validated against the target system, and the old credential was invalidated. I also verified the rotation function had appropriate error handling: I deliberately introduced a misconfiguration in the rotation function and confirmed it failed safely, leaving the old credential valid rather than invalidating it before the new one was confirmed working. Area 2 — application runtime reload testing: I triggered a secret rotation in the staging environment while the application was serving traffic and observed its behaviour using load testing with 20 concurrent users. The application should detect the new secret version and reload without dropped connections. In the initial test, it failed — 45 seconds of authentication errors while the connection pool drained and reconnected with cached credentials. I worked with the development team to implement the recommended AWS pattern: on a database auth error, the application fetches the latest secret version from Secrets Manager and retries — one retry per connection, transparent to the caller. I re-tested after the fix: zero authentication errors during rotation. Area 3 — connection pool behaviour: I specifically tested connection pool handling during rotation. During the rotation window, existing connections authenticated with the old credential remain valid until they are closed. New connections must use the new credential. I verified the application's connection pool was configured with a maximum connection age (30 minutes) so no connection persisted beyond the rotation window, and that the pool retried failed authentication rather than marking connections as permanently failed. Area 4 — credential caching audit: I reviewed the codebase for any location where secrets were read at startup and stored in memory without a refresh mechanism. I found two places: an API client was initialised with a hardcoded API key read at application start, and a third-party SDK was initialised with a database URL containing the password, read once at boot. Both were refactored to read the secret on each initialisation and implement a periodic refresh.

**Result:** The rotation test prevented the repeat of the original outage. The combination of retry-on-auth-error and connection age limits meant rotation was now zero-downtime. The credential caching audit found the two startup-read patterns that would have caused failures — fixing them before any production rotation event. I scheduled quarterly rotation drills in the staging environment as a standing operational practice.

## Key Terms

| Term | Definition |
|------|------------|
| **Secrets rotation** | The replacement of a credential (database password, API key) with a new value, invalidating the old credential — a security practice limiting the exposure window of a compromised secret |
| **Rotation Lambda** | An AWS Lambda function that implements the four-step secrets rotation process: create new credential, update secret, test new credential, invalidate old credential |
| **Connection pool** | A set of pre-established database connections maintained by the application for reuse — connections authenticated with the old credential must be replaced during rotation |
| **Retry-on-auth-error** | An application pattern where a database authentication failure triggers a re-fetch of the current secret version and a reconnection attempt — the standard pattern for zero-downtime rotation |
| **Connection age limit** | A connection pool configuration specifying the maximum time a connection may be kept open — essential during rotation to ensure no connection persists beyond the rotation window using stale credentials |
| **Credential caching** | The storage of a secret value in application memory at startup — creating a failure point during rotation if the cached value is not refreshed |
| **Rotation drill** | A scheduled test of the full rotation process in a staging environment — verifying rotation is zero-downtime and that all applications handle the credential change correctly |
| **Zero-downtime rotation** | The successful replacement of a credential without any service interruption or authentication errors for users |
