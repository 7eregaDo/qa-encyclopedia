## The Intent
The interviewer is checking whether you can solve the tension that every security programme faces: comprehensive coverage versus developer productivity. At senior level, they want to see that you have designed this balance deliberately — with specific decisions about what gates on every PR, what runs asynchronously, and how findings are communicated to developers without creating noise that trains them to ignore security feedback.

## The STAR Script
**Situation:** I was asked to expand the security testing coverage in our CI/CD pipeline. The existing pipeline had one Semgrep check that was taking 4 minutes per PR and producing 30% false positives — developers had started ignoring it. I needed to add DAST, dependency scanning, IaC scanning, and secrets detection without pushing pipeline duration above 10 minutes or further eroding developer trust in security tooling.

**Task:** Design a tiered security testing architecture for the CI/CD pipeline that achieved comprehensive coverage without exceeding time constraints or generating noise that developers would ignore.

**Action:** I redesigned the pipeline around three tiers with different timing, scope, and gating behaviour. Tier 1 — fast gates on every PR (target: under 5 minutes combined, hard fail on critical only): I replaced the slow Semgrep full-scan with an incremental scan on changed files only — reducing from 4 minutes to 45 seconds. I added `gitleaks` for secrets detection (15 seconds), `trivy` image scan on changed services only (60 seconds), and `checkov` IaC scan on changed Terraform files only (30 seconds). Total: under 3 minutes. For gating: Tier 1 blocked merges only on Critical findings — defined as: confirmed secrets detected, critical CVE with a fix available, or a checkov Critical misconfiguration. High findings produced a non-blocking annotation visible in the PR. Medium and below were logged but not surfaced in the PR. Tier 2 — thorough checks on merge to main (target: under 20 minutes, non-blocking with SLA): on merge to main, I ran a full authenticated ZAP DAST scan against the deployment in the integration environment, full dependency tree scan with `trivy` (not just changed services), and a full Semgrep scan across the entire codebase. Results were posted to a security findings board and assigned to the owning team with a 5-day SLA for High findings and a 30-day SLA for Medium. These did not block deployment — they created tracked tickets with defined remediation expectations. Tier 3 — scheduled weekly deep scans (asynchronous, no merge blocking): weekly full DAST scan with an aggressive active scan policy, dependency audit across all environments, and a kube-bench cluster security assessment. Findings from weekly scans fed the security technical debt backlog, reviewed monthly by the engineering lead. False positive management: I introduced a scan configuration review every 6 weeks — if a Tier 1 finding had been suppressed more than three times across different PRs, it was a candidate for removal from the blocking ruleset or a custom suppression rule. This prevented the accumulation of security noise that had eroded developer trust.

**Result:** Pipeline duration for Tier 1 dropped from 4 minutes (single noisy tool) to 3 minutes (four tools with better signal). Developer complaints about security pipeline false positives dropped by 80% in the quarter following the redesign — measured through a team survey. The Tier 2 asynchronous scan caught seven High findings in the first month that would previously have required a quarterly pen test to discover. The monthly technical debt review kept the Tier 3 findings from accumulating — 91% of High findings were remediated within SLA.

| Level | Expected Depth |

| **Mid** | Configures individual security tools in CI with severity-based gates; manages false positives through suppression files |

## Key Terms

| Term | Definition |
|------|------------|
| **Tiered pipeline** | A CI/CD security architecture applying different tools at different stages — fast focused checks on PRs, thorough checks post-merge, and deep scheduled scans — balancing speed with coverage |
| **Incremental scan** | A SAST or IaC scan applied only to files changed in the current PR, rather than the entire codebase — maintaining fast feedback without sacrificing coverage on new code |
| **Non-blocking annotation** | A CI finding displayed as a review comment without failing the pipeline — surfacing security information to developers without impeding merges for non-critical issues |
| **Findings SLA** | A defined maximum time within which a security finding of a given severity must be remediated — creating accountability without requiring all findings to block deployment |
| **False positive governance** | A regular review process identifying and removing scan rules that consistently produce incorrect findings — maintaining developer trust in security tooling |
| **Security technical debt backlog** | A tracked collection of lower-severity security findings that do not require immediate action — reviewed periodically to prevent accumulation |
| **Asynchronous security check** | A security scan that runs after a deployment without blocking it, reporting findings to a tracked queue rather than failing the pipeline |
| **Signal-to-noise ratio** | The proportion of security findings that represent genuine, actionable issues versus false positives — a high ratio is essential for developer trust in security tooling |
