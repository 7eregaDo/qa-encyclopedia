## The Intent
The interviewer is checking whether you recognise that infrastructure configuration is code — and that security defects in IaC are as catchable at the point of change as application code vulnerabilities. At senior level, they want to see that you can design an IaC security testing programme with meaningful gates, false positive management, and a feedback loop that builds developer awareness.

## The STAR Script
**Situation:** My organisation used Terraform to manage all AWS infrastructure. A post-incident review had identified that an S3 bucket containing customer PII had been misconfigured with public read access — a Terraform change made six months earlier. The IaC repository had no security scanning. Every misconfiguration was being deployed directly to production before anyone reviewed it from a security perspective.

**Task:** Design and implement an IaC security testing programme that would catch misconfigurations at the point of change — in the PR, before deployment.

**Action:** I designed the programme across three components. Component 1 — tool selection and baseline: I evaluated `tfsec`, `checkov`, and `terrascan` against our Terraform codebase. I selected `checkov` for its broad rule coverage across AWS, Azure, and Kubernetes and its support for custom policy writing in Python. I ran an initial baseline scan and received 347 findings — a number that required triage before any CI gate could be meaningful. I spent two days categorising all existing findings: Critical (open security groups to `0.0.0.0/0`, missing encryption on databases, publicly accessible S3 buckets) — 12 findings requiring immediate remediation. High (missing logging, overly permissive IAM, non-encrypted EBS volumes) — 41 findings scheduled for remediation. Accepted/suppressed (findings that were intentional, such as a public S3 bucket serving the marketing website's static assets) — 89 findings documented with business rationale. Medium and low — tracked but not gating. Component 2 — CI gate configuration: I configured checkov in the GitHub Actions pipeline with three behaviours. Hard fail: any new Critical finding in a PR blocked the merge — using checkov's `--soft-fail` flag combined with a baseline file that excluded pre-existing known findings, so the gate applied only to newly introduced misconfigurations. Soft fail with annotation: new High findings created a non-blocking PR annotation visible to the reviewer. Baseline file management: I committed the `.checkov.baseline` file and required a second reviewer to approve any suppression added to it — preventing developers from silently bypassing the gate. Component 3 — developer feedback: I wrote a one-page Terraform security guide covering the ten most commonly violated rules with correct code examples — added to the team's engineering handbook. I ran a 45-minute session showing developers how to read checkov output and what each finding meant architecturally.

**Result:** The CI gate caught the exact type of misconfiguration that had caused the original incident — a new S3 bucket with a permissive ACL — in a PR submitted two weeks after implementation. The developer corrected it before review. The 12 critical baseline findings were remediated within the first sprint. After three months, the average number of new checkov findings per PR had dropped from 4.2 to 0.8 — evidence that the developer guide and feedback loop were working.

## Key Terms

| Term | Definition |
|------|------------|
| **Infrastructure-as-Code (IaC)** | The practice of defining infrastructure configuration in version-controlled code (Terraform, CloudFormation, Pulumi) — enabling code review, testing, and version history for infrastructure changes |
| **Checkov** | An open-source static analysis tool for Terraform, CloudFormation, and Kubernetes manifests — detecting security misconfigurations against hundreds of built-in policies |
| **tfsec** | An open-source Terraform-specific security scanner with a focus on AWS, Azure, and GCP misconfigurations |
| **Baseline file** | A checkov configuration recording pre-existing known findings to exclude from CI gates, ensuring the pipeline fails only on newly introduced misconfigurations |
| **Soft fail** | A checkov mode that reports findings without returning a non-zero exit code — used for informational annotations without blocking the pipeline |
| **Suppression governance** | A process requiring review and approval before a finding is added to the suppression list — preventing developers from silently disabling security gates |
| **ACL (Access Control List)** | An S3 access control mechanism — permissive ACLs (e.g. `public-read`) expose bucket contents to unauthenticated internet access |
| **Custom policy** | A user-defined checkov rule written in Python to detect organisation-specific misconfigurations not covered by built-in rules |
