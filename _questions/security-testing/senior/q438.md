## The Intent
The interviewer is checking whether you can evaluate zero-trust not as a marketing concept but as a set of verifiable security properties. Many organisations claim to have implemented zero-trust without testing whether implicit trust assumptions have actually been eliminated. At senior level, they want to see that you can design tests that distinguish genuine zero-trust from perimeter security with a rebranded name.

## The STAR Script
**Situation:** My organisation had completed an 18-month zero-trust migration — replacing VPN-based network access with identity-aware proxies, implementing device posture checking, and decomposing the flat internal network into micro-segmented zones. The CISO asked me to verify that the zero-trust properties held in practice — that the migration had eliminated implicit trust assumptions rather than just adding an authentication layer on top of an unchanged network.

**Task:** Design and execute a zero-trust verification test that confirmed each core zero-trust property was functioning as intended.

**Action:** I tested five zero-trust properties systematically. Property 1 — no implicit network trust: I provisioned a device on the internal corporate network (simulating an insider or a compromised device on-premises) and attempted to access internal services without authentication — the same tests that would have worked before the migration when the network itself was the trust boundary. Every service rejected unauthenticated requests with 401 — network location alone granted no access. Property 2 — identity verification per request: I captured a valid access token and replayed it after its expiry (30 minutes). The identity-aware proxy rejected the expired token — confirming per-request verification rather than session-level caching. I also tested token scope enforcement: a token issued for the HR application was rejected by the Finance application — confirming that tokens were scoped to specific resources. Property 3 — device posture enforcement: I attempted to access internal services from a device with an outdated OS version that did not meet the device posture policy. The identity-aware proxy returned a remediation page rather than granting access — confirming device posture was evaluated. I then temporarily disabled the endpoint security agent on a compliant device and retried — access was revoked within the agent's heartbeat interval (90 seconds). Property 4 — lateral movement prevention: from a compromised application server (simulated by executing commands from within an application pod), I attempted to reach services in other micro-segments that the application had no business need to access. All attempts were blocked by network micro-segmentation policies — confirming that a compromised workload could not pivot laterally. Property 5 — audit completeness: I verified that every access attempt — both granted and denied — was logged with the requesting identity, device ID, resource, timestamp, and policy decision. I sampled 50 requests from the previous hour and confirmed all appeared in the audit log. I also tested a denial scenario to confirm denied access was logged — a missing entry would indicate a gap in audit completeness.

**Result:** Four findings: one service was not routing through the identity-aware proxy (accessing it directly by internal IP bypassed authentication — a configuration gap), device posture re-evaluation was not triggered promptly on agent disablement (90-second gap was acceptable but the CISO requested a reduction to 30 seconds), one token scope was broader than required (the HR token also granted read access to payroll), and audit logs were not being retained for the required 12 months (configured for 90 days). All were addressed within the sprint.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Understands what zero-trust means conceptually — never trust, always verify |
| **Mid** | Tests that authentication is required regardless of network location; verifies token expiry enforcement |
| **Senior** | Designs systematic zero-trust verification tests covering all five properties — network trust elimination, per-request identity verification, device posture enforcement, lateral movement prevention, and audit completeness |

## Key Terms

| Term | Definition |
|------|------------|
| **Zero-trust architecture** | A security model eliminating implicit trust based on network location — every access request is verified based on identity, device posture, and least-privilege policy |
| **Identity-aware proxy** | A security component that authenticates and authorises every request based on user identity and device posture before forwarding it to the target service |
| **Device posture** | The security state of a device — OS version, patch level, endpoint agent status — evaluated as part of the access decision in a zero-trust model |
| **Micro-segmentation** | The division of a network into small, isolated zones with controlled inter-zone communication — preventing lateral movement between workloads |
| **Token scope** | The set of resources a specific access token is authorised to access — enforcing least privilege at the token level |
| **Lateral movement prevention** | A zero-trust property ensuring that a compromised workload cannot reach other internal resources it has no business need to access |
| **Audit completeness** | The property that every access attempt — granted or denied — is recorded in an immutable log with sufficient detail for security investigation |
| **Per-request verification** | The evaluation of identity and policy on every individual request, rather than establishing trust once at session creation and caching it |
