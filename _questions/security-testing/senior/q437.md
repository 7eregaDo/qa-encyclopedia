## The Intent
The interviewer is checking whether you understand supply chain attacks as a distinct security threat class — where the attacker compromises a dependency, a build tool, or the CI/CD pipeline rather than the application itself. After high-profile incidents like SolarWinds and the XZ Utils backdoor, supply chain security is an active concern for senior security engineers. At senior level, they want to see systematic coverage of the build pipeline as an attack surface.

## The STAR Script
**Situation:** Following a sector-wide advisory about dependency confusion attacks targeting our industry, my CISO asked me to assess our supply chain security posture. We used npm for JavaScript, pip for Python, and a self-hosted CI/CD pipeline. I had no existing supply chain security controls to build on.

**Task:** Design and implement a supply chain security testing programme covering dependency integrity, build pipeline security, and artefact verification.

**Action:** I addressed supply chain security across four areas. Area 1 — dependency source integrity: I audited our npm and pip configurations for dependency confusion risks — cases where a private package name could be shadowed by a public package with the same name on the public registry. I found three internal Python packages with names that did not exist on PyPI — a dependency confusion window. I mitigated this by publishing placeholder packages to PyPI under those names and configuring pip to use a trusted private index with `--index-url` and `--extra-index-url` priority. I also enabled lock files (`package-lock.json` and `requirements.txt` with pinned hashes) and verified them in CI — preventing any dependency from being silently upgraded to a compromised version. Area 2 — build pipeline security: I reviewed the CI/CD pipeline configuration (GitHub Actions) for injection risks. I found four workflow files using `${{ github.event.pull_request.head.sha }}` in `run:` commands directly — a script injection vulnerability where a PR with a malicious branch name could execute arbitrary commands in the CI environment. I also found that the pipeline used `actions/checkout@main` rather than a pinned SHA — meaning a compromised action could alter pipeline behaviour. I pinned all third-party actions to specific commit SHAs and parameterised the vulnerable workflow interpolations. Area 3 — artefact integrity: I implemented artefact signing using `cosign` on all container images pushed to the registry. Every image was signed at build time with a key stored in AWS KMS. The deployment pipeline was updated to verify the signature before pulling an image — rejecting any unsigned or incorrectly signed image. Area 4 — SBOM generation: I integrated `syft` to generate an SBOM for every container image at build time, stored alongside the image in the registry. This provided a complete inventory of every component in each deployed image — enabling rapid impact assessment when new CVEs were published.

**Result:** The dependency confusion assessment identified a real window in our Python packages — a researcher had already registered one of our private package names on PyPI (a benign researcher testing the same attack pattern, not malicious). The placeholder publication prevented future exploitation. The GitHub Actions script injection vulnerabilities would have allowed a PR from a forked repository to exfiltrate CI secrets. Three of the four were in workflows triggered by `pull_request_target` — a known high-risk configuration. All were fixed before any external contribution arrived.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Understands that third-party dependencies can introduce vulnerabilities; runs dependency vulnerability scans |
| **Mid** | Implements lock files and dependency scanning; checks CI pipeline for obvious secret exposure |
| **Senior** | Designs the supply chain security programme — dependency confusion mitigation, CI/CD pipeline injection testing, artefact signing, and SBOM generation — treating the build pipeline as an attack surface |

## Key Terms

| Term | Definition |
|------|------------|
| **Dependency confusion** | A supply chain attack where a malicious package with the same name as a private internal package is published to a public registry — causing package managers to install the malicious version |
| **Lock file** | A file recording the exact versions and cryptographic hashes of all dependencies — enabling integrity verification and preventing silent version changes |
| **Script injection (CI)** | A vulnerability in CI/CD workflow files where untrusted values (branch names, PR titles) are interpolated directly into shell commands — enabling arbitrary code execution in the CI environment |
| **Artefact signing** | The process of cryptographically signing a build output (container image, binary) to enable downstream verification that the artefact was produced by a trusted build process |
| **cosign** | An open-source tool from the Sigstore project for signing and verifying container images |
| **SBOM (Software Bill of Materials)** | A machine-readable inventory of all components and their versions in a software artefact — enabling rapid impact assessment when vulnerabilities are disclosed |
| **syft** | An open-source tool for generating SBOMs from container images and filesystems |
| **pull_request_target** | A GitHub Actions trigger that runs with repository secrets in the context of a PR — dangerous if the workflow uses PR-controlled values in commands, as it allows fork-based PRs to access secrets |
