## The Intent
The interviewer is checking whether your security testing extends to the container runtime and orchestration layer. Applications deployed on Kubernetes inherit the security posture of the cluster — and a misconfigured cluster can turn an application-layer compromise into a full cluster takeover. At senior level, they want to see systematic coverage of both image security and runtime configuration.

## The STAR Script
**Situation:** My organisation had migrated all application workloads to Kubernetes six months earlier. The security programme had not been updated to address container-specific security concerns — image scanning was manual and infrequent, and the cluster had been deployed using default configurations. An external security review had flagged container security as an unaddressed risk area.

**Task:** Design and implement a container and Kubernetes security testing programme covering image security, runtime configuration, and cluster hardening.

**Action:** I structured the programme across four layers. Layer 1 — image scanning in CI: I integrated `trivy` into the build pipeline, scanning every container image on every PR and blocking on critical CVEs with a fix available. I also added a `trivy` misconfiguration scan using the `--security-checks config` flag, which analysed the Dockerfile for security issues — finding two images running as root (should specify a non-root USER), one image with an exposed unnecessary port, and one image copying a `.env` file into the image. Layer 2 — runtime privilege testing: I reviewed all pod specifications for privilege escalation risks using `kube-score` and manual review. Findings: three pods had `privileged: true` in the security context — full host-level access, unnecessary for any of them. Two pods had `allowPrivilegeEscalation: true` without business justification. I wrote a test using `kubectl auth can-i` commands to verify that workload service accounts could not perform administrative Kubernetes API operations — two service accounts had excessive RBAC permissions. Layer 3 — network policy testing: I verified that Kubernetes NetworkPolicies were in place restricting inter-pod communication to documented required paths. The cluster had no NetworkPolicies — all pods could communicate with all other pods by default. I tested this empirically by executing a shell in one pod and attempting to connect to another pod's internal port — successfully connected. I documented this as a lateral movement risk: a compromised pod could reach the database pods directly. Layer 4 — cluster-level hardening: using `kube-bench` (implementing CIS Kubernetes Benchmark checks), I ran an automated assessment of the cluster control plane and node configurations. Significant findings: anonymous authentication was enabled on the kubelet API, the etcd data was not encrypted at rest, and Pod Security Admission was not configured to enforce a baseline security standard.

**Result:** Fourteen findings across the four layers. The critical findings — privileged pods, open cluster networking, and kubelet anonymous auth — were addressed within two sprints. The CI image scanning integration prevented a vulnerable base image (containing a critical CVE) from being deployed two weeks after implementation. The NetworkPolicy implementation reduced the blast radius of any future container compromise significantly.

## Seniority Shift

| Level | Expected Depth |
|-------|---------------|
| **Entry** | Understands that containers should not run as root; is aware that image scanning exists |
| **Mid** | Runs container image scans, checks security context for privileged flags, reviews Dockerfile for obvious security issues |
| **Senior** | Designs the full container and Kubernetes security testing programme — image scanning in CI, runtime privilege testing, network policy verification, and CIS benchmark assessment — connecting container security to the overall application security programme |

## Key Terms

| Term | Definition |
|------|------------|
| **Trivy** | An open-source vulnerability and misconfiguration scanner for container images, filesystems, and Kubernetes manifests |
| **Privileged container** | A container with `privileged: true` in its security context — granting full access to the host's devices and kernel capabilities, equivalent to root on the host |
| **kube-score** | An open-source tool that analyses Kubernetes manifests for security and reliability best practice violations |
| **kube-bench** | An open-source tool implementing the CIS Kubernetes Benchmark security checks against a running cluster |
| **NetworkPolicy** | A Kubernetes resource restricting which pods can communicate with each other — without policies, all pods can reach all other pods by default |
| **Pod Security Admission** | A Kubernetes admission controller enforcing security standards on pod creation — preventing privileged pods, host path mounts, and other dangerous configurations |
| **RBAC (Role-Based Access Control)** | The Kubernetes mechanism controlling which identities (users, service accounts) can perform which actions on which resources |
| **Lateral movement** | A post-compromise technique where an attacker moves from a compromised container to other workloads, databases, or the Kubernetes API — facilitated by absent NetworkPolicies or overpermissioned service accounts |
